## 核心理念速览

| 产品 | 核心设计哲学 | 代表交互 | 数据模型 |
|------|-------------|---------|---------|
| **Anytype** | Everything is an Object | 图视图、动态集合 | Object-Type-Relation-Set |
| **Warp** | Block-based Terminal | 命令面板、AI 命令生成 | Block（命令+输出） |
| **Notion** | Everything is a Block | Slash 命令、多视图 | Block（段落/页面/数据库） |
| **SoloSoul** | 管理的是"你" | 结构化卡片、敏感度分级 | Object-Type-Property（见下文章节） |

**关键认知**：SoloSoul 已经在做的很多设计，与 Anytype 的"对象模型"本质上是**同一条路**。本文的目的是：识别重叠、发现差距、决定取舍。

## 【高优先级】术语统一规范

> **优先级：P0（最高）**
>
> **状态**：待实施
>
> **影响范围**：Rust 代码、TypeScript 代码、数据库 Schema、API 命名、文档、UI 文案
>
> **理由**：SoloSoul 的对象模型与 Anytype 是同一套模型，但术语不统一导致沟通成本高、代码可读性差、文档与代码脱节。重构阶段是统一术语的唯一窗口期。

### 当前术语混乱现状

SoloSoul 的代码和文档中，同一概念使用了多个不同的名称：

| 概念 | Anytype 术语 | 当前 Flutter 代码 | 当前文档 | 问题 |
|------|------------|------------------|---------|------|
| 一个数据条目 | **Object** | `UnifiedObject` | "对象" / "项目" / "条目" | 三个名称指同一事物 |
| 对象的类型定义 | **Type** | `ObjectTypeDefinition` | "类型定义" / "对象类型" | 名称过长，冗余 |
| 对象的属性定义 | **Property** | `PropertyDefinition` | "属性" / "字段" / "Property" | "字段"和"属性"混用 |
| 对象间的关系 | **Relation** | `RelationProperty` | "关系" / "关联" | 与 Property 概念重叠 |
| 对象的集合 | **Set** / **Collection** | `Collection` | "分区" / "Collection" | UI 叫"分区"，代码叫 Collection |
| 属性的值 | **Value** | `PropertyValue` / `FieldValue` | "值" / "字段值" | 与 Property/Field 不对应 |

### 统一后的术语规范

**原则**：向 Anytype 的简洁术语靠拢，减少命名冗余，确保代码、文档、UI 三方一致。

| 概念 | 建议统一术语 | Rust 结构体 | TypeScript 接口 | UI 显示 | 说明 |
|------|------------|------------|----------------|--------|------|
| 一个数据条目 | **Object** | `Object` | `Object` | "对象" | `UnifiedObject` → `Object` |
| 对象的类型定义 | **Type** | `Type` | `ObjectType` | "类型" | `ObjectTypeDefinition` → `Type` |
| 对象的属性定义 | **Property** | `Property` | `ObjectProperty` | "属性" | `PropertyDefinition` → `Property`，废弃"字段" |
| 对象间的关系 | **Relation** | `Relation` | `ObjectRelation` | "关联" | `RelationProperty` → `Relation`，与 Property 分离 |
| 对象的集合 | **Collection** | `Collection` | `Collection` | "集合" | 废弃"分区"，统一为"集合" |
| 属性的值 | **Value** | `PropertyValue` | `PropertyValue` | "值" | 统一前缀为 Property |
| 对象类型模板 | **Template** | `TypeTemplate` | `TypeTemplate` | "模板" | 新增概念，见借鉴 3 |
| 动态筛选集合 | **SmartCollection** | `SmartCollection` | `SmartCollection` | "智能集合" | 新增概念，见借鉴 2 |

## 一、Anytype — 一切皆对象

### 1.1 Anytype 的核心设计

| 概念 | 说明 | 技术实现 |
|------|------|---------|
| **Object** | 每个条目都是一个类型化的对象（Page, Book, Person, Task...） | 每个对象有唯一 ID、类型标识、属性集合 |
| **Type** | 对象有类型，类型定义该对象可以有哪些属性（Property） | 类型是可扩展的，用户可自定义新类型 |
| **Relation** | 对象之间可以建立关系（如"Person - 写过 - Book"） | 双向关系，图数据库风格 |
| **Set/Collection** | 按类型 + 属性筛选对象组成集合（类似数据库视图） | 动态筛选规则，非手动组织 |
| **Graph View** | 对象和关系形成知识图谱 | 力导向图可视化 |
| **Any-Sync** | 本地优先 + P2P CRDT 同步 | MIT 开源协议，DAG 数据结构 |

### 1.2 与 SoloSoul 的模型对比

> 以下对比使用**统一后的术语**（见上文【术语统一规范】）。当前代码中的旧名称在括号中标注。

```
Anytype                    SoloSoul（统一术语后）
─────────────────────────────────────────────────────────
Object 对象                Object（原 UnifiedObject）✅ 已存在
Type 类型                  Type（原 ObjectTypeDefinition）✅ 已存在
Property 属性              Property（原 PropertyDefinition）✅ 已存在
Relation 关系              Relation（原 RelationProperty）✅ 已存在
Set/Collection 集合        Collection（原"分区"）✅ 已存在
Graph View 图视图          ❌ 暂无
P2P CRDT 同步              Any-Sync 参考 ✅ 已规划
本地优先                   ✅ 完全一致
零知识架构                 ✅ 完全一致
```

**关键发现**：SoloSoul 的 `Object` + `Type` + `Property` + `Relation` + `Collection` 与 Anytype 的模型**完全对应**。两者的差异仅在**术语尚未统一**（代码中仍使用旧名称）和**UI 呈现方式**，不在数据模型本身。

> **开发约定**：所有新代码必须使用统一术语（`Object`、`Type`、`Property`、`Relation`、`Collection`）。旧代码在重构阶段逐步迁移。

### 1.3 可借鉴的具体点

#### ✅ 借鉴 1：Graph View（知识图谱可视化）— 优先级 P2

Anytype 的图视图可以直观展示"护照→签证→旅行记录"的关系链。SoloSoul 的 `RelationProperty` 已经支持这种关系，只是缺少可视化。

**价值**：用户可以看到自己的身份数据如何相互关联——比如"这张银行卡绑定了哪个旅行预订"。

**实现思路**：
```typescript
// 在对象工作区页面增加"关系图"视图
interface GraphViewNode {
  id: string;
  label: string;           // 对象名称
  type: string;            // 对象类型（护照/银行卡/旅行记录）
  icon: string;            // 类型图标
  sensitivity: SensitivityLevel;
}

interface GraphViewEdge {
  source: string;          // 源对象 ID
  target: string;          // 目标对象 ID
  relationType: string;    // 关系类型（"绑定" / "属于" / "关联"）
}
```

**注意**：敏感对象在 Graph View 中应遵循现有的敏感度遮盖规则（sensitive/critical 节点需要解锁后才显示标签）。

#### ✅ 借鉴 2：Set 的动态筛选规则 — 优先级 P3

Anytype 的 Set 是**按类型和属性动态筛选**（如"显示所有类型为'银行卡'且过期日在 30 天内的对象"），而 SoloSoul 的 Collection 是**手动组织的容器**。

**价值**：用户不需要手动将每个新银行卡拖入"即将过期"集合，系统自动筛选。

**实现思路**：
```rust
// Collection 支持动态筛选规则
pub enum CollectionRule {
    Static,                          // 当前：手动添加/移除
    Dynamic(DynamicFilter),          // 新增：按规则自动筛选
}

pub struct DynamicFilter {
    pub object_type: Option<String>,         // 只包含特定类型的对象
    pub sensitivity_level: Option<SensitivityLevel>,  // 只包含特定敏感度
    pub property_filter: Option<PropertyFilter>,       // 按属性值筛选
    pub date_filter: Option<DateFilter>,               // 按日期筛选（如"30 天内过期"）
}
```

**注意**：动态集合的筛选规则本身属于用户偏好，应加密存储。筛选结果在 Vault 锁定后不可见。

#### ✅ 借鉴 3：对象类型模板（Type Template）— 优先级 P2

> **重要说明**：SoloSoul **已经实现了类似功能**——`SectionTemplate`（分区模板，代码中 `PresetSectionTemplates`）。但现有实现与 Anytype 的 `Type Template` **处于不同层级**。两者是**互补关系，不是替代关系**。

##### 现有功能：`SectionTemplate`（分区模板）

SoloSoul 当前已有 `SectionTemplatePage`，用户点击"+ 添加分区"时弹出模板选择器，选择后创建一个包含预定义字段的分区：

```dart
// 现有代码（lib/core/models/section_template.dart）
SectionTemplate {
  id: 'china_bank_account',
  nameKey: 'templateChinaBankAccountName',
  fields: [
    TemplateField(key: 'bank_name',      type: 'text', sensitivity: public),
    TemplateField(key: 'account_number', type: 'text', sensitivity: critical),
    TemplateField(key: 'account_holder', type: 'text', sensitivity: sensitive),
  ],
  pageTag: 'bank',
}
```

**`SectionTemplate` 的定位**：
- **层级**：Collection（分区/页面）级别
- **作用时机**：用户手动选择模板后创建分区
- **内容**：字段列表 + 字段类型 + 敏感度分级
- **存储**：代码硬编码（`PresetSectionTemplates.templates`）

##### Anytype 借鉴：`TypeTemplate`（对象类型模板）

Anytype 的类型模板是**类型定义的一部分**，在新建**单个对象**时自动填充属性默认值：

```rust
// 借鉴后的设计：Type 增加 default_properties
pub struct Type {
    pub id: String,
    pub name: String,
    pub properties: Vec<Property>,
    pub template: Option<TypeTemplate>,  // ← 新增：属性级别的默认值
}

pub struct TypeTemplate {
    pub default_values: HashMap<String, PropertyValue>,
}

// 示例：中国护照类型的默认值
let passport_cn = Type {
    id: "passport_cn".to_string(),
    name: "中国护照".to_string(),
    properties: vec![number, name, nationality, issue_date, expiry_date, ...],
    template: Some(TypeTemplate {
        default_values: hashmap! {
            "nationality" => PropertyValue::Text("中国".to_string()),
            "country_code" => PropertyValue::Text("CHN".to_string()),
        },
    }),
};
```

**`TypeTemplate` 的定位**：
- **层级**：Object / Property 级别
- **作用时机**：新建单个对象时**自动**应用
- **内容**：属性的默认值
- **存储**：类型定义的一部分（用户数据，可扩展）

##### 两者的层级差异

```
用户操作流
├── 1. 创建 Collection（分区）
│   └── 使用 SectionTemplate（现有）→ 决定分区内有哪些字段
│       └── 示例：选择"护照"模板 → 创建包含 number/issue_date/expiry_date 的集合
│
└── 2. 在 Collection 中创建 Object（对象）
    └── 使用 TypeTemplate（借鉴）→ 决定对象属性的默认值
        └── 示例：选择"中国护照"类型 → nationality 自动填"中国"
```

| 维度 | `SectionTemplate`（现有） | `TypeTemplate`（借鉴） |
|------|--------------------------|----------------------|
| **层级** | Collection 级别 | Object / Property 级别 |
| **作用** | 创建分区时的字段蓝图 | 新建对象时的属性默认值 |
| **时机** | 手动选择后 | 自动应用 |
| **内容** | 字段列表 + 类型 + 敏感度 | 属性默认值 |
| **用户可扩展** | ❌ 不可（仅预设） | ✅ 可（用户自定义类型） |
| **术语统一后** | `CollectionTemplate` | `TypeTemplate` |

##### 结合使用的最佳体验

**场景：用户在旅行页面添加一本中国护照**

```
步骤 1（SectionTemplate / CollectionTemplate）
├── 用户点击"+ 添加分区"
├── 选择"护照"模板
└── 系统创建一个"护照"集合，包含 number/issue_date/expiry_date 等字段

步骤 2（TypeTemplate）
├── 用户在护照集合中点击"新建对象"
├── 选择类型"中国护照"
├── 系统自动填充：
│   ├── nationality = "中国"
│   └── country_code = "CHN"
└── 用户只需填写：号码、有效期等个性化信息
```

**价值**：
- `SectionTemplate`：减少"从头创建分区"的操作成本
- `TypeTemplate`：减少"重复填写相同默认值"的输入成本
- 两者结合：用户选择模板 → 创建分区 → 新建对象 → 自动填充 → 只需填写个性化信息

##### 现有 `SectionTemplate` 的术语统一

重构后，`SectionTemplate` 应更名为 `CollectionTemplate`，与统一术语保持一致：

```rust
// 术语统一后
pub struct CollectionTemplate {
    pub id: String,
    pub name: String,
    pub description: String,
    pub icon: String,
    pub page_tag: String,           // 所属页面分类
    pub fields: Vec<TemplateField>, // 预定义字段
}

pub struct TemplateField {
    pub key: String,
    pub name: String,
    pub property_type: PropertyType,
    pub sensitivity: SensitivityLevel,
    pub validation: Option<PropertyValidation>,
    pub default_value: Option<PropertyValue>,  // ← 可联动 TypeTemplate
}
```

**注意**：`CollectionTemplate` 中的 `default_value` 可以与 `TypeTemplate` 联动——如果 CollectionTemplate 的字段有默认值，且该字段对应类型的 TypeTemplate 也有默认值，以 **TypeTemplate 为准**（类型级别 > 集合级别）。

### 1.4 不适合借鉴的点

| Anytype 特性 | 不适合的理由 |
|-------------|-------------|
| 弱 Schema 约束 | Anytype 允许用户任意创建类型和属性。SoloSoul 是**强 Schema**——护照必须有"号码"字段，且号码必须符合护照格式。弱约束会削弱"结构化数字孪生"的核心价值 |
| 通用笔记导向 | Anytype 的对象可以是任意笔记（自由文本）。SoloSoul 的对象是**结构化身份数据**（有类型、有验证、有敏感度）。不应变成"任意笔记工具" |
| 开放协作空间 | Anytype 支持多人共享空间。SoloSoul 是**单人本地应用**，不需要协作功能 |

## 二、Warp — 块级交互

### 2.1 Warp 的核心设计

Warp 是 AI 驱动的现代终端，其核心理念是**将终端从"文本流"转变为"结构化块"**。

| 概念 | 说明 |
|------|------|
| **Block** | 每个命令 + 输出 = 一个独立的块，可折叠/复制/分享 |
| **AI 命令生成** | 自然语言描述（"部署到生产环境"）→ 生成正确命令 |
| **命令面板（Command Palette）** | ⌘+K 搜索命令、工作流、环境配置 |
| **现代编辑器** | 多行输入、语法高亮、智能补全、Vim 模式 |
| **块分享** | 块可以生成链接，分享给团队 |

### 2.2 与 SoloSoul 的适配分析

Warp 是**终端工具**，SoloSoul 是**身份数据管理**。领域完全不同，但有几条**交互设计理念**可以借鉴。

#### ✅ 借鉴 1：全局命令面板（Command Palette）— 优先级 P3

Warp 的 ⌘+K 面板让用户不离开键盘就能做任何事。SoloSoul 可以增加全局命令面板：

```
⌘+K → 输入 "护照" →
    ├── 添加护照          → 直接进入护照创建流程
    ├── 搜索护照          → 跳转到搜索结果
    ├── 导出护照          → 打开导出对话框（预筛选护照）
    └── 即将过期的护照    → 打开动态集合视图

⌘+K → 输入 "锁定" →
    └── 锁定 Vault        → 立即锁定

⌘+K → 输入 "设置" →
    ├── 主题设置          → 打开偏好设置页面
    ├── 敏感度设置        → 打开敏感度管理页面
    └── 插件管理          → 打开插件市场
```

**价值**：高级用户无需多次点击菜单，一个快捷键完成所有操作。

**实现注意**：命令面板需要索引用户数据（对象名称、类型名称），但索引本身不应暴露敏感信息。建议：
- `public` / `internal` 级别的对象名称可以加入索引
- `sensitive` / `critical` 级别的对象名称**不加入索引**（或显示为"敏感对象"占位符）

#### ✅ 借鉴 2：AI 辅助操作 — 优先级 P3

Warp 用 AI 将自然语言转为命令。SoloSoul 可以用 AI 辅助：

| 场景 | AI 辅助行为 |
|------|------------|
| 用户说"添加我的新护照" | AI 识别意图 → 打开护照创建模板 |
| 用户上传护照照片 | AI 调用 OCR 插件 → 自动提取字段值 → 填充表单 |
| 用户说"帮我检查哪些证件快过期了" | AI 查询所有有过期日期的对象 → 筛选 90 天内过期的 → 生成报告 |
| 用户在对象编辑器中输入"/护照" | Slash 命令 → 插入护照模板 |

**重要约束**：AI 辅助**不触碰敏感数据**。OCR 提取后的数据需用户确认后才保存，AI 不直接写入 Vault。

#### ✅ 借鉴 3：字段级独立操作 — 优先级 P3

Warp 的块可以独立操作（复制一个命令的输出，不复制整个终端历史）。SoloSoul 可以让**每个字段（Field）成为可独立操作的单元**：

```typescript
// 字段级操作菜单（右键点击字段时）
interface FieldContextMenu {
  copyValue: () => void;           // 只复制字段值（如只复制护照号码）
  copyWithLabel: () => void;       // 复制"护照号码: E12345678"
  shareField: () => void;          // 生成临时链接，对方只能看到这个字段
  revealTemporarily: () => void;   // 临时揭示（遵循现有 1 分钟规则）
  jumpToRelated: () => void;       // 跳转到关联对象（RelationProperty）
}
```

**价值**：超越"对象级"的粒度。用户可能只想分享"护照号码"给旅行社，不需要分享整个护照对象。

**安全约束**：字段级分享时，应遵循该字段的敏感度级别——`critical` 字段不允许分享，`sensitive` 字段分享时需要密码验证。

### 2.3 不适合借鉴的点

| Warp 特性 | 不适合的理由 |
|----------|-------------|
| 流式输出块 | Warp 的块是线性流（命令1 → 输出1 → 命令2 → 输出2）。SoloSoul 的数据是**树形/图状**，不是线性流 |
| AI 命令执行 | Warp 的 AI 可以直接执行命令。SoloSoul 中 AI **不能**直接修改用户数据（安全红线） |
| 团队协作 | Warp 的块分享是团队协作场景。SoloSoul 是单人应用 |

## 三、Notion — 一切皆块

### 3.1 Notion 的核心设计

Notion 的"块模型"是其一切灵活性的来源：

| 概念 | 说明 | 数据结构 |
|------|------|---------|
| **Block** | 段落、标题、图片、数据库、页面都是块 | `{ id, type, parent_id, content, properties }` |
| **嵌套块** | 块可以无限嵌套 | 树形结构，parent_id 指向父块 |
| **Slash 命令** | `/heading` `/todo` `/database` 快速插入块 | 命令 → 块类型映射 |
| **数据库即块** | 数据库行也是块，有自定义属性 | 行 = 块，列 = property |
| **多视图** | 同一块数据可以有表格、看板、日历、画廊视图 | 同一数据源，不同渲染方式 |
| **实时协作** | OT/CRDT 多人同时编辑 | 操作转换 + 冲突解决 |

### 3.2 与 SoloSoul 的模型对比

```
Notion 块模型              SoloSoul 当前模型
─────────────────────────────────────────────────
Block（段落级）             PropertyDefinition（字段级）✅
Page（块容器）              UnifiedObject（对象级）✅
Database（行集合）          Collection（分区）✅
多视图（表格/看板/日历）      ❌ 暂无
Slash 命令                  ❌ 暂无
实时协作                    ❌ 不适用（单人本地）
嵌套页面                     ✅ 已有（页面→分区→项目）
```

### 3.3 可借鉴的具体点

#### ✅ 借鉴 1：Slash 命令（/快捷插入）— 优先级 P2

Notion 的 `/` 命令是极高效率的交互模式。SoloSoul 可以在**对象编辑器**中引入：

```
用户在对象编辑器中输入 "/" →
    ├── /passport        → 插入"护照"类型模板
    ├── /bankcard        → 插入"银行卡"类型模板
    ├── /relation        → 插入关联字段（选择目标对象）
    ├── /attachment      → 插入附件上传框
    ├── /date            → 插入日期选择器
    ├── /select          → 插入下拉选择器
    ├── /sensitive       → 将当前字段标记为 sensitive（需密码确认）
    └── /critical        → 将当前字段标记为 critical（需密码+确认）
```

**价值**：用户无需在工具栏中寻找按钮，键盘输入即可插入任何内容。

**实现注意**：Slash 命令需要适配 SoloSoul 的**强 Schema**——不是所有块类型都能在任何位置插入。例如：
- ✅ 在"中国护照"对象中输入 `/date` → 插入日期字段（护照有 issue_date）
- ❌ 在"中国护照"对象中输入 `/todo` → **不允许**（护照对象不应有 todo 列表）

#### ✅ 借鉴 2：多视图（表格/卡片/时间线）— 优先级 P2

Notion 的同一块数据可以有多种视图。SoloSoul 的 Collection（分区）目前只有一种**列表视图**，可以增加：

| 视图 | 适用场景 | 渲染方式 |
|------|---------|---------|
| **列表视图** | 通用浏览 | 当前已有 |
| **表格视图** | 对比多个对象的同字段 | 一行一个对象，一列一个字段 |
| **卡片视图** | 护照、银行卡的可视化展示 | 每个对象一张卡片，含图标+关键字段 |
| **时间线视图** | 按有效期排序 | 横轴为时间，对象按过期日期排列 |
| **画廊视图** | 附件预览 | 每个对象显示其附件缩略图 |

**示例：护照集合的多视图**

```
表格视图：
┌──────────┬──────────┬────────────┬────────────┐
│ 名称     │ 国籍     │ 号码       │ 有效期至   │
├──────────┼──────────┼────────────┼────────────┤
│ 中国护照 │ 中国     │ E12345678  │ 2030-05-20 │
│ 香港护照 │ 中国香港 │ K98765432  │ 2028-11-15 │
└──────────┴──────────┴────────────┴────────────┘

卡片视图：
┌──────────────┐  ┌──────────────┐
│ 🛂 中国护照   │  │ 🛂 香港护照   │
│ E12345678    │  │ K98765432    │
│ 2030-05-20   │  │ 2028-11-15   │
│ [查看详情]   │  │ [查看详情]   │
└──────────────┘  └──────────────┘

时间线视图：
2026 ──── 2027 ──── 2028 ──── 2029 ──── 2030
              │              │              │
           香港护照        ...          中国护照
          2028-11-15                   2030-05-20
```

**安全注意**：多视图中敏感字段（sensitive/critical）仍然需要遵循现有的遮盖规则。表格视图中 sensitive 字段显示为"••••••"，点击后触发密码验证。

#### ✅ 借鉴 3：字段类型转换 — 优先级 P3

Notion 中块可以一键变换类型（段落 → 标题 → 待办）。SoloSoul 中字段也可以支持类型转换，只要数据格式兼容：

| 源类型 | 目标类型 | 兼容性 | 行为 |
|--------|---------|--------|------|
| Text | Select | ✅ | 文本值变为 Select 的选项之一 |
| Select | Text | ✅ | 选中值变为纯文本 |
| Date | Text | ✅ | ISO 日期格式转为文本 |
| Text | Date | ⚠️ | 尝试解析文本为日期，失败则保留原值 |
| Number | Text | ✅ | 数字转为文本 |
| Text | Number | ⚠️ | 尝试解析文本为数字，失败则保留原值 |
| Relation | Text | ❌ | 不允许（关系是对象引用，不能降级为文本） |

**价值**：用户导入数据或迁移时，可以灵活调整字段类型。

**安全约束**：类型转换本身属于数据修改，应写入审计日志。涉及 sensitive/critical 字段的类型转换需要密码验证。

### 3.4 不适合借鉴的点

| Notion 特性 | 不适合的理由 |
|------------|-------------|
| 无限嵌套块 | Notion 允许在段落里嵌套数据库，数据库里嵌套页面。这种**无限自由度**对 SoloSoul 是灾难——用户需要一个"护照"对象，里面应该只有标准字段，不应允许在护照号码下嵌套 todo 列表。SoloSoul 是**强 Schema 约束**，Notion 是**无 Schema 自由** |
| 实时协作 | Notion 的多人实时编辑需要 OT/CRDT 冲突解决。SoloSoul 是**单人本地应用**，不需要这个复杂度 |
| 富文本块 | Notion 的核心是文档编辑（段落、加粗、列表）。SoloSoul 不是文档工具，不需要富文本块 |
| 自由页面布局 | Notion 允许用户在页面中任意排列块。SoloSoul 的对象编辑器是**表单式布局**（字段从上到下排列），不应变成自由画布 |

## 五、关键结论

### 5.1 SoloSoul 与 Anytype 是同一条路

**最值得深入借鉴的是 Anytype 的对象模型**——不是因为它最先进，而是因为 **SoloSoul 已经在做这件事，只是还没意识到自己和 Anytype 在同一条路上**。

Anytype 的"Object-Type-Relation-Set" 与 SoloSoul 的"UnifiedObject-ObjectTypeDefinition-RelationProperty-Collection" 本质上是同一套模型。区别在于定位：

| | Anytype | SoloSoul |
|--|---------|----------|
| **定位** | 通用知识管理（笔记、任务、项目） | 个人身份数据（护照、银行卡、履历） |
| **Schema** | 弱约束（用户任意创建类型和属性） | 强约束（标准字段有验证规则） |
| **数据用途** | 思考、记录、协作 | 填写表单、生成文件、身份验证 |
| **核心交互** | 自由编辑、图浏览 | 结构化表单、敏感度分级 |
| **可视化** | Graph View + 自由页面 | 结构化卡片 + 多视图 |

### 5.2 不应为了借鉴而借鉴

SoloSoul 的核心差异是**"结构化身份数据"**——Anytype 和 Notion 都做不到：
- **自动验证护照号码格式**
- **根据出生日期计算年龄**
- **根据有效期自动提醒更新**
- **敏感度分级 + 字段级加密**

这些是 SoloSoul 的护城河，不应为了模仿其他产品的灵活性而削弱。

### 5.3 借鉴的原则

1. **交互效率可以借鉴**（Slash 命令、命令面板、多视图）—— 不改变数据模型，只改变交互方式
2. **数据可视化可以借鉴**（Graph View、多视图）—— 不改变数据结构，只改变呈现方式
3. **数据模型不应借鉴**（无限嵌套块、弱 Schema、富文本编辑）—— 会破坏 SoloSoul 的核心定位

Month 2: 多视图框架
