# 技术选型重新评估：Tauri + Rust 是否为最佳方案？

> **文档状态**：活跃  
> **最后更新**：2026-06-04  
> **评估范围**：SoloSoul 跨平台客户端技术栈  
> **相关文档**：《ADR-003-Rust_Crate拆分与架构.md》、SoloSoul 宣言

---

## 1. 为什么要重新评估？

SoloSoul 目前已确定的重构方向是 **Tauri + Rust**，替代现有的 **Flutter + Rust FFI** 架构。但在投入大量工程资源之前，我们需要回答一个问题：

> **Tauri + Rust 是"足够好"的方案，还是"最佳"方案？有没有其他更适合（不一定是更好）的候选方案？**

这份文档从 SoloSoul 的产品定位、技术约束、团队能力和长期维护角度出发，对 6 个候选方案进行了系统性评估。

---

## 2. SoloSoul 的核心约束条件

任何技术选型都必须满足以下硬约束，按优先级排序：

### 2.1 硬约束（不可妥协）

| # | 约束 | 原因 |
|---|---|---|
| 1 | **跨五平台** | macOS / iOS / Android / Windows / Linux |
| 2 | **Rust 原生密码学** | Argon2id + AES-256-GCM 是核心竞争力，必须用 Rust 实现 |
| 3 | **本地优先** | 100% 核心功能在无网络环境下可用 |
| 4 | **零知识加密** | 端到端加密、内存安全、Zeroize 缺一不可 |
| 5 | **系统级集成** | Keychain、生物识别、文件系统、通知、原生菜单 |
| 6 | **长期可维护性** | 个人数据管理软件的生命周期是 10 年+ |
| 7 | **开源可控** | 必须基于开源协议，避免 vendor lock-in |

### 2.2 软约束（可权衡）

| # | 约束 | 优先级 |
|---|---|---|
| 1 | 开发效率 | 高 |
| 2 | 包体积 | 高 |
| 3 | 内存占用 | 高 |
| 4 | 原生体验 | 中高 |
| 5 | 人才招聘 | 中 |
| 6 | 生态成熟度 | 中 |

---

## 3. 候选方案评估

### 方案 1：Tauri + Rust（当前方向）

**架构**：Web 前端（React/Vue/Svelte）+ Rust 后端 + OS WebView 渲染

#### 优势

| 维度 | 评估 |
|---|---|
| **桌面端性能** | ⭐⭐⭐⭐⭐ 极佳。3-15MB 包体积，20-80MB 内存，200-500ms 冷启动 |
| **安全性** | ⭐⭐⭐⭐⭐ Rust 内存安全 + OS WebView 沙箱 + 最小攻击面 |
| **Rust 兼容性** | ⭐⭐⭐⭐⭐ 原生集成，无需 FFI，直接复用 `solosoul-crypto` crate |
| **跨平台覆盖** | ⭐⭐⭐⭐⭐ 一套代码覆盖 macOS / iOS / Android / Windows / Linux |
| **资源效率** | ⭐⭐⭐⭐⭐ 无 Chromium 捆绑，更新包仅 1-5MB（delta） |
| **开源许可** | ⭐⭐⭐⭐⭐ MIT / Apache 2.0 |

#### 劣势

| 维度 | 评估 |
|---|---|
| **移动端成熟度** | ⭐⭐⭐ 可用但不如 Flutter/React Native。手势、原生组件、调试工具有限 |
| **前端生态** | ⭐⭐⭐ Web 技术丰富，但移动端特定组件（如 iOS 原生导航）需要自建 |
| **渲染一致性** | ⭐⭐⭐ WebView2 / WKWebView / WebKitGTK 实现有差异，需要平台适配 |
| **人才招聘** | ⭐⭐ Rust 开发者薪资高 15-25%，人才池小 |
| **测试工具** | ⭐⭐ `tauri-driver` 仍在 pre-alpha，全平台 E2E 测试需借助 Appium |
| **Liquid Glass UI** | ⭐⭐ 需要在前端用 CSS/WebGL 重写，无法直接用 iOS 原生控件 |

#### 适合场景
- 桌面是主战场，移动端是"够用即可"
- 安全敏感型应用
- 团队能接受 Rust 学习曲线
- 对包体积和启动速度敏感

#### 总体评分：**8.5 / 10**

---

### 方案 2：Flutter + Rust FFI（保持现状）

**架构**：Flutter/Dart UI + Rust FFI 桥接

#### 优势

| 维度 | 评估 |
|---|---|
| **移动端成熟度** | ⭐⭐⭐⭐⭐ 最成熟的跨移动框架 |
| **UI 组件** | ⭐⭐⭐⭐⭐ `liquid_glass_widgets` 已集成，设计系统成熟 |
| **开发效率** | ⭐⭐⭐⭐⭐ Hot Reload、丰富插件 |
| **生态** | ⭐⭐⭐⭐⭐ pub.dev 生态庞大 |
| **已有代码积累** | ⭐⭐⭐⭐⭐ `lib/` 下已有完整实现 |

#### 劣势

| 维度 | 评估 |
|---|---|
| **桌面端体验** | ⭐⭐ macOS 菜单、窗口管理、原生行为一直有 gap |
| **FFI 开销** | ⭐⭐⭐ 序列化/反序列化开销，调试困难 |
| **包体积** | ⭐⭐ 动辄 50MB+ |
| **长期维护** | ⭐⭐ FFI 层是持续的技术债务 |
| **重构目标** | 与当前重构方向直接冲突 |

#### 适合场景
- 移动是主战场
- 已有大量 Flutter 代码不愿重写
- 桌面体验要求不高

#### 总体评分：**6.5 / 10**（对 SoloSoul 当前阶段不适用）

---

### 方案 3：React Native + Rust

**架构**：React Native UI + Rust TurboModules + JS Bridge

#### 优势

| 维度 | 评估 |
|---|---|
| **移动端生态** | ⭐⭐⭐⭐⭐ 最大的人才池和第三方库 |
| **Web 团队转型** | ⭐⭐⭐⭐⭐ 熟悉 React 的团队可以直接上手 |
| **热更新** | ⭐⭐⭐⭐⭐ OTA 更新成熟 |

#### 劣势

| 维度 | 评估 |
|---|---|
| **桌面端** | ⭐ 基本不支持。Expo 不支持桌面，社区方案不成熟 |
| **性能** | ⭐⭐⭐ JS Bridge 调用 Rust 有开销，加密密集型场景不理想 |
| **安全边界** | ⭐⭐⭐ JS 运行时增加了攻击面 |
| **依赖复杂度** | ⭐⭐ npm + CocoaPods + Gradle，依赖地狱 |
| **Rust 集成** | ⭐⭐⭐ TurboModules 需要为每个平台写绑定 |

#### 关键排除理由
**桌面端不支持**直接违反 SoloSoul 的跨平台硬约束。如果 SoloSoul 只做移动端，React Native 是强有力的候选；但它不是。

#### 总体评分：**4.5 / 10**

---

### 方案 4：Kotlin Multiplatform + Compose Multiplatform + Rust

**架构**：KMP 共享业务逻辑 + Compose Multiplatform UI + Rust 加密（通过 FFI）

#### 优势

| 维度 | 评估 |
|---|---|
| **逻辑共享** | ⭐⭐⭐⭐⭐ 90-95% 业务逻辑可共享 |
| **原生 UI 选项** | ⭐⭐⭐⭐ 可选择原生 UI（SwiftUI/Jetpack Compose）或共享 UI |
| **Android 体验** | ⭐⭐⭐⭐⭐ 最佳 Android 体验 |
| **Google/JetBrains 背书** | ⭐⭐⭐⭐ 长期支持有保障 |
| **2025 进展** | ⭐⭐⭐⭐ Compose Multiplatform iOS 稳定性大幅提升 |

#### 劣势

| 维度 | 评估 |
|---|---|
| **iOS 成熟度** | ⭐⭐⭐ 不如 Flutter，Compose Multiplatform iOS 2025 才趋于稳定 |
| **桌面端** | ⭐⭐ 桌面支持还在发展中 |
| **Rust 集成** | ⭐⭐⭐ 需要 Kotlin/Native ↔ Rust FFI，复杂度高 |
| **生态** | ⭐⭐ 第三方库远少于 Flutter/React Native |
| **人才** | ⭐⭐⭐ 需要 Kotlin + Swift + Rust 混合团队 |
| **工具链** | ⭐⭐⭐ IDE 支持不如 Flutter/Android Studio 成熟 |

#### 关键评估
这是一个**非常有潜力的长期选项**。如果现在是 2027-2028 年，KMP + Compose Multiplatform 可能是首选。但在 2026 年：
- 桌面端支持仍不足
- iOS 端刚趋于稳定，风险较高
- Rust 集成路径不清晰

#### 总体评分：**6.5 / 10**（未来值得重新评估）

---

### 方案 5：纯原生开发

**架构**：macOS/iOS 用 SwiftUI/AppKit，Android 用 Jetpack Compose，Windows 用 WinUI，Linux 用 GTK

#### 优势

| 维度 | 评估 |
|---|---|
| **原生体验** | ⭐⭐⭐⭐⭐ 无可挑剔 |
| **性能** | ⭐⭐⭐⭐⭐ 最佳 |
| **系统集成** | ⭐⭐⭐⭐⭐ 最深 |

#### 劣势

| 维度 | 评估 |
|---|---|
| **代码重复** | ⭐ 3-4 套代码，维护成本极高 |
| **团队需求** | ⭐ 需要 Swift/Kotlin/C#/C 多语言专家 |
| **一致性** | ⭐ 各平台 UI/行为难以统一 |
| **开发速度** | ⭐ 远低于跨平台方案 |
| **与"统一 Schema"理念的冲突** | 四套代码维护同一 Schema，极易出现语义漂移 |

#### 关键排除理由
SoloSoul 是小团队产品，纯原生开发的维护成本不可接受。它与"Centralized Schema definition"的理念也相冲突。

#### 总体评分：**3 / 10**

---

### 方案 6：Electron + Rust

**架构**：Web 前端 + Node.js + Rust Native Modules + 自带 Chromium

#### 优势

| 维度 | 评估 |
|---|---|
| **桌面生态** | ⭐⭐⭐⭐⭐ 最成熟 |
| **开发效率** | ⭐⭐⭐⭐⭐ VS Code/Slack/Discord 已验证 |
| **Web 人才** | ⭐⭐⭐⭐⭐ 最多 |
| **调试工具** | ⭐⭐⭐⭐⭐ Chrome DevTools |

#### 劣势

| 维度 | 评估 |
|---|---|
| **包体积** | ⭐ 120-250MB |
| **内存占用** | ⭐ 100-300MB 空闲 |
| **冷启动** | ⭐ 1-2 秒 |
| **移动端** | ⭐ 完全不支持 |
| **安全攻击面** | ⭐⭐ Chromium + Node.js 攻击面巨大 |
| **资源浪费** | ⭐ 每个 Electron 应用都自带 Chromium |

#### 关键排除理由
包体积和移动端不支持直接排除。SoloSoul 崇尚"最小依赖"和"本地优先"，Electron 的臃肿与之完全不符。

#### 总体评分：**3.5 / 10**

## 5. 为什么 Tauri + Rust 仍然是最佳方案？

### 5.1 SoloSoul 的战场是桌面优先

从当前状态可以看出：
- macOS Release 已发布（DMG 安装包）
- 构建脚本 `build_dmg.sh` 已成熟
- 主要开发在 macOS 上进行

Tauri 在桌面端的评分是 **⭐⭐⭐⭐⭐**，而 Flutter 桌面只有 **⭐⭐⭐**。对于桌面优先的产品，Tauri 是压倒性优势。

### 5.2 Rust 后端不可替代

SoloSoul 的核心竞争力是**密码学实现**（Argon2id + AES-256-GCM + Zeroize）。无论选哪个前端框架：
- Rust 库 `solosoul-crypto` 都应该保留
- FFI/桥接层都是技术债务
- Tauri 是唯一让 Rust **直接作为应用核心**的方案

### 5.3 "desktop-first with mobile reach" 正好匹配 SoloSoul 场景

Tauri 官方对自身移动端的定位是：

> *"Tauri mobile apps are WebView-based and may not feel as native as React Native apps for consumer-facing mobile experiences. However, for teams building desktop-first applications that need mobile reach... Tauri's cross-platform story is a compelling economic advantage."*

SoloSoul 正好属于后者：
- 不是消费者社交 App，不需要极致的原生动画和手势
- 移动端主要场景是"查看数据"和"接收通知"
- 复杂的数据录入、导出、同步主要在桌面端完成

### 5.4 资源效率符合宣言

SoloSoul 宣言中强调"持久 > 流行"、"依赖最小化"。Tauri：
- 不捆绑 Chromium
- 最小化运行时依赖
- 更新包 1-5MB
- 完美契合宣言中的架构信条

## 6. 但 Tauri 不是完美的：风险与缓解

### 风险 1：移动端体验不够原生

**影响**：中  
**缓解**：
- 移动端采用"数据查看 + 轻量编辑"的定位
- 复杂操作（批量导入、导出、同步设置）引导用户到桌面端
- 必要时为移动端写少量原生插件（Swift/Kotlin）补充 Tauri 能力不足的部分

### 风险 2：Liquid Glass UI 需要重写

**影响**：中高  
**缓解**：
- 将 `liquid_glass_widgets` 的设计语言翻译为 Web 实现（CSS backdrop-filter + WebGL 毛玻璃效果）
- 优先保证 macOS/iOS 风格的视觉一致性
- 桌面端可以使用更原生的菜单/工具栏，不完全复制 Flutter 实现

### 风险 3：Rust 人才招聘困难

**影响**：中  
**缓解**：
- Tauri 前端使用 TypeScript/React，这部分人才丰富
- Rust 后端主要维护 `solosoul-crypto` 和同步协议，不需要庞大的 Rust 团队
- 核心成员掌握 Rust，普通开发者可以只写前端

### 风险 4：移动端测试工具不成熟

**影响**：中  
**缓解**：
- 桌面端用 `tauri-driver`（稳定后）
- 移动端用 Appium 做 E2E 测试
- 核心加密逻辑用 Rust 单元测试充分覆盖，减少对 UI 测试的依赖

### 风险 5：WebView 跨平台渲染差异

**影响**：中  
**缓解**：
- 建立跨平台视觉回归测试
- 使用 CSS 特性检测和渐进增强
- 避免依赖最新的 Web 标准特性

## 7. 备选策略：如果移动端变得更重要

如果未来 SoloSoul 的移动用户占比显著提升，可以考虑**分层策略**：

```
┌─────────────────────────────────────────────────────────────┐
│  桌面端：Tauri + Rust（完整功能）                            │
│  ├── 复杂数据录入                                            │
│  ├── 批量导入导出                                            │
│  ├── 同步设置                                                │
│  ├── 附件管理                                                │
│  └── 插件管理                                                │
└─────────────────────────────────────────────────────────────┘
                              ↓ 共享 Rust 核心 + 同步协议
┌─────────────────────────────────────────────────────────────┐
│  移动端：Tauri + Rust（轻量功能）或 Flutter + Rust FFI       │
│  ├── 查看数据                                                │
│  ├── 简单编辑                                                │
│  ├── 接收通知                                                │
│  └── 二维码/配对码同步                                       │
└─────────────────────────────────────────────────────────────┘
```

**建议**：在 Tauri 重构完成并稳定运行至少 1 年后，再评估是否需要为移动端单独维护一个 Flutter 客户端。

---

## 8. 最终决策

**维持 Tauri + Rust 作为 SoloSoul 的主技术栈。**

这不是因为 Tauri 在所有维度都最好，而是因为：
1. 它在 SoloSoul **最重要的维度**（桌面性能、安全、Rust 原生集成、跨平台覆盖）上得分最高
2. 它在 SoloSoul **可接受的弱点**（移动端原生体验）上得分"够用"
3. 没有任何其他候选方案能在满足全部硬约束的同时，在核心优势上超过 Tauri

### 一句话总结

> **对于 SoloSoul，Tauri + Rust 不是"唯一正确"的答案，但它是"在当前约束下最正确"的答案。**

---

## 9. 决策后的行动

基于这个评估，Tauri 重构的以下假设继续成立：

- ✅ Rust 核心 `solosoul-crypto` 继续作为独立 crate 开发
- ✅ Tauri 前端使用 React + TypeScript
- ✅ 移动端功能先做"够用"版本，不追求完美原生
- ✅ 密码学逻辑全部在 Rust 侧，前端绝不接触原始密钥
- ✅ 持续监控 Tauri 移动端生态和 Compose Multiplatform 发展，2 年后重新评估
