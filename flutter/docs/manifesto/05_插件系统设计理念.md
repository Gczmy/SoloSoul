# 05 插件系统设计理念

> *"插件不是应用的延伸，而是用户数据的访客。"*
> 
> *访客可以参观，但主人可以随时关门。*

---

## 1. 为什么 SoloSoul 需要插件？

SoloSoul 管理的是人生中最私密的数据——护照、银行卡、身份凭证。这些数据的需求是无限的：有人需要生成签证检查清单，有人需要计算保险到期提醒，有人需要将地址格式化为不同国家的标准格式。

如果我们在核心应用中实现所有这些功能，应用会变成一个臃肿的怪物。更重要的是，**每增加一个功能，就增加了我们触碰用户数据的面积**——这与"最小权限"原则相悖。

插件系统提供了一条第三条路：

```
❌ 方案 A：我们在核心应用中实现所有功能
    → 功能臃肿，代码膨胀，安全风险累积

❌ 方案 B：将数据上传到云端，由外部服务处理
    → 违背隐私优先原则，零知识架构被破坏

✅ 方案 C：插件在本地沙盒中运行，只访问用户明确授权的数据
    → 功能可扩展，数据不离开设备，权限精确可控
```

**插件不是"应用的延伸"，而是"用户授权的外部工具"。**

---

## 2. 核心理念：三条铁律

### 铁律 1：插件是访客，不是居民

**定义**：插件在用户设备上没有永久居住权。它们被安装，被授权，被使用，被撤销——每一个生命周期都由用户完全控制。

**实践**：

- 插件无法访问 Vault 主密钥，无法自行解密任何数据
- 插件的所有数据访问都必须通过 Host Functions 代理
- 插件执行结束后，其 Wasm 内存被销毁，不留下任何持久状态
- 插件可以在任何时候被用户卸载，卸载后无残留（审计日志除外）

**隐喻**：

```
传统应用扩展（如浏览器插件）
→ 像租客，签了一年合同，有权改造房间

SoloSoul 插件
→ 像访客，主人说"请进"才能进门，主人说"请回"就必须离开
```

**设计检验**：如果插件在不被用户察觉的情况下可以读取或修改数据，这个插件系统就是失败的。

---

### 铁律 2：数据访问 = 用户授权 + 知情同意

**定义**：插件对用户数据的每一次访问都必须经过两个条件的同时满足：

1. **声明** — 插件必须在 manifest 中预先声明要访问哪些字段
2. **授权** — 用户在插件执行前通过 Consent 对话框明确同意这些访问

缺少任何一个条件，访问都被拒绝。

**Consent 不是一次性授权**：

```
安装时声明 → "我需要访问护照号码和有效期"
执行前授权 → "允许本次运行访问这些字段吗？"
敏感字段确认 → "护照号码是受限数据，您确定要授权吗？"
TTL 到期后 → 需要重新授权
```

**设计检验**：如果用户无法回答"这个插件在上次运行时读了哪些数据"这个问题，Consent 机制就是失败的。

---

### 铁律 3：默认拒绝，逐项放行

**定义**：插件的默认状态是"什么都做不了"。每增加一项能力，都必须有明确的理由和用户的明确授权。

**能力清单**（插件默认不具备任何能力）：

| 能力 | 默认状态 | 如何获得 | 用户控制 |
|------|---------|---------|---------|
| 读取用户数据字段 | ❌ 拒绝 | manifest 声明 + Consent 授权 | 逐项字段级别 |
| 访问网络 | ❌ 拒绝 | manifest 声明域名白名单 | 域名级别 |
| 弹出对话框 | ❌ 拒绝 | manifest 声明 + 官方签名 | 仅白名单插件 |
| 写入用户数据 | ❌ 拒绝 | manifest 声明（暂未开放） | — |
| 持久化存储 | ❌ 拒绝 | 无（插件无持久存储权） | — |
| 读取文件系统 | ❌ 拒绝 | 无 | — |
| 执行系统命令 | ❌ 拒绝 | 无 | — |

**设计检验**：如果一个插件可以"悄悄"做任何用户未明确授权的事情，沙盒就是失败的。

---

## 3. 安全模型：零信任沙盒

### 3.1 对插件的假设

我们不信任任何插件，即使它是官方发布的。安全模型的基础假设：

```
1. 插件可能包含恶意代码
2. 插件可能试图读取超出声明范围的数据
3. 插件可能试图泄露数据到未授权的网络地址
4. 插件可能试图在设备上留下持久痕迹
5. 插件可能试图耗尽系统资源
```

这些假设不是偏执——它们是**正确的设计起点**。

### 3.2 五层防御

```
┌─────────────────────────────────────────────────────────────────┐
│  Layer 5: 用户控制层                                             │
│  ── 用户可以随时撤销 Session、卸载插件、查看审计日志             │
├─────────────────────────────────────────────────────────────────┤
│  Layer 4: 审计层                                                 │
│  ── 所有字段访问、网络请求、错误都写入审计日志                   │
│  ── 日志位置: ~/.solosoul/{account_id}/audit/plugin_audit.log    │
│  ── 每个账户独立维护，切换账户时审计日志上下文同步切换           │
├─────────────────────────────────────────────────────────────────┤
│  Layer 3: 速率与资源层                                           │
│  ── Fuel 限制（10M 指令 / Release）防止死循环                    │
│  ── 字段访问速率限制（10 次/分钟/字段）防止暴力读取              │
│  ── TTL 超时后自动销毁 Wasm 内存                                │
├─────────────────────────────────────────────────────────────────┤
│  Layer 2: 权限层                                                 │
│  ── manifest 字段声明校验（通配符匹配）                          │
│  ── 敏感度分级授权（Public/Internal 直接过，Sensitive+ 需确认）  │
│  ── 网络域名白名单（默认阻断所有出站）                           │
├─────────────────────────────────────────────────────────────────┤
│  Layer 1: 隔离层                                                 │
│  ── Wasmtime Store 隔离（每个插件独立内存空间）                  │
│  ── 无文件系统访问（WASI 仅继承标准输入输出）                    │
│  ── 无持久存储（插件无法写入任何文件）                           │
│  ── Trap 捕获（插件 panic 不会崩溃主程序）                       │
└─────────────────────────────────────────────────────────────────┘
```

**关键设计**：任何一层被突破，下一层仍然有效。攻击者需要同时突破五层才能接触到用户数据——而这在设计上是不可能的。

## 4. 用户主权：用户对插件的绝对控制

### 4.1 知情权

用户有权知道：

- 哪些插件已安装？（插件仪表盘）
- 插件在运行时读了哪些字段？（审计日志）
- 插件是否访问了网络？访问了哪些域名？（审计日志）
- 当前有哪些插件在运行？（活跃 Session 列表）
- 插件的结果是什么？如何被处理的？（结果面板）

**我们不提供"信任这个插件，以后不再询问"的选项。** 每次执行都需要重新授权——这是设计选择，不是技术限制。

### 4.2 撤销权

用户可以在任何时刻：

- **撤销 Session**：正在运行的插件立即停止，内存被清零
- **卸载插件**：插件文件被删除，无法再次执行
- **撤销字段授权**：即使已授权，用户也可以随时收回对特定字段的访问权
- **删除审计日志**：用户有权删除当前账户的审计记录（仅影响当前账户，不影响其他账户）

**撤销不是"取消订阅"，是"立刻生效的物理终止"。**

### 4.3 选择权

- 用户可以选择不安装任何插件，核心功能 100% 可用
- 用户可以选择安装插件但永不运行
- 用户可以选择运行插件但拒绝某些字段授权
- 用户可以选择只使用官方插件，或完全禁用插件系统

**插件系统是可选的增强，不是核心依赖。**

## 5. 插件生态的定位

### 5.1 插件是什么

| 类型 | 示例 | 说明 |
|------|------|------|
| **数据检查类** | 护照有效期检查、签证材料清单生成 | 读取数据 → 分析 → 返回建议 |
| **格式转换类** | 地址格式化为各国标准、日期格式转换 | 读取数据 → 转换格式 → 返回结果 |
| **辅助填写类** | 根据护照信息自动填写签证表格 | 读取数据 → 填充模板 → 返回文档 |
| **提醒监控类** | 证件到期提醒、保险续期提醒 | 读取日期 → 计算 → 返回日历事件 |

### 5.2 插件不是什么（禁区）

```
❌ 插件不能替代核心功能
   → SoloSoul 必须在没有插件的情况下完全可用

❌ 插件不能上传用户数据到外部服务
   → 网络访问仅限白名单域名，且必须用户知情

❌ 插件不能修改用户数据
   → 当前仅开放 Read 模式，Write 模式不在计划中

❌ 插件不能在后台持续运行
   → 没有后台驻留机制，每次执行都需要用户主动触发

❌ 插件不能读取未声明的字段
   → 任何未在 manifest 中声明的字段访问都会被拒绝

❌ 插件不能绕过 Consent 机制
   → 即使是官方插件，也必须走完整的授权流程
```

### 5.3 官方插件与第三方插件

我们不计划建立"插件商店"。SoloSoul 的插件以以下方式分发：

- **官方插件**：随应用发布，由 SoloSoul 团队维护，签名验证
- **社区插件**：通过 GitHub Releases 等方式分发，用户手动安装
- **用户自制插件**：高级用户可以编写自己的插件处理数据

**我们不审核第三方插件**。审核意味着我们要检查代码，这违背了我们不触碰用户数据的承诺。插件的安全由沙盒保证，不是由审核保证。

## 6. 与传统扩展机制的对比

| 维度 | 浏览器扩展 | VS Code 扩展 | SoloSoul 插件 |
|------|-----------|-------------|--------------|
| **隔离级别** | 进程隔离 | Node.js 进程 | Wasmtime Store 隔离 |
| **数据访问** | 可读取任意网页 | 可访问工作区所有文件 | 仅 manifest 声明的字段 |
| **网络访问** | 默认允许 | 默认允许 | 默认阻断，白名单例外 |
| **持久存储** | 有（localStorage等） | 有（文件系统） | 无（执行后内存清零） |
| **用户授权** | 安装时一次性 | 安装时一次性 | **每次执行都需重新授权** |
| **审计日志** | 无 | 无 | **所有访问写入审计日志** |
| **后台运行** | 可以 | 可以 | **不可以（TTL 到期即销毁）** |
| **卸载残留** | 常有配置残留 | 常有配置残留 | **无残留** |

**关键区别**：传统扩展机制信任扩展程序，通过权限声明限制其能力。SoloSoul 不信任插件，通过沙盒 + Consent + 审计三层机制确保即使恶意插件也无法损害用户。

## 7. 插件开发者的契约

如果你是插件开发者，以下是你对用户的承诺：

```
1. 我只访问 manifest 中声明的字段
2. 我不会试图绕过 Host Functions 直接访问用户数据
3. 我不会将用户数据发送到未声明的域名
4. 我的插件执行结束后不会留下任何持久状态
5. 我会尊重用户的拒绝和撤销决定
6. 我不会耗尽系统资源（Fuel、速率限制内运行）
```

违反以上任何一条的插件，无论功能多么有用，都是**恶意插件**。沙盒会阻止它们，但开发者不应试图挑战沙盒。

## 8. 设计检验框架

当设计或评估一个插件系统功能时，按以下顺序提问：

```
1. 这个功能会让插件在未经用户明确授权的情况下访问数据吗？
   └─ 是 → 拒绝，重新设计
   └─ 否 → 继续

2. 这个功能会让插件获得超出声明范围的能力吗？
   └─ 是 → 拒绝，重新设计
   └─ 否 → 继续

3. 这个功能会让插件的数据访问无法被审计吗？
   └─ 是 → 拒绝，重新设计
   └─ 否 → 继续

4. 这个功能会让插件在后台持续运行吗？
   └─ 是 → 拒绝，重新设计
   └─ 否 → 继续

5. 这个功能会让用户更难理解插件正在做什么吗？
   └─ 是 → 简化或增加透明度
   └─ 否 → 继续

6. 这个功能会让插件获得持久存储权吗？
   └─ 是 → 拒绝，插件不应有持久状态
   └─ 否 → 通过
```

**前三个问题的答案必须是"否"，否则功能不应该存在。**

## 9. 与 SoloSoul 核心理念的对照

| 核心理念 | 在插件系统中的体现 |
|---------|------------------|
| **本地优先** | 插件在用户设备上运行，数据不离开设备 |
| **隐私优先** | 插件无法自行解密数据，所有访问经 Host Function 代理 |
| **用户主权** | 用户可随时撤销 Session、卸载插件、查看审计日志 |
| **安全默认** | 插件默认什么都做不了，每项能力需明确授权 |
| **最少惊喜** | Consent 对话框明确展示插件要访问哪些字段 |
| **透明** | 审计日志记录每一次字段访问和网络请求 |

---

## 10. 总结

> **SoloSoul 的插件系统是一个"数据安全沙盒"。**
> 
> 它不是为了"扩展功能"而设计的——它是为了**让用户可以在不损失控制权的前提下扩展功能**而设计的。
> 
> 插件可以为用户提供便利，但便利的代价必须是**完全可控、完全透明、完全可撤销**的。
> 
> 如果某个插件功能需要以牺牲用户主权为代价才能实现，那么这个功能就不应该通过插件实现——它应该被重新设计，或者干脆不存在。
