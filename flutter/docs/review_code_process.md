任务概述
你将被指定一个代码库。你的目标是系统性地分析、优化并修复该代码库，过程需完全自动化（或半自动）并持久化记录。核心流程如下：

全库扫描与分析：探测死代码、可优化结构、性能瓶颈、潜在漏洞/安全风险。

生成初始报告：将发现写入 CODE_ANALYSIS_REPORT.md，并按优先级排序问题。

迭代修复：一次只解决一个高优先级问题 → 更新报告状态 → 提交到 Git → 继续下一问题。

最终复审：所有问题标记完成后，重新进行全面分析，生成终版报告（覆盖或并列保存）。

循环改进：若终版报告仍有新问题，则重复步骤 3-4（形成渐进式修复循环）。

详细执行步骤
阶段 0：环境准备与初始检查
确认当前目录为代码库根路径。

检查是否已存在 CODE_ANALYSIS_REPORT.md：

若不存在 → 进入阶段 1。

若存在 → 读取报告中未解决的问题（状态 [ ]），按优先级继续修复（跳至阶段 3）。

确保 Git 仓库干净（git status 无未提交改动），如果有未提交代码，则先执行git commit & git push，根据修改编写commit message，来确保本地仓库与远程仓库同步。

阶段 1：全库分析（产生初始报告）
分析维度（使用静态分析 + 启发式规则）：

死代码：未被调用的函数、未使用的变量/导入、不可达分支。

可优化代码：

重复代码片段（相似度 > 70%）

过长函数（>50 行非注释代码）

深层嵌套（>4 层）

可简化的条件表达式

性能问题：

O(n²) 或更高复杂度的循环（如嵌套循环遍历大集合）

频繁的 I/O 或数据库查询在循环内

无缓存的重复计算

内存泄露风险（如全局事件监听未移除）

潜在漏洞：

未过滤的用户输入（XSS/SQL 注入风险）

不安全的反序列化

弱加密或硬编码密钥

命令注入（如 eval、exec 处理用户输入）

越权风险（缺少权限检查）

输出报告格式（CODE_ANALYSIS_REPORT.md）：

markdown
# 代码分析修复报告

> 最后更新：YYYY-MM-DD HH:MM:SS  
> 当前分支：`main`  
> 修复轮次：1（初始分析）

## 问题清单（按优先级 P0 > P1 > P2）

| ID   | 优先级 | 类别       | 文件位置                         | 描述                                           | 状态      |
|------|--------|------------|----------------------------------|------------------------------------------------|-----------|
| P001 | P0     | 漏洞       | `src/auth/login.js:23`           | SQL 注入：直接拼接用户输入到查询                | `[ ]` 待修复 |
| P002 | P0     | 性能       | `src/parser/xml.js:112-130`      | 嵌套循环 O(n²)，待解析文件可能 >10MB           | `[ ]` 待修复 |
| P003 | P1     | 死代码     | `src/utils/old_helper.js`        | 整个文件无任何引用                              | `[ ]` 待修复 |
| ...   | ...    | ...        | ...                              | ...                                            | `[ ]`      |

## 修复进度

- 已完成：0 / N
- 当前处理：无

## 详细问题描述与修复指引

（对每个问题展开，包含代码片段、影响分析、建议修复方案）
阶段 2：确定修复顺序
按 P0（严重）→ P1（中等）→ P2（轻微） 排序。

同优先级内，按依赖顺序（改动可能影响其他问题的先做）。

阶段 3：迭代修复（一次一问题）
对当前优先级的第一个未解决问题（状态 [ ]）：

标记进行中：在报告的“当前处理”字段填入问题 ID，并更新“最后更新”时间。

实施修复：

修改代码以解决问题。

遵循代码库现有风格，最小化改动。

若修复涉及 API 变化或重大重构，在报告中添加“修复备注”。

本地验证（可选但推荐）：

运行项目的单元测试（若有）。

手动验证改动未引入明显错误。

更新报告：

将该问题状态改为 [x]。

在问题下方添加“修复说明”（如：改了哪几行、采用的方案）。

更新“已完成”计数。

清除“当前处理”字段。

提交到 Git：

bash
git add .
git commit -m "fix: resolve [ID] - [简要描述]"
git push origin <当前分支>
继续下一个问题：重复阶段 3，直到所有问题的状态均为 [x]。

阶段 4：最终复审与循环
当所有问题都被标记 [x] 后：

重新执行阶段 1 的分析（全库扫描）。

生成新报告，保存为 CODE_ANALYSIS_REPORT_FINAL.md（若希望保留历史）或覆盖原报告（需保留历史则重命名）。

若新报告中发现 任何严重等级（P0/P1）问题 → 这不是终版。将新问题追加到原报告（标记为新一轮），重置状态为 [ ]，回到阶段 3 继续修复。

若新报告仅剩 P2 或零问题 → 终版报告有效。

推送终版报告并打标签：

bash
git tag -a "code-audit-passed-$(date +%Y%m%d)" -m "Final code quality audit"
git push --tags
输出总结：在控制台打印“✅ 所有可识别问题已修复，代码库质量评估达标。”

约束与注意
不要自动执行破坏性操作（如删除文件、强制推送）。如果修复问题需要删除文件（如删除死代码，未使用代码等），则先讲相关问题标记为暂缓，先执行其他修复任务，最后报告给用户修复总结时，再提醒用户相关任务的暂缓原因。

大文件跳过：分析时忽略 node_modules、.git、dist、build、*.min.js 等生成目录。

误报处理：若某问题经分析是误报，可将其标记为 [x] 并在备注写明“误报/设计如此”。

测试依赖：如果项目无测试，修复后应至少保证语法正确和主要路径不崩溃。

报告更新频率：每次修复后必须更新报告并提交 Git，保证历史可溯。

用户显式授权可选开关
你可以在任务开始时询问以下参数（或由用户写入环境变量）：

MAX_FIXES_PER_RUN：单次运行最多修复多少个问题（避免循环过久），默认 100。

SKIP_GIT_AUTO_COMMIT：若为 true，仅修改报告和代码但不自动提交，默认 false。

SAFE_MODE：若为 true，修复前自动备份原文件到 .backup/，默认 true。
