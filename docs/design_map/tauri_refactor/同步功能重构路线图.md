## 1. 执行摘要

当前 SoloSoul 的同步功能基于 `yrs`（Yjs 的 Rust 绑定）实现了一个基础的双向同步协议，但在实际运行中存在**CRDT 合并失效、粒度粗糙、传输冗余、离线无队列**等系统性问题。Flutter 端的同步功能虽有已知 Bug，但本路线图选择**不在当前架构上修复**，而是将其作为 Tauri 重构阶段的重点功能重新设计和实现。

本路线图参考 **Anytype Any-Sync 协议**的本地优先（Local-First）架构理念，结合 2025-2026 年 CRDT 生态的最新进展（Automerge 3、Loro 1.0、Eg-walker），规划了一个分四阶段的同步重构方案。

**核心决策**：
- CRDT 引擎从 `yrs` 迁移至 **Loro**（Rust 原生，支持 movable tree，API 更友好）
- 同步协议从"请求-响应"升级为"**持续连接 + 后台推送**"
- 引入**离线编辑队列（Outbox）**和**本地同步日志**
- 网络层增加 **QUIC/WebRTC** 选项，突破局域网限制
- 保留 Noise 端到端加密，但改用**非对称密钥派生**（每台设备独立 keypair）

## 2. 当前架构诊断（从源码分析）

### 2.1 现有实现概览

| 模块 | 文件 | 实现 |
|---|---|---|
| CRDT 引擎 | `native/src/sync/crdt.rs` | `SoloDoc` 基于 `yrs::Doc`，每个 section 存为 JSON 字符串 |
| 同步引擎 | `native/src/sync/engine.rs` | 状态向量 + 差异更新，发起方/响应方双角色 |
| 加密通道 | `native/src/sync/protocol.rs` | Noise_IK（`snow` + `x25519-dalek`） |
| 网络传输 | `native/src/sync/transport.rs` | TCP + 4 字节长度前缀分帧 |
| Dart 端 | `lib/core/services/sync_service.rs` | 调用 FFI 接口，展示 SyncPage |

### 2.2 已知问题清单（代码级）

#### ❌ 问题 1：CRDT 合并经常失效，依赖 LWW Fallback

```rust
// engine.rs:241-276
let before = self.crdt.to_profile().ok();
if let Some(diff) = remote_diff {
    self.crdt.apply_update(&diff)?;  // ← 经常不生效
}
let after = self.crdt.to_profile().ok();
// ...
if b_json == a_json {
    // Fallback: 用 updated_at 比较，全量覆盖
    if remote_updated_at > self.local_updated_at {
        self.crdt = SoloDoc::from_profile(&remote_profile, &meta);
    }
}
```

**根因**：`SoloDoc` 将每个 section 序列化为整段 JSON 字符串存入 Yrs Map。当双方修改同一 section 的不同字段时，Yrs 的 Map CRDT 会对整个 value（JSON 字符串）做 LWW，导致**字段级修改丢失**。此时 `apply_update` 看似"成功"但实际上没有产生有意义的合并，所以 before/after 相同，触发 fallback。

#### ❌ 问题 2：传输冗余——每次携带完整 `profile_json`

```rust
// SyncMessage::StateVectorRequest / StateVectorResponse
profile_json: String,  // ← 完整 Profile JSON，可能数 MB
```

即使差异只有几百字节，同步消息中也携带完整的 `profile_json` 作为 fallback 素材。这在移动网络下不可接受。

#### ❌ 问题 3：同步粒度太粗——Section 级而非字段/对象级

```rust
// crdt.rs:52-79
if let Some(ref identity) = profile.identity {
    let json = serde_json::to_string(identity).unwrap_or_default();
    root.insert(&mut txn, KEY_IDENTITY, json);  // ← 整个 identity section 是一个字符串
}
```

修改护照号码和修改姓名被视为修改了同一个 "identity" section，冲突时整段被覆盖。

#### ❌ 问题 4：请求-响应模式，无持续连接

每次同步都要：
1. mDNS 发现 → 2. TCP 连接 → 3. Noise 握手 → 4. 状态交换 → 5. 断开

没有 WebSocket/长连接，无法实现**后台静默同步**。

#### ❌ 问题 5：离线无队列

用户在离线时编辑数据，修改只保存在本地 SQLite。当重新联网后，**不会自动触发同步**。没有 Outbox/同步队列概念。

#### ❌ 问题 6：附件串行传输

```rust
// engine.rs:504-522
for item in &my_missing {
    self.request_attachment(item, &dir, &mut stats)?;  // ← 串行，无并发
}
```

#### ❌ 问题 7：Noise_IK 使用相同 Keypair

```rust
// protocol.rs:428-432
let shared_kp = SecureChannel::derive_keypair(pairing_key, b"solosoul-sync-v1");
let (mut alice, mut bob) = SecureChannel::handshake_ik(&shared_kp, &shared_kp).unwrap();
```

测试代码中双方使用相同的 keypair。生产代码虽然传入不同 salt，但缺乏**设备身份认证**——任何知道 pairing key 的设备都可以冒充。

#### ❌ 问题 8：没有持久化同步日志

`SyncLogEntry` 只在 Dart 端的 UI 状态中存在，没有写入磁盘。同步失败后无法诊断原因。

## 3. Anytype Any-Sync 架构参考

### 3.1 核心设计理念

Anytype 的 Any-Sync 协议与 SoloSoul 的目标高度契合：

| 理念 | Any-Sync 实现 | SoloSoul 适用性 |
|---|---|---|
| **本地优先** | 主副本始终在本地设备，同步后台静默进行 | ✅ 完全一致 |
| **无网络依赖** | 支持局域网 P2P（mDNS）同步，无需互联网 | ✅ 完全一致 |
| **E2EE** | 所有 change 签名+加密，备份节点不可读 | ✅ 完全一致 |
| **创作者控制密钥** | 用户持有私钥，控制空间 ACL | ✅ 完全一致 |
| **CRDT DAG** | 每个对象是 DAG，change 是节点，多 head 自动合并 | ⚠️ 需引入 |
| **备份节点** | sync node / file node 解决"闭盖笔记本问题" | ⚠️ 可选引入 |
| **桥接模式** | 同一局域网内，有外网设备可为无外网设备桥接 | ⚠️ 可选引入 |

### 3.2 数据表示：CRDT DAG

```
Object (Profile)
├── Change 1 (初始创建) ──→ CID: 0xabc...
├── Change 2 (修改姓名) ──→ CID: 0xdef... ──→ parent: 0xabc
├── Change 3 (添加护照) ──→ CID: 0xghi... ──→ parent: 0xdef
│   └── Head A (设备 A 的视角)
└── Change 4 (修改国籍) ──→ CID: 0xjkl... ──→ parent: 0xdef
    └── Head B (设备 B 的视角)

当设备 A 再次编辑时：
Change 5 ──→ parent: [0xghi, 0xjkl]  (合并两个 head)
    └── New Head A'
```

**关键设计**：
- 每个 change 是**不可变**的，通过 CID（内容哈希）引用
- 每个 change 用 **Ed25519** 签名，验证来源
- change 内容是**加密的**，只有持有私钥的设备能解密
- 多 head 时，新 change 引用所有 head 作为 parent，实现自动合并
- **Snapshot**：概率性地将某 change 标记为 snapshot，跳过前面所有 change 直接重建状态

### 3.3 节点类型

```
┌─────────────────────────────────────────────────────────────┐
│                        用户设备层                             │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐                      │
│  │ MacBook │  │ iPhone  │  │ iPad    │  ← 本地存储 + P2P    │
│  └────┬────┘  └────┬────┘  └────┬────┘                      │
│       └─────────────┴─────────────┘                         │
│              mDNS / 局域网直连                                │
└─────────────────────────────────────────────────────────────┘
                            │
       ┌────────────────────┼────────────────────┐
       ▼                    ▼                    ▼
┌─────────────┐    ┌─────────────┐    ┌─────────────────────┐
│ Sync Node   │    │ File Node   │    │ Coordinator Node    │
│ (空间存储)   │    │ (附件存储)   │    │ (设备发现/配置)      │
└─────────────┘    └─────────────┘    └─────────────────────┘
       │                    │
       ▼                    ▼
┌─────────────────────────────────────────────────────────────┐
│              Consensus Node (ACL 变更验证)                   │
└─────────────────────────────────────────────────────────────┘
```

**SoloSoul 的简化**：
- 不强制要求用户运行节点，但**支持用户自建**（开源任何-sync-node 类似的组件）
- Coordinator 可以是**可选的公有服务**（仅用于设备发现，不存储数据）
- File Node 功能可以合并到 Sync Node
- 最小化部署：两台设备 + 可选的备份节点

### 3.4 对 SoloSoul 的启示

1. **引入 DAG 结构**：每条编辑都是一个带签名的 change，不是覆盖式更新
2. **设备独立身份**：每台设备有独立的 Ed25519 密钥对，不只是配对密钥
3. **后台持续同步**：长连接 + push，不是手动触发同步
4. **备份节点解决离线问题**：用户可以在自己的 VPS/NAS 上运行轻量节点
5. **桥接模式**：MacBook 可以为 iPhone 做桥，iPhone 不需要直连互联网

## 4. CRDT 引擎选型对比

### 4.1 候选库评估

| 维度 | **yrs** (当前) | **Automerge 3** | **Loro 1.0** | **cr-sqlite** |
|---|---|---|---|---|
| **语言** | Rust (Yjs 的 Rust 绑定) | Rust + WASM | Rust + WASM | C + SQLite |
| **数据模型** | Map/Text/Array | JSON-like | Map/List/Text/**MovableTree** | SQL 表行 |
| **文本 CRDT** | YATA (优秀) | Peritext (优秀) | Fugue (优秀) | N/A |
| **树结构** | ❌ 不支持 | ⚠️ 有限 | ✅ **原生 MovableTree** | ❌ |
| **性能** | 文本极快，JSON 一般 | 10x 文档压缩后优秀 | 与 Yjs/Automerge 同级 | SQLite 级别 |
| **内存占用** | 小 | 中 (3.0 大幅改善) | 中 | 最小 |
| **Dart/Flutter 绑定** | ✅ `yrs` crate 直接 | ❌ 需 WASM 桥接 | ✅ `loro` crate 直接 | ❌ 需 FFI |
| **Undo/Redo** | ✅ Yjs UndoManager | ✅ 原生支持 | ✅ 原生支持 | ❌ |
| **生态成熟度** | ⭐⭐⭐⭐⭐ 最成熟 | ⭐⭐⭐⭐ 增长中 | ⭐⭐⭐ 新兴但活跃 | ⭐⭐⭐ |
| **2026 推荐度** | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ **首选** | ⭐⭐⭐ |

### 4.2 为什么选 Loro？

**SoloSoul 的数据特征**：
- 结构化数据为主（个人档案、对象属性）
- 有层级关系（文件夹 → 对象 → 字段）
- 有文本字段（备注、描述）
- 有列表（附件、历史记录）
- 对象可能在不同分类间移动

**Loro 的匹配优势**：

1. **MovableTree**：SoloSoul 的 `UnifiedObject` 在不同 page/category 间移动，Loro 的 movable tree CRDT 能正确处理"并发移动同一节点到不同父节点"的冲突。Yrs/Automerge 对此支持有限。

2. **统一数据模型**：一个 `LoroDoc` 同时包含 Map（对象属性）、List（附件列表）、Text（备注）、Tree（对象层级），不需要像当前代码那样把 everything 序列化为 JSON 字符串。

3. **Rust 原生**：`loro` crate 直接集成到 Tauri 命令层，无需 WASM 桥接。`automerge` 虽然有 Rust 核心，但官方推荐通过 WASM 使用，Dart/Flutter 集成复杂。

4. **Snapshot + Diff**：Loro 支持 `export_snapshot()` 和 `export_from()`（差异导出），与 Any-Sync 的 snapshot 机制理念一致。

5. **DAG 语义**：Loro 内部使用 Event Graph，天然适合映射为 Any-Sync 的 CRDT DAG。

**示例对比**（当前 vs Loro）：

```rust
// ===== 当前实现（yrs）：粒度粗糙 =====
let json = serde_json::to_string(identity).unwrap();
root.insert(&mut txn, "identity", json);  // 整段 JSON 作为一个字符串

// ===== Loro 实现：字段级 =====
let identity = doc.get_map("identity");
identity.insert("full_name", "Alice Smith");
identity.insert("nationality", "US");
// 另一设备并发修改 passport_number → 自动合并，互不覆盖
```

## 5. 重构路线图

### Phase 1：基础修复（MVP，2-3 周）

**目标**：在不改变架构的前提下，修复当前同步的最严重 Bug，使其可用。

| 任务 | 详情 | 优先级 |
|---|---|---|
| 1.1 修复 CRDT 粒度 | 将 `SoloDoc` 从 section 级 JSON 改为**字段级**存储 | P0 |
| 1.2 移除 `profile_json` 冗余传输 | `SyncMessage` 中不再携带完整 JSON，仅传输 diff | P0 |
| 1.3 修复 Noise 密钥派生 | 每台设备使用独立 salt 生成独立 keypair，引入设备身份验证 | P1 |
| 1.4 附件并发传输 | 使用线程池/通道实现并行附件传输 | P1 |
| 1.5 持久化同步日志 | 将 `SyncLogEntry` 写入 SQLite，支持诊断 | P1 |

**技术方案**：
- 继续使用 `yrs`，但修改 `SoloDoc` 的映射策略
- 每个 `UnifiedObject` 对应一个 Yrs Map
- 每个字段对应 Map 的一个 entry（不再是 JSON 字符串）
- 附件列表使用 Yrs Array

### Phase 2：架构升级（核心重构，4-6 周）

**目标**：引入 Loro + 后台持续同步 + 离线队列。

| 任务 | 详情 | 优先级 |
|---|---|---|
| 2.1 引入 Loro | 替换 `yrs` 为 `loro` crate，重新设计 `SoloDoc` | P0 |
| 2.2 设计 Loro Schema | Profile → LoroDoc 映射：Map（对象）、Tree（层级）、List（附件）、Text（备注） | P0 |
| 2.3 后台同步服务 | Tauri 后台进程：长连接/心跳 + 自动重连 + 静默同步 | P0 |
| 2.4 离线编辑队列 | Outbox：本地修改先写队列，联网后自动批量推送 | P0 |
| 2.5 同步日志 v2 | 记录每个 change 的 CID、parent、签名、设备 ID | P1 |

### Phase 3：Any-Sync 风格 DAG（高级功能，4-6 周）

**目标**：引入 Any-Sync 风格的 CRDT DAG + 多设备身份 + 可选备份节点。

| 任务 | 详情 | 优先级 |
|---|---|---|
| 3.1 Change 结构 | 每个编辑 = 加密的 Loro diff + Ed25519 签名 + parent CID 列表 | P0 |

| 3.3 DAG 存储 | SQLite 表：`changes(id, cid, encrypted_diff, signature, parents, device_id, timestamp)` | P0 |
| 3.4 多 head 合并 | 检测到多 head 时，新 change 引用所有 head 作为 parent | P1 |
| 3.5 Snapshot 机制 | 每 N 个 change 或每 M 天自动生成 snapshot | P1 |
| 3.6 备份节点协议 | 轻量 sync node 实现（Rust），用户可自建 | P2 |
| 3.7 桥接模式 | 局域网内，有外网连接的设备为无外网设备中继 | P2 |

**Change 结构**：

```rust
pub struct Change {
    /// 内容哈希 (CID)
    pub cid: [u8; 32],
    /// 父 change 的 CID 列表（多 head 时多个 parent）
    pub parents: Vec<[u8; 32]>,
    /// 加密的 Loro diff（用账户主密钥加密）
    pub encrypted_diff: Vec<u8>,
    /// 设备 Ed25519 签名（验证来源）
    pub signature: [u8; 64],
    /// 设备公钥标识
    pub device_id: String,
    /// 时间戳（用于排序和调试，不参与一致性）
    pub timestamp: i64,
}
```

## 6. 冲突解决策略演进

### 6.1 当前策略（问题重重）

```
冲突场景               当前行为                    问题
─────────────────────────────────────────────────────────────
同 section 不同字段      整段 JSON LWW              字段修改丢失
同对象删除 vs 更新       保留更新（软删除）          可能不符合用户预期
双方同时编辑同一字段      LWW fallback              后提交者 wins，数据丢失
附件修改                 文件名 hash 对比            无版本控制
```

### 6.2 Phase 1 策略（字段级 LWW + 时间戳）

```
冲突场景               策略
─────────────────────────────────────────────────────────────
同对象不同字段          自动合并（Yrs Map 的 LWW 在字段级）
同字段同时修改          LWW，保留 updated_at 较新的值
删除 vs 更新            保留更新，标记"待审查"
附件                  文件级 hash 对比，缺失则传输
```

### 6.3 Phase 2 策略（Loro 自动合并）

```
冲突场景               策略
─────────────────────────────────────────────────────────────
同对象不同字段          ✅ 自动合并，互不覆盖
同字段同时修改          Loro Register/Map 的 LWW 语义
文本字段并发编辑        Loro Text 的 CRDT 合并（无丢失）
列表并发操作            Loro List 的插入/删除自动合并
对象移动                Loro MovableTree 的合并语义
删除 vs 更新            用户配置策略（默认保留更新）
```

### 6.4 Phase 3 策略（DAG + 用户审查）

```
冲突场景               策略
─────────────────────────────────────────────────────────────
所有场景               自动合并为默认，但保留完整历史
歧义合并               标记为"需要审查"，用户可在"同步日志"
                       中查看冲突详情并选择版本
恶意设备              Ed25519 签名验证失败 → 拒绝 change
回滚需求              用户可选择恢复到任意历史 snapshot
```

## 7. 关键技术决策

### 7.1 决策矩阵

| 决策项 | 选项 A | 选项 B | 推荐 | 理由 |
|---|---|---|---|---|
| CRDT 引擎 | 继续使用 `yrs` | 迁移到 `loro` | **B** | MovableTree + 字段级 + Rust 原生 |
| 同步模式 | 请求-响应（手动） | 持续连接（后台自动） | **B** | Any-Sync 风格，用户体验更好 |
| 离线支持 | 无队列 | Outbox 队列 | **B** | 本地优先应用必备 |
| 传输协议 | TCP 唯一 | TCP + QUIC | **B** | QUIC 更好的 NAT 穿透和多路复用 |
| 网络范围 | 仅局域网 | 局域网 + 可选中继 | **B** | 解决"不在同一 WiFi"场景 |
| 设备认证 | 配对密钥 | 配对密钥 + Ed25519 | **B** | 防止密钥泄露后的冒充 |
| 备份节点 | 无 | 轻量自托管 | **可选** | 解决闭盖笔记本问题，但非 MVP |

### 7.2 依赖库清单

| 库 | 用途 | 引入阶段 |
|---|---|---|
| `loro` | CRDT 引擎 | Phase 2 |
| `ed25519-dalek` | 设备身份签名 | Phase 3 |
| `quinn` | QUIC 传输 | Phase 2 |
| `sha2` / `blake3` | CID 哈希计算 | Phase 3 |
| `snow` | Noise 协议（保留） | 已有 |
| `x25519-dalek` | 密钥交换（保留） | 已有 |
| `tokio` | 异步运行时（后台同步） | Phase 2 |

### 7.3 数据迁移策略

当前 `yrs` 格式的同步数据不需要迁移——同步数据是临时的（状态向量 + diff），不持久化。Vault 中的 Profile JSON 是主数据源。

重构后：
1. 本地 SQLite 增加 `sync_changes` 表存储 DAG
2. Profile JSON 作为 LoroDoc 的 snapshot 导出/导入
3. 首次启动重构版本时，从 Profile JSON 初始化 LoroDoc
4. 旧版设备与新设备同步时，通过 Profile JSON fallback 兼容

## 8. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| `loro` 生态尚不成熟 | 中 | 密切关注 1.0 稳定性，保留 `yrs` 回退路径；Phase 1 先用 `yrs` 修复粒度问题 |
| QUIC 防火墙穿透困难 | 低 | TCP 作为 fallback，QUIC 作为优化 |
| 后台同步耗电 | 中 | 移动端限制后台频率，WiFi 时全量、蜂窝时仅关键数据 |
| DAG 历史膨胀 | 中 | Snapshot + 定期 GC（保留最近 90 天 change） |
| 多设备 Ed25519 密钥管理 | 中 | 密钥派生自账户主密钥 + 设备标识，无需额外备份 |

### 9.2 术语表

|---|---|
