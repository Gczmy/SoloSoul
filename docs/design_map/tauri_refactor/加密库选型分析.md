## 1. 当前实际使用的库

| 库 | 版本 | 用途 | 代码位置 |
|---|---|---|---|
| `aes-gcm` | 0.10 | AES-256-GCM 对称加密 + 认证 | `native/src/crypto/aes.rs` |
| `argon2` | 0.5 | Argon2id 密钥派生 (KDF) | `native/src/crypto/argon2.rs` |
| `zeroize` | 1.7 | 安全内存擦除 (`Zeroizing<T>`) | 全模块 |
| `rand` | 0.8 | CSPRNG 随机数生成 | `aes.rs` (OsRng) |
| `snow` | 0.9 | Noise 协议（设备同步加密通道） | 间接使用 |
| `x25519-dalek` | 2 | X25519 密钥交换（Noise 握手） | `Cargo.toml` 显式依赖 |
| `sha2` | 0.10 | SHA-256（插件握手等） | 辅助用途 |

### 1.1 核心加密流程

```
用户密码 ──→ Argon2id ──→ 32-byte 主密钥 ──→ AES-256-GCM ──→ SOLO blob
                                                         (Magic + Nonce + Ciphertext + Tag)
```

### 1.2 当前架构的加密能力边界

- ✅ 密码派生（Argon2id，3 档参数可调：Fast / Balanced / Secure）
- ✅ 对称加密（AES-256-GCM，单块 + 分块两种格式）
- ✅ 密钥交换（X25519，通过 Noise 协议）
- ✅ 内存安全（zeroize 自动擦除）
- ❌ 数字签名（无 Ed25519）
- ❌ 零知识证明（无 ZKP）
- ❌ 同态加密（无 HE）
- ❌ 后量子密码学（无 PQC）
- ❌ 流加密备选（无 ChaCha20-Poly1305）

## 2. 与候选库的逐项对比

### 2.1 AES-256-GCM（当前 `aes-gcm`） vs ChaCha20-Poly1305

| 维度 | AES-256-GCM（当前） | ChaCha20-Poly1305 |
|---|---|---|
| **算法家族** | 分组密码 (AES) + GCM 模式 | 流密码 (ChaCha) + Poly1305 MAC |
| **性能（有硬件加速）** | ⭐⭐⭐⭐⭐ 极快（x86 AES-NI, ARM AES 指令） | ⭐⭐⭐ 纯软件，无专用指令 |
| **性能（无硬件加速）** | ⭐⭐ 软件实现慢 | ⭐⭐⭐⭐⭐ 恒定的软件性能 |
| **侧信道抗性** | ⭐⭐ 对时序攻击敏感（需恒定时间实现） | ⭐⭐⭐⭐⭐ 天然恒定时间 |
| **nonce 重用风险** | ❌ 灾难性（密钥恢复） | ❌ 灾难性（但概率更低） |
| **标准化** | NIST FIPS 197 | RFC 8439 (IETF 标准) |
| **Rust 实现** | `aes-gcm` (RustCrypto) | `chacha20poly1305` (RustCrypto，同组织) |

**结论**：两者都是安全的 AEAD 算法。AES-GCM 在有硬件加速时更快（现代桌面/手机都有），ChaCha20 在软件实现上更优且侧信道抗性更好。当前 AES-GCM 选择完全合理，但**建议增加 ChaCha20-Poly1305 作为用户可选算法**（特别是为 ARM 无 AES 加速的旧设备）。

**Tauri 推荐度**：
- `aes-gcm`：⭐⭐⭐⭐⭐ **继续使用**
- `chacha20poly1305`：⭐⭐⭐⭐ **建议增加为备选**

---

### 2.2 x25519-dalek（当前已通过 snow 使用）

| 维度 | 当前状态 |
|---|---|
| **用途** | Noise_IK 握手（设备同步的密钥交换） |
| **实现质量** | dalek-cryptography 组织，业界标杆，已审计 |
| **显式依赖** | `x25519-dalek = { version = "2", features = ["static_secrets"] }` |

**结论**：当前已经在用，且是最好的实现之一。无需替换。

**Tauri 推荐度**：⭐⭐⭐⭐⭐ **继续使用**

---

### 2.3 ed25519-dalek（当前未使用）

| 维度 | Ed25519 |
|---|---|
| **用途** | 数字签名（与 X25519 同曲线，但不同用途） |
| **典型场景** | 插件签名验证、备份文件签名、去中心化身份 |
| **当前需求** | 暂无签名需求 |
| **未来可能需求** | 插件市场安全（验证插件作者签名）、备份完整性校验 |

**结论**：SoloSoul 当前没有数字签名场景。但如果未来引入"插件签名验证"或"备份文件防篡改签名"，Ed25519 是最佳选择（与已有的 X25519 共享 Edwards25519 曲线基础设施）。

**Tauri 推荐度**：⭐⭐⭐ **按需引入**（有签名需求时再添加）

---

### 2.4 Swanky / zkryptium（零知识证明）

| 维度 | Swanky | zkryptium |
|---|---|---|
| **出品方** | Galois（美国国防承包商） | 社区 |
| **成熟度** | ⭐⭐⭐⭐⭐ 生产级 | ⭐⭐⭐ 研究级 |
| **Rust 集成** | 良好 | 良好 |
| **典型场景** | 隐私身份验证、范围证明、合规证明 | 研究/高级场景 |

**SoloSoul 场景匹配度分析**：

ZKP 的核心价值是**"向第三方证明某属性为真，但不暴露属性值"**。例如：
- 向航空公司证明"我年满 18 岁"，但不暴露出生日期
- 向银行证明"我的资产 > $100k"，但不暴露具体金额

**SoloSoul 的问题**：SoloSoul 是**完全本地优先**的应用，数据不上传云端，没有"向第三方证明"的场景。ZKP 解决的是**多方不信任场景**下的隐私问题，而 SoloSoul 的场景是**单方完全控制**下的数据加密。

**唯一可能的 ZKP 场景**：未来如果 SoloSoul 允许用户"选择性披露"某些加密字段给外部服务（如 eKYC、保险理赔），ZKP 才有价值。

**Tauri 推荐度**：⭐ **当前不需要**。如果新增"选择性披露/隐私凭证"功能，Swanky 是首选（Galois 出品，经过实战检验）。

### 2.5 libsumatracrypt-rs（同态加密 + 后量子）

这是最有讨论价值的库，包含两个完全不同的技术方向：

#### A. 同态加密（Homomorphic Encryption）

| 维度 | 评估 |
|---|---|
| **能力** | 在**不解密**的情况下对密文进行计算 |
| **Rust 状态** | `tfhe-rs`、`concrete` 较成熟，但 `libsumatracrypt-rs` 集成度未知 |
| **性能** | ⭐ 极慢（比明文慢 1000x–1000000x） |
| **SoloSoul 场景** | "在加密数据上运行 AI/搜索"听起来很诱人，但目前性能完全不可行 |

**现实判断**：2026 年的全同态加密（FHE）仍无法在交互式桌面应用中实时运行。如果用户有 1000 条加密记录，FHE 搜索可能需要数秒到数分钟。这与 SoloSoul 的流畅体验目标冲突。

**Tauri 推荐度**：⭐ **不建议当前引入**。可作为长期技术跟踪。

#### B. 后量子密码学（Post-Quantum Cryptography）

| 维度 | 评估 |
|---|---|
| **威胁模型** | 量子计算机（Shor 算法破解 RSA/ECC，Grover 算法削弱 AES-256 到 128-bit 等效） |
| **NIST 标准** | CRYSTALS-Kyber（KEM）+ CRYSTALS-Dilithium（签名），2024 已正式发布 |
| **迁移紧迫性** | 低（大规模量子计算机预计 10-15 年后） |
| **SoloSoul 特殊考量** | 用户数据可能保存 10-20 年（护照、身份等长期有效），**今天加密的数据未来可能被量子破解** |

**关键决策点**：这是**所有密码学应用都面临的长期问题**。即使量子计算机 15 年后出现，攻击者可以**今天截获加密数据，15 年后用量子计算机解密**（"harvest now, decrypt later"）。

**建议**：
1. **短期**：在 Vault 元数据中预留 `algorithm` 字段（当前已有 `KdfAlgorithm` 枚举模式，可扩展为 `CipherAlgorithm`），为未来算法升级做准备
2. **中期（2-3 年）**：评估 `ml-kem`（Kyber 的 Rust 实现）替代 X25519 用于设备同步密钥交换
3. **长期**：当后量子算法生态更成熟时，迁移主加密算法

**Tauri 推荐度**：⭐⭐⭐ **中长期必须规划**，但当前不急于实现。建议现在做好**算法可插拔的架构设计**。

## 4. Tauri 重构时的加密模块建议

### 4.1 推荐的最小可行目录结构（MVP）

```
crates/solosoul-crypto/
├── src/
│   ├── lib.rs
│   ├── kdf.rs          # Argon2id（保持当前实现）
│   ├── cipher.rs       # AES-256-GCM + ChaCha20-Poly1305（双算法）
│   ├── exchange.rs     # X25519（保持当前 snow 集成）
│   ├── sign.rs         # Ed25519（预留，按需启用）
│   ├── secure.rs       # zeroize + SecureBytes
│   └── pqc.rs          # 后量子预留接口（空实现/traits）
```

### 4.2 关键决策

| 决策 | 建议 | 理由 |
|---|---|---|
| **保持 AES-GCM 为主算法** | ✅ | 硬件加速成熟，当前数据格式已稳定 |
| **增加 ChaCha20-Poly1305** | ✅ | 作为 `CipherAlgorithm` 枚举的第二个变体，用户可选 |
| **引入 Ed25519** | 观望 | 有插件签名/备份签名需求时再引入 |
| **引入 ZKP** | ❌ | 当前无匹配场景 |
| **引入同态加密** | ❌ | 性能不满足实时需求 |
| **后量子预留** | ✅ | 在 `KdfParams`/`CipherAlgorithm` 枚举中预留 PQC 变体，为未来迁移做准备 |
| **密钥派生参数** | 保持 3 档 | Fast(8MiB/2it) / Balanced(16MiB/3it) / Secure(64MiB/3it) 设计合理 |

### 4.3 具体建议：增加算法可插拔性

当前 `argon2.rs` 中已有很好的 `KdfAlgorithm` 枚举设计：

```rust
pub enum KdfAlgorithm {
    #[serde(rename = "argon2id")]
    Argon2id,
    #[serde(rename = "pbkdf2")]
    Pbkdf2,
}
```

建议在 Tauri 重构时，将这一模式扩展到**对称加密算法**：

```rust
pub enum CipherAlgorithm {
    #[serde(rename = "aes-256-gcm")]
    Aes256Gcm,        // 当前默认
    #[serde(rename = "chacha20-poly1305")]
    ChaCha20Poly1305, // 新增备选
    // #[serde(rename = "ml-kem-768")]
    // MlKem768,      // 后量子预留
}
```

这样 Vault 的 `config.json` 可以记录使用的算法，未来无缝迁移到后量子算法时，旧数据仍能被正确解密。

## 5. 总结

当前 SoloSoul 的加密选型（`aes-gcm` + `argon2` + `x25519-dalek` + `zeroize`）是**非常合理且行业标准**的组合。

用户提供的参考库中，**只有 `chacha20poly1305` 和 `ed25519-dalek` 值得在 Tauri 重构时考虑引入**，其余（ZKP、HE）与当前场景不匹配，后量子密码学则应做好**架构预留**而非立即实现。

**核心原则**：不要为技术而技术。SoloSoul 的加密需求是"保护本地个人数据"，而非"构建隐私计算平台"或"区块链身份系统"。选型应以**场景匹配度**为第一优先级。
