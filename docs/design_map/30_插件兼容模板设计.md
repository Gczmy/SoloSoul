# 30 — 插件兼容模板设计

> **版本**：v1.0
> **状态**：设计稿 / 待评审
> **作者**：SoloSoul Team
> **日期**：2026-06-13

---

## 1. 背景与问题

SoloSoul 的核心理念之一是**用户可以自由定义任何类型与字段**。用户可以创建名为"地址对象"的类型，也可以把街道字段叫做"街道""Street"或"addr_01"。这种自由在前端只影响显示名称，后端实际依赖的是 `type_id` 与字段 `id`。

但插件系统目前通过固定路径读取数据，例如：

```rust
get_field("address.count")
get_field("address[0].street")
```

这意味着插件只能识别：

- `type_id` 为 `address` 的对象；
- 字段 `id` 为 `street`、`city`、`country` 等的属性。

当用户自定义了类型名或字段名，但底层 `type_id` / 字段 `id` 与插件期望不一致时，插件就会读到空数据（如 `address.count = 0`），运行失败。

这就形成了一个设计矛盾：

- **自由定义** → 用户可能使用任意 `type_id` / 字段 `id`；
- **插件互操作** → 插件需要稳定的 `type_id` / 字段 `id` 契约。

本方案提出**"插件兼容模板（Plugin-Compatible Template）"**机制：在完全自由的 Schema 之上，提供一组官方推荐的"契约模板"。用户可以在这些模板上自由扩展，但只要不破坏插件所需的字段骨架，就能与官方插件无缝配合。

---

## 2. 设计目标

| 目标 | 说明 |
|------|------|
| **保留用户自由** | 用户仍可在兼容模板上增加字段、修改显示名称、图标、分类等。 |
| **提供稳定契约** | 官方模板与官方插件之间保持固定的 `type_id` / 字段 `id` 映射。 |
| **可视化兼容关系** | 在模板选择、类型管理、对象详情等页面展示"插件兼容"徽章。 |
| **防止无意破坏** | 当用户删除、重命名插件必需字段，或修改类型 `type_id` 时，给出明确警告。 |
| **渐进式落地** | 先覆盖官方插件与官方模板，未来可扩展至第三方插件。 |

---

## 3. 非目标

本方案**不解决**以下问题：

- 用户完全自定义的类型与官方插件的自动匹配（需要语义映射或运行时字段映射）。
- 第三方插件的强制规范（第三方插件仍可声明自己的 `required_fields`，但官方不会为其提供模板）。
- 插件之间的字段冲突仲裁（如两个插件对同一名称字段有不同语义要求）。

---

## 4. 术语

| 术语 | 定义 |
|------|------|
| **契约类型（Contract Type）** | 官方插件依赖的底层 `type_id`，如 `address`、`contact`、`passport`。 |
| **契约字段（Contract Field）** | 官方插件依赖的底层字段 `id`，如 `street`、`city`、`country`。 |
| **插件兼容模板（Plugin-Compatible Template）** | 包含完整契约类型与契约字段的官方示例模板。 |
| **兼容性状态（Compatibility Status）** | 某个用户类型/对象是否仍满足特定插件的字段要求。 |
| **插件徽章（Plugin Badge）** | UI 上用于提示模板/类型/对象与哪些插件兼容的视觉标记。 |

## 6. 详细设计

### 6.1 官方模板的数据结构

在现有 `SampleTemplate` 基础上，新增插件兼容元数据：

```ts
interface SampleTemplate {
  id: string;
  nameI18nKey: string;
  nameFallback: string;
  category: TemplateCategory;
  // ... 现有字段

  /**
   * 是否为插件兼容模板。
   * 为 true 时，typeId 与字段 id 必须与对应插件的 required_fields 对齐。
   */
  isPluginCompatible?: boolean;

  /**
   * 兼容的插件 ID 列表。
   * 一个模板可以同时兼容多个插件（如 address 类型未来可能被多个插件使用）。
   */
  compatiblePluginIds?: string[];

  /**
   * 契约类型 id，必须等于插件期望的 type_id。
   */
  typeId: string;

  /**
   * 契约字段列表。
   * 这些字段的 id 不可被用户修改或删除。
   */
  contractFields: {
    id: string;
    nameI18nKey: string;
    type: PropertyType;
    required: boolean;
  }[];
}
```

示例：地址格式化器兼容模板

```ts
{
  id: "official-address-compatible",
  nameI18nKey: "template:official_address_compatible",
  nameFallback: "Address (Plugin Compatible)",
  category: "identity",
  isPluginCompatible: true,
  compatiblePluginIds: ["com.solosoul.official.address-fmt"],
  typeId: "address",
  contractFields: [
    { id: "title", nameI18nKey: "template:field_title", type: "text", required: false },
    { id: "street", nameI18nKey: "template:field_street", type: "text", required: true },
    { id: "district", nameI18nKey: "template:field_district", type: "text", required: false },
    { id: "city", nameI18nKey: "template:field_city", type: "text", required: true },
    { id: "state", nameI18nKey: "template:field_state", type: "text", required: false },
    { id: "postalCode", nameI18nKey: "template:field_postal_code", type: "text", required: false },
    { id: "country", nameI18nKey: "template:field_country", type: "text", required: true }
  ]
}
```

> **⚠️ SampleTemplate.typeId 与 PluginContractBinding.typeId 的映射规则**：
>
> 上述示例中 `typeId: "address"` 仅作示意。在实际实现中，推荐 SampleTemplate 直接使用反向域名版本号格式（如 `"com.solosoul.address/v1"`）作为 `typeId`，这样 SampleTemplate → UserTemplate → PluginContractBinding 三层数据流无需中间映射表。如果必须使用短名（如 `"address"`），则须在模板中心维护短名到反向域名的映射表，确保写入 UserTemplate 的 `contract_type_id` 与插件 manifest `contracts[0].typeId` 一致。否则 resolve_typed 无法匹配 `UserTemplate.contract_type_id == PluginContractBinding.typeId`。

### 6.2 从模板创建类型/对象时的约束

当用户选择插件兼容模板时：

1. 生成的用户类型 `type_id` 固定为模板 `typeId`，不可在 UI 中直接修改（或修改时弹出强警告）。
2. 契约字段的 `id` 固定，用户只能修改：
   - 显示名称（`name`）
   - 敏感度等级
   - 图标、描述、默认值等元数据
3. 用户可以自由添加新字段，但新字段 `id` 不能和契约字段冲突。
4. 契约字段默认**不可删除**。如果用户坚持删除，触发 6.4 节的警告流程。

### 6.3 兼容性检测算法

#### 6.3.1 解析插件契约

从插件 manifest 的 `required_fields` 中解析出契约类型与契约字段。

支持的路径模式：

| 路径示例 | 解析结果 |
|---|---|
| `address.count` | 类型 `address`，特殊字段 `count`（忽略） |
| `address.street` | 类型 `address`，字段 `street` |
| `address[0].country` | 类型 `address`，字段 `country` |
| `travel.primary_passport.number` | 类型 `travel`，字段 `primary_passport`（视为对象字段，可递归） |

算法步骤：

1. 去掉数组下标部分（`[n]`）。
2. 去掉 `.count` 后缀。
3. 取第一部分为 `type_id`。
4. 剩余部分按 `.` 分割，第一级字段 id 即为契约字段。

#### 6.3.2 判断类型/对象兼容性

```ts
function getCompatibilityStatus(
  template: UserTemplate,
  pluginManifests: PluginManifest[]
): CompatibilityStatus {
  const affectedPlugins: string[] = [];
  const missingFields: Record<string, string[]> = {}; // pluginId -> fieldIds

  for (const manifest of pluginManifests) {
    const contract = parseContractFields(manifest.requiredFields);
    if (contract.typeId !== template.id) continue;

    const templateFieldIds = new Set(template.properties.map(p => p.id));
    const missing = contract.fieldIds.filter(id => !templateFieldIds.has(id));

    if (missing.length > 0) {
      affectedPlugins.push(manifest.id);
      missingFields[manifest.id] = missing;
    }
  }

  if (affectedPlugins.length === 0) {
    return { compatible: true };
  }

  return {
    compatible: false,
    affectedPlugins,
    missingFields
  };
}
```

兼容性状态用于：

- 渲染插件徽章（全部兼容时显示绿色徽章）。
- 灰显或禁用插件运行按钮（缺少必需字段时）。
- 在对象/类型详情页展示缺失字段清单。

> **适用范围说明**：§6.3 的兼容性算法（基于 `required_fields` 字符串前缀解析）适用于以下两类场景：
>
> - **Legacy 插件**（manifest 未声明 `contracts`）—— 仅能通过 `required_fields` / `permissions` 推断契约类型与字段。
> - **Typed 插件的降级展示**—— 在 typed-lookup 运行时（§13.3）生效前，前端 UI 仍需通过此算法渲染兼容性徽章。
>
> Stage 4 完成后，typed 插件（manifest 声明了 `contracts`）的字段绑定以 `contract_type_id` + `contract_field` 为准，不再依赖字符串前缀解析。此时 §6.3 算法退化为仅用于 legacy 插件和前端降级展示的 fallback 路径。

### 6.4 删除/重命名/改 type_id 时的警告

在类型编辑器、对象编辑器、模板管理页面，执行以下操作前需要调用兼容性检查：

| 用户操作 | 检查逻辑 | 提示文案示例 |
|---|---|---|
| 删除字段 | 字段 id 是否在某插件的契约字段列表中 | "`street` 是「地址格式化器」必需的字段，删除后该插件将无法运行。" |
| 重命名字段 id | 旧字段 id 是否是契约字段 | "重命名 `street` 会导致「地址格式化器」无法识别该字段。" |
| 修改 type_id | 该 type_id 是否被任何插件依赖 | "修改类型标识符后，此类型将不再与官方插件兼容。" |

警告级别：

- **删除/重命名字段 id / 改 type_id**：强警告，需要用户二次确认。
- **修改字段显示名称**：无警告。
- **新增字段**：无警告。
- **删除非契约字段**：无警告。

### 6.5 插件运行前的兼容性校验

在插件详情页或运行按钮处：

1. 根据插件 manifest 的 `required_fields` 解析契约。
2. 扫描用户 Vault 中是否存在 `type_id` 匹配的类型。
3. 检查该类型是否包含所有契约字段。
4. 如果不匹配：
   - 禁用运行按钮；
   - 显示提示：缺少类型 `address` 或缺少字段 `street`；
   - 引导用户安装/使用对应的官方兼容模板。

### 6.6 徽章设计

#### 6.6.1 模板示例徽章

在 `SampleTemplateGallery` 和 `SampleTemplateDetail` 中，对 `isPluginCompatible === true` 的模板显示：

```
🧩 兼容：地址格式化器
```

如果兼容多个插件：

```
🧩 兼容：地址格式化器、地址导出器
```

#### 6.6.2 类型/对象徽章

在类型管理页、对象详情页、列表页中：

- 若该类型/对象仍满足所有契约字段：显示绿色徽章。
- 若缺少部分字段：显示黄色警告徽章，hover 时展示缺失字段。
- 若用户已修改 `type_id` 脱离契约：不显示徽章。

## 7. 数据流与状态管理

### 7.1 后端

无需新增数据库表。兼容性判断完全基于：

- 已安装插件的 manifest（`required_fields`）；
- 用户类型的 schema（`type_id`、`properties[].id`）。

可以新增一个 Rust 工具函数或 Tauri Command：

```rust
#[command]
pub async fn plugin_check_type_compatibility(
    state: State<'_, AppState>,
    type_id: String,
) -> Result<TypeCompatibilityReport, String>;
```

### 7.2 前端

新增一个工具函数：

```ts
export function checkTypeCompatibility(
  template: UserTemplate,
  installedManifests: PluginManifest[]
): TypeCompatibilityReport;
```

在以下页面调用：

- `SampleTemplateGallery` / `SampleTemplateDetail`：渲染徽章。
- 类型编辑器：删除/重命名字段前弹窗。
- 插件详情页/卡片：运行按钮状态。
- 对象详情页：展示兼容徽章。

## 8. 实现阶段

### 前置阶段（Stage 4）：Typed-lookup 宿主底层依赖

> 本节是 §13 （Stage 4 完整设计）的概要，对应下面的 Stage 4-A ~ Stage 4-D。Stage 4 是 typed-lookup 宿主层的必经前置依赖，完成后才能解锁上方 Phase 1-5 中与插件运行时绑定相关的部分。为避免命名冲突，Stage 4 子阶段不使用 (P0)/(P1) 等优先级标签。

- **Stage 4-A — Schema 扩展**：将 SDK manifest schema 版本从 1.0 升级至 1.1，增加 `contracts` 与 `field_bindings` 字段。新增 `PluginContractBinding` / `PluginFieldBinding` Rust 结构体。同步更新 `tauri/crates/solosoul-plugin/src/{manager,manifest}.rs` 与 `tauri/src-tauri/src/plugin/{manager,manifest}.rs` 两份镜像代码。按 §13.2.3 清单补全 struct-literal 站点（`contracts: vec![]` / `field_bindings: vec![]`）。`MarketManifestRaw` 与 `RegistryEntry` 仅需增加反序列化字段，不需要改动加载逻辑。
- **Stage 4-B — Typed-lookup 运行时（核心）**：实现 `field.rs::resolve_typed` 与别名桥接 `parse_typed_field`（详见 §13.3.2.5），改造 `resolve()` 与 `field_metadata()` 为双路径分发。新增 4 个单元测试 + 1 个集成测试 + 1 个 Tauri 镜像测试。
- **Stage 4-C — 官方插件 manifest 升级（P1）**：按 §13.6 可达矩阵分批推进（BATCH-A → BATCH-B → BATCH-C），每个插件一条 commit。
- **Stage 4-D — 废弃 legacy 路径（P3）**：通过 `legacy_field_parse` feature flag 控制，默认 `true` 保持至 v3.0。v3.0 起默认 `false`，宿主拒绝 `plugin_api_version < 1.1` 的插件。legacy 兼容窗口从 Stage 4-C 完成后起算至少保留 6 个月，并可通过配置开关延长。

### Phase 1：官方兼容模板（P0）

1. 在 `SampleTemplate` 数据结构里新增 `isPluginCompatible`、`compatiblePluginIds`、`contractFields`。
2. 新增"地址（插件兼容）"官方示例模板，与 `com.solosoul.official.address-fmt` 对齐。
3. 在模板画廊和模板详情页渲染插件兼容徽章。
4. 模板选择后，生成的用户类型 `type_id` 和字段 `id` 固定为契约值。

### Phase 2：类型/对象徽章（P1）

1. 新增 `plugin_check_type_compatibility` Command 或前端工具函数。
2. 在类型管理页、对象详情页展示兼容性徽章。
3. 徽章状态随 schema 变化实时更新。

### Phase 3：编辑守卫（P1）

1. 在类型编辑器中，删除字段、重命名字段 id、修改 type_id 时调用兼容性检查。
2. 对契约字段的破坏性操作弹出二次确认弹窗。
3. 用户确认后，徽章状态降级为"部分兼容"或消失。

### Phase 4：运行前校验（P2）

1. 在插件卡片/详情页的运行按钮处集成兼容性校验。
2. 不兼容时禁用按钮并展示原因清单。
3. 提供快捷入口：跳转到对应官方兼容模板。

### Phase 5：多插件与第三方扩展（P3）

1. 支持一个模板兼容多个官方插件。
2. 允许第三方插件在 manifest 中声明 `compatible_templates`，系统据此推荐模板。
3. 评估是否需要引入语义标签作为补充机制。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 官方模板字段 ID 后续变更 | 既有用户数据与新版插件不兼容 | 官方模板发布后字段 id 冻结；如需调整，发布新契约类型（如 `address_v2`）并同步更新插件。 |
| 用户复制模板后改 type_id | 插件找不到数据 | 改 type_id 时强警告；运行前校验明确提示缺少类型。 |
| 用户删除契约字段后运行插件 | 插件读到空数据或失败 | 运行按钮置灰；编辑删除时二次确认。 |
| 一个类型兼容多个插件，字段要求冲突 | 难以同时满足 | 目前官方插件统一由官方维护，避免冲突；未来第三方插件通过语义标签解决。 |
| 模板过多导致画廊拥挤 | 用户体验下降 | 增加"插件兼容"筛选器，让用户只看官方推荐模板。 |

## 10. 附录：地址格式化器契约示例

### 10.1 插件 manifest 片段

```json
{
  "plugin_id": "com.solosoul.official.address-fmt",
  "required_fields": [
    "address.count",
    "address.title",
    "address.street",
    "address.district",
    "address.city",
    "address.state",
    "address.postalCode",
    "address.country"
  ]
}
```

### 10.2 官方兼容模板契约

| 契约字段 id | 是否必需 | 插件用途 |
|---|---|---|
| `title` | 否 | 结果卡片中的地址标签 |
| `street` | 是 | 街道 |
| `district` | 否 | 区/县 |
| `city` | 是 | 城市 |
| `state` | 否 | 省/州 |
| `postalCode` | 否 | 邮编 |
| `country` | 是 | 国家，用于选择格式化规则 |

### 10.3 用户可自由修改的内容

- 类型显示名称（如"地址""Addresses""アドレス"）
- 字段显示名称
- 字段敏感度
- 字段默认值、描述、图标
- 类型分类
- 新增任意字段

### 10.4 用户不可破坏的内容

- 类型 `type_id`：`address`
- 契约字段 `id`：`street`、`city`、`country` 等

## 13. Stage 4 设计 — typed-lookup plugin ↔ object 绑定

> **状态**:待评审 / 待实现
> **作者**:SoloSoul Team
> **日期**:2026-06-18
> **前置条件**：Stage 1 (commit `382f0cc5`) + Stage 2 (`cf12e7ff` + `c6eac2ef`) + Stage 3 (`b89e221c`) 已合并，`v2.4.0` 已发布。
> **解决的问题**：Schema 层的 contract 字段已经落地到数据库，但运行时还没有任何宿主函数读取这些字段。Stage 4 填补这一落差，为后续 Stage 5（多插件 / 第三方契约支持）奠定 typed-lookup 基线。

### 13.1 关键诊断与动机

**当前 plugin ↔ object 绑定的唯一实际路径**(验证:`tauri/crates/solosoul-plugin/src/field.rs`):

```rust
// plugin/field.rs:113 — 唯一的 fallback 路径
if let Some((type_id, prop_path)) = parse_type_property(field_id) {
    let objects = vault.list_objects(account_id, Some(&type_id), ...)?;
    Ok(extract_property(&objects[0].properties, &prop_path))
}
```

- `parse_type_property` 把 `"address.street"` 拆为 `(type_id="address", prop_path="street")`;
- 然后 `vault.list_objects(account_id, Some("address"), ...)` 走 `UserTemplate.id == "address"` **字面**匹配 — **不查 `t.contract_type_id`**;
- `host.rs::solosoul_field_metadata` 走同样的字符串前缀 (`trace plugin.rs:165-180`),**也不查 `t.contract_type_id`**;
- `build_structure_tree` (host.rs::solosoul_get_data_structure_tree) 也只看 `t.id`, 不带 contract 字段。

**结论**:`contract_type_id` / `contract_field` (Stage 1-3 落到 v17 + 202 tests passing) 在 host 层是**完全死的字段**。Plugin ↔ object 仍然完全靠 `parse_type_property` 字符串前缀 + `required_fields` 字符串列表,**0 typed lookup**。

**Stage 4 目标 (业务动机)**:

1. 让 `UserTemplate.contract_type_id` 在运行时实际起作用,作为 plugin 事实上的 binding anchor。
2. 让 `TemplateProperty.contract_field` 起到 gate 作用 — 不是"任意 property 都能被 plugin 读",而是"被 `contract_field=true` 显式 opt-in 的 property 才能被 plugin 通过 typed 路径读"。
3. 在多 plugin 场景下 (Stage 5),让 `ObjectRecord.contract_type_id` 反向找到一组 templates 后,可让 plugin 选 typed lookup 而不是必须靠 `<type_id>` 字符串猜测。
4. 不破坏既有 6 个官方插件:任何缺 `contracts` 声明的插件继续走 legacy `parse_type_property`,向后兼容。

### 13.3 Typed-lookup API

#### 13.3.1 resolve() 双路径

`FieldResolver::resolve` 改成:

```rust
pub fn resolve(&self, field_id: &str) -> Result<String, PluginError> {
    let normalized = normalize_for_permission(field_id)
        .ok_or_else(|| PluginError::InvalidField(...))?;
    if !self.is_allowed(&normalized) {
```

#### 13.3.2 resolve_typed 实现骨架

```rust
fn resolve_typed(&self, field_id: &str) -> Result<String, PluginError> {
    // 1. parse "address.street" → (contract_type_id, prop_path)
    //    type-id 前缀必须 equals manifest.contracts[i].type_id (允许 alias table)
    let parsed = parse_typed_field(field_id)?;            // Option<(ctid, prop_path)>
    let (ctid, prop_path) = parsed.ok_or_else(||
        PluginError::InvalidField("typed 路径不能解析".into()))?;

    // 2. 反向查 UserTemplate: list_user_templates, find t.contract_type_id == ctid
    let templates = vault.list_user_templates(account_id)?;
    let template = templates.into_iter()
        .find(|t| t.contract_type_id.as_deref() == Some(&ctid))
        .ok_or_else(|| PluginError::InvalidField(
            format!("未找到 contract_type_id={} 的用户类型", ctid)))?;

    // 3. 反向查 ObjectRecord: list_objects, filter o.contract_type_id == ctid
    let objects = vault.list_objects(account_id, Some(&template.id), None, None, false, false)?;
    if objects.is_empty() {
        return Ok(String::new());
    }
    let mut objects = objects;
    objects.sort_by(|a, b| a.created_at.cmp(&b.created_at));

    // 4. 取每个 object 的 properties[prop_path]
    //    注意:只在 contract_field = Some(true) 的 property 上读取;
    //    这里我们用 template.properties[].contract_field gate
    let prop_first = prop_path.split('.').next().unwrap_or("");
    let prop = template.properties.iter()
        .find(|p| p.id == prop_first)
        .ok_or_else(|| PluginError::InvalidField(
            format!("contract {} 没有属性 {}", ctid, prop_first)))?;
    if prop.contract_field != Some(true) {
        return Err(PluginError::InvalidField(
            format!("属性 {} 未声明为 contract_field (gate 拒绝)", prop_first)));
    }

    Ok(extract_property(&objects[0].properties, &prop_path))
}
```

#### 13.3.2.5 parse_typed_field alias bridge 算法 (双查)

`field_id` 是 short string,typed contract 是 `contract_type_id` (反向域名 + 主版本),两者需要桥。`parse_typed_field` 采用 **双查 (dual-lookup)** 预案。

**Field 拆分规则 (`parse_type_property`, 已落地于 `tauri/crates/solosoul-plugin/src/field.rs:307` 与 mirror `tauri/src-tauri/src/plugin/field.rs:307`)**:

| 输入 `field_id` | `type_id` (alias bridge key) | `prop_path` (返回值第二段) | 拆分 |
|---|---|---|---|
| `"address.street"` | `"address"` | `"street"` | 2 段 → 命中按常规 path |
| `"address.primary_passport.number"` | `"address"` | `"primary_passport.number"` | 3 段 → 嵌套 path 返回 “含 `.`” |
| `"address.count"` | (不走此函数) | — | `strip_suffix(".count")` 岔路,不在 typed-lookup 范围 |
| `"contact_exporter.full_name"` | `"contact_exporter"` | `"full_name"` | 单下划线型 — 拆点还是首个 `.` |

拆分语义 (确定):
- `field_id.split('.').collect::<Vec<_>>()` 拆分后 **取首个 `.`** (不是最后一个,也不是把所有点全拆);
- `type_id = parts[0]` 第一段 (后续作为 `UserTemplate.id` 反查 与 `manifest.contracts[*].type_id_aliases` 查表 key);
- `prop_path = parts[1..].join(".")` 剩余段 join 回去所以保留原嵌套 (例如 `primary_passport.number` 中的 `.` 不丢);
- `prop_path` **不是** `field_id` verbatim。这点是 §13.3.2.6 Usage 示例中 assert_eq! 必须匹配 的关键。

`parse_typed_field` 调用点 (line 714): `let (alias, prop_path) = parse_type_property(field_id).ok_or_else(...)?;` — 其中 `alias = type_id` 名参、与 `self.contracts[*].type_id_aliases` 的查表退耦。类型语义上:你向上写什么 alias,host 反查什么 alias;你以什么 prop_path 调用 `extract_property`,host 就以什么 prop_path 从 object.properties 里 dot-traverse。

```rust
/// 解析 field_id → (contract_type_id, prop_path)。双查路径:
///   1. PRIMARY: 按 UserTemplate.id 反查 -> 找到 contract_type_id.is_some() 的 t
///   2. SECONDARY: 按 manifest.contracts[*].type_id_aliases 反查
///   3. 都 miss -> None (交 caller 走 legacy / 报 InvalidField)
impl FieldResolver {
    /// 解析 field_id → typed contract lookup 结果 (双查)。
    ///
    /// 路径:
    ///   1. PRIMARY: 从 vault 拉 UserTemplate 列表,find t where t.id == alias AND t.contract_type_id.is_some()
    ///   2. SECONDARY: 从 self.contracts 找 c where c.type_id_aliases.contains(alias)
    ///   3. 都 miss → Ok(None) (交给 caller:legacy fallback / typed InvalidField)
    ///
    /// 注:`vault` 与 `account_id` 是 FieldResolver.enclosing 状态;self.contracts
    /// 由 PluginManager::run 在构造时从 `manifest.contracts` 装载 (mirror
    /// `allowed_patterns` 字段装载路径)。
    pub fn parse_typed_field(
        &self,
        field_id: &str,
    ) -> Result<Option<(String, String)>, PluginError> {
        // 复用现有 parse_type_property 拆 alias + prop_path
        let (alias, prop_path) = parse_type_property(field_id).ok_or_else(|| {
            PluginError::InvalidField(format!("不支持的字段路径: {}", field_id))
        })?;

        // PRIMARY: UserTemplate 反查 (user-space 真实 anchor)
        if let (Some(vault), Some(account_id)) = (self.vault.as_ref(), self.account_id.as_ref()) {
            let templates = vault
                .list_user_templates(account_id)
                .map_err(|e| PluginError::ExecutionFailed(format!("读取模板失败: {}", e)))?;
            if let Some(t) = templates
                .iter()
                .find(|t| t.id == alias && t.contract_type_id.is_some())
            {
                return Ok(Some((t.contract_type_id.clone().unwrap(), prop_path)));
            }
        }

        // SECONDARY: manifest contracts aliases 反查
        if let Some(c) = self
            .contracts
            .iter()
            .find(|c| c.type_id_aliases.iter().any(|a| a == &alias))
        {
            return Ok(Some((c.type_id.clone(), prop_path)));
        }

        Ok(None)
    }
}
```

两个预案产生的设计意义:
- **PRIMARY（主路径）**：基于用户空间的实际模板进行校验。当用户从 SampleTemplate 创建 UserTemplate 时已写入 `contract_type_id`，宿主可反向查找到对应的 typed entity。这一步为 §13.7 中的 Stage 4-A 桥接提供了确切的入口。
- **SECONDARY（副路径）**：依赖 Manifest 中显式声明的别名表（`type_id_aliases`）。允许将传统的字符串前缀（如 `"address"`）作为 typed 入口，避免强制改造所有现有 Wasm 插件中的 'address.street' 等字符串。
- **`contracts` 字段的装载路径**与 `allowed_patterns` 同构：由 `PluginManager::run` 在构造时复制 `manifest.contracts` → `SolHostFunctions` 宿主状态 → `FieldResolver.contracts`。这使得 `parse_typed_field` 能作为 `&self` 方法而非自由函数，避免每个调用方重复维护两组集合。
- **分发规则**：`parse_typed_field` 的调用方不需要显式指定走 PRIMARY 还是 SECONDARY，命中哪个返回哪个。`vault == None`（测试模式）仍可走 SECONDARY fallback，调用方最终决定：legacy fallback / typed InvalidField / 放弃。（详见 §13.3.2.6）

#### 13.3.2.6 FieldResolver 字段扩 + 构造注入路径(Stage 4-B 实现规约)

> **前置条件**：`PluginManifest.contracts` 字段（§13.2.2 Stage 4-A）已落地。否则 `manifest.contracts` 不存在 → 编译失败。**Stage 4-B 必须在 Stage 4-A 完成后才能启动**。

注入路径：Stage 4-B 需补两个 constructor 帮助 `PluginManager::run` (manager.rs:225-263) 当前调用点走了 `with_vault`。两条等价路径供实现者选择：

```rust
impl FieldResolver {
```

Usage 示例 (测试 SECONDARY alias 路径,vault==None):

```rust
let ab = PluginContractBinding {
    type_id: "com.solosoul.address/v1".to_string(),
    type_id_aliases: vec!["address".to_string()],
    strict_contract_gate: false,
```

#### 13.3.3 验证 contract_field gate 的 4 个 scenario

### 13.4 field_metadata 与 consent 对齐

`host.rs::solosoul_field_metadata` 当前走 `parse_indexed_field` / `parse_type_property` + `t.id == type_id`。

Stage 4 同步改造:
- typed 路径:`templates.find(|t| t.contract_type_id == Some(ctid))` 反向定位 + `prop.contract_field == Some(true)` gate + 返回 `(label, sensitivity)`。
- legacy 路径:保留现状,不破坏既有兼容模板 + 用户定义类型。

`solosoul_request_consent` (host.rs:466-540) 当前走 `field_metadata` + 用 field_id 字符串。Stage 4 后,typed 插件发出来的 consent request 会带"已被 contract 校验"的元数据,UI 可在 confirm 弹窗里加一行"此字段由插件 `com.solosoul.official.address-fmt` 通过 typed-lookup 访问,字段名:省份"(取得 `sensitivity_level` 自动对应 masking tier)。

#### Stage 4-D — 废弃 legacy 路径（P3）

### 13.10 实现注意事项与已知陷阱

#### 13.10.1 代码重复：两份镜像的同步要求

`tauri/crates/solosoul-plugin/src/field.rs` 与 `tauri/src-tauri/src/plugin/field.rs` 内容几乎逐行一致。`manager.rs` 同样是两份镜像。Stage 4 的每个改造步骤都必须在两边同步执行，否则会出现行为不一致。

**强制检查项**：每个 Stage 4 子阶段完成后，必须在以下两个文件中确认改动一致：

- `tauri/crates/solosoul-plugin/src/` ↔ `tauri/src-tauri/src/plugin/`
- 所有 `PluginManifest { ... }` 字面量构造点（含测试夹具）

建议长期方向：将 Tauri 目录下的 plugin 模块改为直接复用 `solosoul-plugin` crate，从根本上消除维护负担。

#### 13.10.2 保留 required_fields 原始字段

当前 `MarketManifestRaw` 将 `required_fields` 与 `optional_fields` 合并后存入 `PluginManifest.permissions`，原始区分信息已丢失。按 §6.3 实现兼容性检测算法时，将无法区分必需字段与可选字段，也无法精确解析契约类型。

**要求**：在 `PluginManifest` / `MarketManifestRaw` 中保留 `required_fields` 和 `optional_fields` 原始字段，仅在 `permissions` 中合并用于权限匹配。

#### 13.10.3 老数据 backfill 与对象创建时继承 contract_type_id

**问题**：v17 migration 只增加了数据库列，未回填已有数据。老用户已创建的对象和模板中 `contract_type_id` 均为 `None`。即使后续发布插件兼容模板，老数据也无法走 typed-lookup 路径。

**要求**：

1. **Backfill 脚本**：在 Stage 4-A 或 Stage 4-B 中增加一次性 backfill 逻辑，根据 `UserTemplate.id` 与已知系统模板 key 的映射关系回填 `contract_type_id`。
2. **对象创建继承**：在 `object_create` / `object_update` 中，若 `template_id` 指向的 UserTemplate 带有 `contract_type_id`，自动将该值复制到 `ObjectRecord.contract_type_id`（当前代码写死为 `None`）。

#### 13.10.4 Typed-lookup 第一阶段仅覆盖单对象读取

当前 `resolve_typed`（§13.3.2）在找到所有匹配对象后只取 `objects[0]`，这与 legacy 行为一致。但地址格式化器等插件实际需要读取多条记录（如测试中"发现 2 条地址"的断言）。

**说明**：typed-lookup 第一阶段（Stage 4-B）仅覆盖"单对象便捷读取"场景。多对象读取将通过新的宿主函数（如 `list_objects_by_contract`）在 Stage 5 中扩展支持。

#### 13.10.5 别名冲突校验

`PluginContractBinding.type_id_aliases` 允许多个插件声明相同的别名（如 `["address"]`），若指向不同的 `contract_type_id`，`parse_typed_field` 的 SECONDARY 路径会命中第一个匹配项，产生不可预期的行为。

**要求**：在插件安装时校验别名冲突。若多个插件声明相同 alias 但指向不同 `contract_type_id`，应拒绝安装并提示冲突。或者限制 alias 仅在 PRIMARY 路径未命中时才生效，并在命中时给出 warning。

#### 13.10.6 Slotgo 长期策略

`slotgo` 作为跨多 type_id 的通用插件，被规划为 LEGACY-1（保留 1.0 不升级）。若未来 v3.0 起默认关闭 legacy 路径，该插件将直接失效。

**策略**：slotgo 的长期方案有两种选择：

- **永久例外**：为 slotgo 保留一个永久 legacy whitelist 入口，即使全局关闭 legacy 也允许加载。
- **独立 shim**：为 slotgo 单独维护一个轻量 typed-lookup shim，使其在 typed 模式下仍能工作。

决策留到 Stage 5 讨论。

#### 13.10.7 PluginManifest.contracts 与 Rust 代码注释中残留 Phase 引用

Stage 4-A 在 `PluginManifest` 中新增 `contracts` 字段后，所有现有 `PluginManifest { ... }` 字面量构造点必须补齐 `contracts: vec![]` / `field_bindings: vec![]`，否则编译失败。涉及文件已在 §13.2.3 中列出。

同时注意：Rust 代码中若干注释（如 `field.rs` 中的 `// Phase A: typed lookup`）在实现 Stage 4-B 时应统一改为 `// Stage 4-B: typed lookup`，避免后续维护者困惑。

#### 13.10.8 RegistryEntry / generate_registry.py 转发契约字段

当前 `RegistryEntry` 不包含 `contracts` / `field_bindings` 字段。Stage 4-A 必须同步更新：

- `RegistryEntry` struct 增加 `#[serde(default)] contracts/field_bindings`；
- `SoloSoul_plugin_market/scripts/generate_registry.py` 在生成注册表时同步输出契约信息。

否则前端无法在插件市场卡片上展示 typed-lookup 兼容状态。

### 13.8 与现地文档去重说明

- §6.1 提出的 `SampleTemplate.contractFields` / `compatiblePluginIds` 是前端层面的 SampleTemplate 概念，与本节的 `PluginContractBinding` 属于两层设计（SampleTemplate 提供 UI 选择入口，manifest 是插件实际的契约断言）。二者不互替：
  - **SampleTemplate 层**：用户选择 SampleTemplate 并生成 UserTemplate 时，将 `contract_type_id` 和 `contract_field` 写入 UserTemplate。
  - **PluginManifest 层**：manifest 声明 `contracts: [typeId]` 是宿主调用时所依据的 contract_type_id。
- §6.3 算法:以 `manifest.required_fields` 提取 `(type_id, field_id)` 仍适用于 **PluginManifest 没声明 contracts** 的 fallback 路径。Stage 4 仅在 contracts 存在时反向走 schema 字段。
- §6.4 编辑器守卫（删除字段时的警告弹窗）保留不变 — contract_field gate 仅是宿主层调度逻辑，不介入 UI 编辑器。

### 13.9 Stage 4 不做的事 (non-scope)

- ❌ 不 process plugins 需要 Tauri re-compile (ABI 1.0 → 1.1 插件仍然可运行)。
- ⚠ `solosoul_cli` 受 Stage 4-A struct 增量间接影响（但不在 typed-lookup 宿主路径）：`solosoul_cli/src/commands/plugin.rs` 只使用 `solosoul-plugin` crate 的 install/uninstall/registry API，**不调用 `FieldResolver::resolve`**、不执行 wasm，故 typed-lookup 不是 CLI 的宿主问题。但 Stage 4-A 在 `PluginManifest` / `MarketManifestRaw` / `RegistryEntry` 增加 `#[serde(default)] contracts/field_bindings` 后，CLI 反序列化 manifest 时会静默接受新字段，仍需 `cargo test --package solosoul_cli` 一并运行（Stage 4-A 验证必需项），以防后续逻辑边界问题。
- ❌ 不改变 Wasm-only call signature (host function favors `*(ptr,len) -> i32` 不变)。
- ❌ 不加 schema bump (v18, v19 …):v17 migration 完成时 contract 字段已存在,Stage 4 不需 v18。
- ❌ 不重写 search `/` list_objects:ObjectSummary ✅ 与 contract_type_id 合 path 已 Stage 2 上粉。
- ❌ 不修改 sync:plugin 路径与 sync 脱钩 (`sync.rs` 中 contract_type_id 已 roundtrip但 sync 并不以此路由)。
