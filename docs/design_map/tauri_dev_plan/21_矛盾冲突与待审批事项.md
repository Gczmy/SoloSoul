# 21 — 矛盾冲突与待审批事项

> **目的**：本文档汇集 Tauri 重构计划中与 Manifesto 理念存在矛盾的设计决策。
> **处理原则**：**不在此文档中直接解决矛盾**，仅记录矛盾点、原因和可选方案，供团队审批。

## 冲突 1：敏感度等级数量（6 级 vs 4 级）

### 矛盾点

| 文档 | 等级数量 | 定义 |
|------|---------|------|
| `02_设计哲学.md`（Manifesto） | **6 级** | public / internal / private / sensitive / restricted / critical |
| 现有代码（`sensitivity_enums.dart`） | **4 级** | public / internal / sensitive / critical |
| Tauri 重构所有文档 | **4 级** | 同现有代码 |

### 原因

- 6 级方案中 `internal` 与 `private` 的差异过于细微（都是"模糊显示"），`sensitive` 与 `restricted` 的差异也过于细微（都是"完全遮盖 + 验证"）
- 现有代码、测试、插件系统均基于 4 级实现
- 迁移到 6 级改动巨大且收益有限
- 4 级已覆盖所有安全场景

### 可选方案

| 方案 | 说明 | 影响 |
|------|------|------|
| A | 统一为 4 级，更新 `02_设计哲学.md` | Manifesto 需要修订 |
| B | 保持 Manifesto 6 级，迁移全部代码到 6 级 | 巨大工作量，所有代码/测试/插件需改动 |
| C | 保留 Manifesto 6 级作为"设计愿景"，当前实现先用 4 级 | 代码与文档不一致，技术债务 |

### 审批决策（2026-06-05）：**已批准 — 统一为 4 级**

**后续行动**：修订 `02_设计哲学.md` 中的敏感度分级描述（6 级 → 4 级），所有 Tauri 重构代码使用 4 级。

## 冲突 2：AI/LLM 功能与本地优先原则

### 矛盾点

| Manifesto 原则 | 实现计划 |
|---------------|---------|
| "AI 功能（如有）必须运行在本地" | LLM 集成支持任意 OpenAI 兼容 API（详见文档 26） |
| "绝不上传原始数据" | AI 对话功能需要发送用户输入到外部 API |

### 原因

- 本地 LLM（Ollama）质量尚不及云端模型，用户体验差距大
- 用户有真实需求使用 AI 辅助数据管理（智能填充、自然语言搜索）
- 设计上已做安全措施：用户自选 Provider、API 密钥本地加密存储、用户控制发送哪些字段

### 技术缓解措施（已设计）

1. AI 绝不直接写入 Vault（只生成建议，用户确认后才执行）
2. 审计日志记录每次 AI 调用（不记录用户输入内容）
3. API 密钥从 Vault 加密读取，使用后内存擦除
4. 用户可选择纯本地模型（Ollama）或拒绝使用 AI 功能

### 可选方案

| 方案 | 说明 |
|------|------|
| A | 只支持本地模型（Ollama），不接入任何云端 API |
| B | 支持云端 API 但默认禁用，用户需主动开启并确认风险 |
| C | 完全移除 AI 功能，符合"本地优先"的严格解释 |

**审批决策（2026-06-05）：已批准 — 方案 B（默认禁用 + 风险告知）**

**后续行动**：LLM 功能默认禁用，首次开启时展示风险告知对话框，AI 对话历史加密存储。

## 冲突 3：设备同步备份节点与数据仅存本地

### 矛盾点

| Manifesto 原则 | 实现计划 |
|---------------|---------|
| "数据只存在于你的设备上" | 同步路线图 Phase 3 引入备份节点（用户自建） |
| "同步发生在你的设备之间，不经过第三方服务器" | 备份节点可作为中继，数据加密后存储于用户 VPS/NAS |

### 原因

- "闭盖笔记本问题"：设备关闭时无法同步，备份节点解决此问题
- Any-Sync 协议设计：备份节点存储的是**加密的 change**，节点本身无法解密
- 备份节点是**可选**的，非强制

### 技术缓解措施

1. 备份节点只能看到加密后的数据（E2EE）
2. 用户自己运行节点（VPS/NAS），非 SoloSoul 运营
3. 用户选择不使用备份节点时，仅局域网 P2P 同步

### 可选方案

| 方案 | 说明 |
|------|------|
| A | 不支持任何中继节点，仅局域网 P2P 同步 |
| B | 支持用户自建备份节点，加密数据，用户完全控制 |
| C | SoloSoul 运营中继节点（违背 Manifesto，不推荐） |

**审批决策（2026-06-05）：已批准 — 方案 B（用户自建 + E2EE）**

**后续行动**：同步 Phase 3 中实现可选的备份节点协议，节点仅存储加密 change。

## 冲突 4：术语重命名（Object vs UnifiedObject、集合 vs 分区）

### 矛盾点

| 现有代码/文档 | 提议的新术语 |
|-------------|------------|
| `UnifiedObject` | `Object` |
| "分区" (Collection) | "集合" |
| "字段" (Field) | "属性" (Property) |

### 原因

- 与 Anytype 等成熟产品的术语对齐，降低新用户学习成本
- `UnifiedObject` 名称过长且冗余（SoloSoul 中所有对象都是 unified 的）
- "分区"歧义大（磁盘分区？地理分区？）
- 重构阶段是唯一可以统一术语的窗口期

### 影响范围

- Rust 代码：结构体重命名、数据库表重命名
- TypeScript 代码：接口重命名
- IPC 命令：`unified_object_*` → `object_*`
- UI 文案：全文替换
- 数据库迁移：`unified_objects` 表 → `objects` 表

### 可选方案

| 方案 | 说明 |
|------|------|
| A | 立即重命名（重构阶段统一） |
| B | 保持现有命名，仅文档统一 |
| C | 渐进迁移（先代码后 UI） |

**审批决策（2026-06-05）：已批准 — 方案 A（重构阶段统一重命名）**

**后续行动**：`UnifiedObject` → `Object`、`PropertyDefinition` → `Property`、UI "分区" → "集合"、IPC 命令 `unified_object_*` → `object_*`。

## 冲突 5：明文导出选项与"导出必须加密"

### 矛盾点

| Manifesto 原则 | 实现计划 |
|---------------|---------|
| "导出必须加密，不可关闭" | 导入导出设计提供明文 JSON 导出选项（需要用户明确确认风险） |

### 原因

- 互操作性需求：用户可能需要将数据导入不支持 `.solosoul` 格式的工具
- 用户主权：用户应有权决定以何种格式导出自己的数据
- 已有充分的风险告知机制

### 技术缓解措施

1. 明文导出前显示高风险警告对话框
2. 要求密码重新验证
3. 明文导出操作记录到审计日志（标注 "明文导出"）
4. 文件权限设置为仅所有者可读写（`chmod 600`）

### 可选方案

| 方案 | 说明 |
|------|------|
| A | 严格遵循 Manifesto：完全禁止明文导出 |
| B | 允许明文导出但需三重确认（风险警告 + 密码 + 审计） |
| C | 明文 JSON 也使用弱加密（密码保护 ZIP） |

**审批决策（2026-06-05）：已批准 — 方案 B（允许但需三重确认）**

**后续行动**：明文 JSON 导出需要风险警告对话框 → 密码重新验证 → 审计日志记录，导出文件自动 `chmod 600`。

## 冲突 6：外部产品设计借鉴与"反模板政策"

### 矛盾点

| 来源 | 矛盾 |
|------|------|
| Web 设计质量规则（用户全局 rules） | "禁止默认卡片网格、禁止安全灰白配色" |
| 外部产品借鉴（Notion/Anytype/Warp） | 可能引入与这些产品过于相似的 UI 模式 |

### 原因

- 效率与原创性的权衡：借鉴成熟设计 vs 保持独特性
- 借鉴的是**理念**（对象模型、命令面板、材质系统）而非**像素级复制**
- SoloSoul 有自己的差异化：敏感度分级遮罩、加密状态指示器、本地优先交互

### 缓解措施

1. 每个借鉴的设计必须有 SoloSoul 特有的差异化
2. 不直接复制任何产品的配色/排版/组件样式
3. Liquid Glass 材质系统是跨平台原创设计

### 状态：**信息记录**（非矛盾，但需在设计中保持警惕）
