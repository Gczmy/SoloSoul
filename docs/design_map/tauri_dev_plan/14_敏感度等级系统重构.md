## 1. 问题诊断：当前设计的安全漏洞

```
用户想查看 critical 字段（如护照号码）
  → 系统要求密码验证 → 用户不知道密码
    → 进入 设置 → 敏感度设置
      → 将 "护照号码" 从 critical 降级为 public
        → 无需密码即可查看 ← 安全漏洞！
```

**根本原因**：保护数据访问的机制（敏感度等级）本身**没有被保护**。

---

## 2. 核心设计原则

### 2.1 唯一真理来源（Single Source of Truth）

```
[错误] 字段实例自己定义敏感度（数据与策略耦合）
[错误] 代码默认 + 用户覆盖 + 字段实例 三份来源
[正确] SensitivityMap：一份加密的映射表，运行时统一查询
```

### 2.2 修改即访问（Modify = Access）

- 将 `critical` 降级为 `public` → 等同于"我现在要看这个 critical 字段"
- **降级操作需要等同于查看该级别数据的验证强度**

### 2.3 敏感度等级：统一 4 级（已批准）

> **审批决策（2026-06-05）**：全团队统一采用 4 级敏感度方案，修订 `02_设计哲学.md` 中的 6 级描述。

| 级别 | 视觉 | 验证要求 |
|------|------|---------|
| `public` | `IconSensitivityPublic`（空心圆环，暖绿色描边）始终可见 | 无 |
| `internal` | `IconSensitivityInternal`（单点圆点，蓝灰色填充）blur(2px)，点击展开 | 无 |
| `sensitive` | `IconSensitivitySensitive`（实心圆点，琥珀色填充）blur(8px) + 蒙层 | 生物识别/密码 |
| `critical` | `IconSensitivityCritical`（锁形图标，深红色填充）blur(16px) + 锁图标 | 密码 + 操作确认 |

> 早期设计文档曾用 6 级（含 `private`/`restricted`），已统一为 4 级。旧 6 级中的 `private` 归入 `internal`，`restricted` 归入 `sensitive`。

## 3. SensitivityMap 架构

### 3.1 数据结构

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct SensitivityMap {
    pub version: u8,
    pub entries: HashMap<String, SensitivityLevel>, // field_id → level
    pub last_modified_at: DateTime<Utc>,
}

impl SensitivityMap {
    pub fn get(&self, field_id: &str) -> SensitivityLevel {
        self.entries.get(field_id).copied().unwrap_or(SensitivityLevel::Public)
    }

    pub fn set(&mut self, field_id: &str, level: SensitivityLevel) {
        self.entries.insert(field_id.to_string(), level);
        self.last_modified_at = Utc::now();
    }
}
```

### 3.2 存储位置

```
~/.solosoul/{account_id}/
├── sensitivity_map.enc    # 加密：字段级敏感度映射表（唯一真理来源）
└── sensitivity_log.enc    # 加密：变更历史（不可删除）
```

### 3.3 废弃字段实例中的 sensitivity

```dart
// 重构前 [错误]
class TextProperty {
  final String text;
  final SensitivityLevel sensitivity;  // 废弃
}

// 重构后 [正确]

  final String text;
  // sensitivity 移除 —— 运行时从 SensitivityMap 查询
}
```

## 4. 分级验证规则

| 操作 | 需要的验证 | 理由 |
|------|-----------|------|
| `critical` → `sensitive` 降级 | **密码重新验证** | 等同于访问 critical 数据 |
| `critical` → `public` 降级 | **密码 + 降级确认** | 永久解除 critical 保护 |
| `sensitive` → `public` 降级 | **密码重新验证** | 等同于访问 sensitive 数据 |
| `internal` → `public` 降级 | 无需额外验证 | 无安全风险 |
| `public` → `critical` 升级 | 升级确认对话框 | 加强保护（无需密码） |

**核心规则**：降级 = 访问（需密码），升级 = 安全（无需密码）

## 5. 冷却期机制

```rust
const DOWNGRADE_COOLDOWN_SECONDS: u64 = 300; // 5 分钟

/// 同一字段在 5 分钟内不能再次降级（防止暴力绕过）
fn check_downgrade_cooldown(
    log: &SensitivityLog,
    field_id: &str,
    new_level: SensitivityLevel,
    old_level: SensitivityLevel,
) -> Result<(), SensitivityError> {
    if old_level <= new_level { return Ok(()); } // 升级无需冷却

    if let Some(last) = log.entries.iter().rev()
        .find(|e| e.field_id == field_id && e.old_level > e.new_level)
    {
        let elapsed = Utc::now() - last.timestamp;
        if elapsed.num_seconds() < DOWNGRADE_COOLDOWN_SECONDS as i64 {
            return Err(SensitivityError::DowngradeCooldown { ... });
        }
    }
    Ok(())
}
```

## 6. 修改权限的严格边界

```
[正确] 用户本人（通过密码验证后）
   → 敏感度管理页面 → 输入密码 → 修改 SensitivityMap

[错误] 插件 → 只能读取敏感度（用于 Consent 判断），无权修改
[错误] 前端 UI 组件 → 只读 SensitivityMap，无写入权
[错误] 同步引擎 → 只传输副本，不触发修改（冲突时本地优先）
[错误] 导入流程 → 用户需确认后才覆盖，不自动静默覆盖
```

## 7. 临时揭示 ≠ 修改敏感度

临时揭示是**纯前端 UI 状态**，与 SensitivityMap 完全隔离：

```typescript
// 仅前端内存，不持久化，不写入 Vault
interface RevealState {
  revealedFields: Set<string>;        // 当前揭示的字段
  expiresAt: Map<string, number>;     // TTL 1 分钟
}

function shouldMask(fieldId: string): boolean {
  const realLevel = sensitivityMap.get(fieldId);    // 来自 Vault
  if (revealState.revealedFields.has(fieldId)       // 临时揭示
      && Date.now() < revealState.expiresAt.get(fieldId)!) {
    return false; // 揭示中，不遮盖
  }
  return realLevel === 'sensitive' || realLevel === 'critical';
}
```
