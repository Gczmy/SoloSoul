# 导入导出功能：文档规范不合理性分析报告

> **分析日期**：2026-06-08
> **分析视角**：以工程实践、用户体验、API 设计合理性为出发点，审视文档中不切实际、过于僵化或与安全/效率原则相矛盾的条款
> **核心观点**：文档 ≠ 圣经。当代码实现与文档不一致时，存在大量代码优于文档的案例，应通过修订文档来承认这些更好的工程决策。

---

## 一、文档存在明显安全/体验缺陷，代码实现更优的案例

### 1. P0 导入"全量覆盖当前账户数据"——灾难性的默认策略

**文档原文**（§4 P0 导入流程第③步）：
> ③ 确认导入（**全量覆盖当前账户数据**）

**代码实际行为**：
`import_execute` 默认使用 `ImportStrategy::SkipExisting`，即**跳过已有对象**，而非覆盖。

**为什么文档不合理**：
- **意外覆盖风险极高**：用户导入一个旧备份，默认行为不应该是抹掉现有数据。这是数据丢失的单向门。
- **不符合用户心智模型**："导入"通常意味着"补充/合并"，而非"删除并替换"。以覆盖为默认策略的产品（如 iCloud 恢复）都需要极强的上下文暗示（如"从此备份恢复"），而 SoloSoul 的导入场景是"迁移数据"。
- **没有撤销机制**：文档将"导入前自动静默备份"定为"未来"功能。在没有撤销机制时，覆盖默认策略是危险的。

**代码为什么更好**：
- `SkipExisting` 是**防御性默认**（defensive default）：最坏情况是"没导入某些对象"，而不是"丢失了现有对象"。前者可修复，后者不可逆。
- P2 的策略选择器（SkipExisting / Overwrite / Merge）已在前端实现，将选择权交给用户，而非替用户做覆盖决定。

**建议**：文档应将 P0 导入重新定义为**"增量导入（跳过已有对象）"**，将"全量覆盖"降级为 P2 策略选项之一。

### 2. IPC 命令使用扁平参数——违背 Tauri 工程最佳实践

**文档定义**（§5 IPC 命令）：
```rust
pub async fn export_execute(
    scope: ExportScope,
    password: String,
    password_hint: Option<String>,
    save_path: String,
) -> Result<String, String>;
```

**代码实际签名**：
```rust
pub async fn export_execute(
    state: State<'_, AppState>,
    account_id: String,
    req: ExportRequest,  // 打包 struct
) -> Result<String, String>;
```

**为什么文档不合理**：
- **扩展性灾难**：扁平参数在新增字段时必然破坏 API 签名。例如 P1 加入 `password_hint`、P2 加入 `export_format` 时，所有调用方都需要修改参数列表。
- **参数顺序易错**：4 个以上的同类型参数（如两个 `String`）极易在调用时顺序写错，编译器无法捕获。
- **与 Tauri 前端调用风格冲突**：前端通过 JSON 对象调用 IPC，扁平参数需要展开为多个顶层字段，而打包参数天然对应一个 JSON 对象。

**代码为什么更好**：
- `ExportRequest` / `AdvancedImportRequest` 打包参数支持**向后兼容扩展**：新增可选字段不会影响现有调用方。
- 与 TypeScript 前端类型天然对应，减少序列化/反序列化的心智负担。
- 这是 Tauri 社区和 Rust 社区的公认最佳实践。

**建议**：文档应全面采用 struct 打包参数风格，并承认扁平参数定义是设计失误。

### 3. 要求导入通过 `object_create` 接口——会破坏对象 ID 一致性

**文档要求**（§8 完成标准）：
> `import_execute` 解密 payload → **通过 object_create 导入**

**代码实际行为**：
直接调用 `vault.save_object(&record)`（`INSERT ... ON CONFLICT(id) DO UPDATE`）。

**为什么文档不合理**：
- **`object_create` 强制生成新 UUID**：查看 `commands/object.rs:134`：`let id = Uuid::new_v4().to_string();`。如果导入流程走 `object_create`，所有对象都会获得**全新的随机 ID**。
- **关联关系断裂**：导入的对象如果包含 `parent_id`、`children_ids` 或 `RelationProperty`，这些引用都基于原始 ID。ID 被重新生成后，所有关联关系会变成**悬空引用**。
- **与导出闭环矛盾**：用户在同一账户导出再导入，预期是"恢复数据"，而不是"创建一批全新对象"。

**代码为什么更好**：
- `save_object` 使用 `ON CONFLICT(id) DO UPDATE`，可以**保留原始 ID**，同时支持"已存在则覆盖、不存在则插入"。
- 这是数据迁移场景下的标准做法（如 `pg_restore` 的 `--clean` / `--data-only` 模式都保留原主键）。
- 只有在"跨账户迁移"时才可能需要重新生成 ID，但这不在 P0 范围内。

**建议**：文档应删除"通过 object_create 导入"的要求，改为"通过 `save_object` 或等效的 UPSERT 操作导入，保留原始对象 ID"。

---

### 4. `import_execute` 返回 `bool`——信息密度过低

**文档定义**：`Result<bool, String>`
**代码实际返回**：`Result<usize, String>`（实际导入的对象数量）

**为什么文档不合理**：
- `bool` 只能表达"成功/失败"，但用户需要知道"导入了多少条"。特别是在 SkipExisting 策略下，用户非常关心"有多少是新导入的，有多少是跳过的"。
- 前端无法基于 `bool` 给出有意义的成功提示（"导入成功！" vs "导入成功！共导入 15 个对象"）。

**代码为什么更好**：
- `usize` 提供了可操作的反馈，前端可以直接使用这个值做 i18n 提示：`t('settings:import_success', { count })`。

**建议**：文档应接受 `usize` 作为标准返回值。

---

### 5. `PageGroup` 接口缺少 `objectCount`——迫使前端做冗余计算

**文档定义**：
```typescript
interface PageGroup {
  sectionType: string;
  pageName: string;
  objects: ObjectSummary[];
}
```

**代码实际**：Rust 和前端都增加了 `objectCount: number`。

**为什么文档不合理**：
- 前端在渲染页面组标题时，需要显示对象数量（如 "Travel (3)"）。如果接口不提供 `objectCount`，前端必须遍历 `objects` 数组计算 `length`。
- 当 `objects` 数组因分页或懒加载被截断时，`objects.length` 不等于实际总数，导致显示错误。

**代码为什么更好**：
- `objectCount` 由后端从数据库统计返回，不受前端分页影响，数据更准确。
- 减少前端计算负担，符合"后端做计算、前端做展示"的分工原则。

**建议**：文档应正式纳入 `objectCount` 字段。

## 二、文档过于保守/僵化，代码实现更务实的案例

### 6. 标签筛选导出定为 P2——后端已就绪，不应人为延迟

**文档定位**：标签筛选（`selected_tags`）= **P2（增强）**

**代码实际**：
- 后端 `ExportScope` 已包含 `selected_tags` 字段
- `collect_scope_objects` 已实现标签交集过滤逻辑
- 前端 `ExportImportPage.tsx` 中虽然始终传 `[]`，但 API 契约已完整

**为什么文档不合理**：
- 后端实现成本已经支付，接口已经存在。将其标为 P2 导致前端完全不做该功能，造成**已实现的后端能力闲置**。
- 标签筛选是对象级导出的自然延伸（"只导出标签为 `2025日本` 的旅行记录"），用户体验增益高，实现成本低。

**建议**：将标签筛选降级为 **P1**，前端补充一个标签多选组件即可闭环。

### 7. 附件导出严格绑定"附件模块就绪"——代码的临时方案提供了即时价值

**文档说明**（§2 导出包格式 & §7 关键决策）：
> 附件支持依赖附件存储模块就绪，在附件系统未完成前，导入导出不处理附件。

**代码实际**：
已实现了基于 `properties["__attachments"]` 的附件读取、打包、解压和恢复逻辑，且包含三层路径回退（`vault_path` → `src_path` → `base_dir`）。

**为什么文档不合理**：
- "附件模块就绪"是一个模糊的时间点，可能导致该功能无限期延迟。
- 代码实现的方案虽然依赖 properties 中的附件元数据（非正式接口），但在当前数据模型下**可以工作**。
- 工程上，提供"能工作但未来可能重构"的功能，比"等待完美方案"更有价值。

**代码为什么更好**：
- 用户现在就能备份带附件的数据，而不是等待一个不确定的里程碑。
- 即使未来附件系统重构，导出包格式的 `attachments/` 目录结构可以保留，只需替换元数据读取逻辑。

**建议**：文档应承认当前的临时实现方案，并将附件导出调整为 **P1（基于现有 properties 实现）**，未来附件系统重构时再迁移到正式接口。

### 8. Manifest 定义过于封闭——代码的扩展字段是合理演进

**文档定义**（§2 manifest.json 完整定义）：
```json
{
  "version": "2.0",
  "export_scope": "partial",
  "selected_pages": [...],
  "selected_objects": [...],
  "export_time": "...",
  "export_platform": "...",
  "export_app_version": "...",
  "has_attachments": false,
  "extra_files": []
}
```

**代码实际**：额外增加了 `has_preferences`（bool）、`password_hint`（string）、`salt_hex`（string）、`object_count`（number）等字段。

**为什么文档不合理**：
- manifest 是导出包的**自描述元数据**，其本质就是应该随着功能演进不断丰富。
- 将 manifest 字段严格限定在一个封闭集合中，会阻碍合理的向后兼容扩展。
- `has_preferences` 比检查 `extra_files` 数组是否包含 `"preferences.enc"` 更直观、更高效。
- `salt_hex` 是解密必需的，文档的 manifest 示例中居然**没有定义 `salt_hex`**，这本身就是一个遗漏。

**代码为什么更好**：
- `salt_hex` 是 P0 功能正确运行的必要字段，代码补充了文档的遗漏。
- `has_preferences` 提供了更高效的元数据读取路径。

**建议**：文档应将 manifest 定义为"最小必需字段 + 允许向后兼容扩展"的开放结构，而非封闭枚举。同时补上 `salt_hex` 的定义。

## 三、文档缺失导致代码不得不做"不好决定"的案例

### 9. 偏好数据导出：文档未定义密钥派生方案，代码选择了不安全实现

**文档要求**（§2 未来扩展版）：
> 当需要支持 preferences 时，在 ZIP 中新增对应加密文件 `preferences.enc`

**代码实际**：
```rust
let prefs_key = derive_export_key(&format!("{}_prefs_salt", password), &salt)?;
```

**文档的问题**：
- 文档只说了"加密存储 preferences"，但**完全没有定义密钥如何派生**。
- 实现者被迫自行设计派生方案，结果选择了"密码拼接字符串后重新走 KDF"这种**非标准做法**。

**为什么这个代码方案不好（但情有可原）**：
- `format!("{}_prefs_salt", password)` 不是标准的密钥分离方案（如 HKDF）。
- 如果主 payload 的密钥泄露，攻击者可能通过已知的拼接模式推导出 preferences 密钥。
- 这不是代码的错，是**文档没有给出标准**，实现者只能自行决定。

**建议**：文档应明确定义偏好数据的密钥派生方案，例如：
> `preferences.enc` 的密钥通过 HKDF-SHA256 从主导出密钥派生，info = "solosoul:preferences:v1"。

## 六、对文档修订的具体建议

### 应修改的文档条款（承认代码更优）

1. **§4 P0 导入流程**：将第③步从"全量覆盖"改为"跳过已有对象（增量导入）"。
2. **§5 IPC 命令**：将所有扁平参数改为 struct 打包参数（`ExportRequest`、`AdvancedImportRequest`）。
3. **§8 完成标准**：删除"通过 object_create 导入"，改为"通过 UPSERT 操作导入，保留原始对象 ID"。
4. **类型定义**：`import_execute` 返回 `usize`，`PageGroup` 增加 `objectCount`。
5. **§2 Manifest**：定义为开放结构，明确允许向后兼容扩展；补上 `salt_hex`、`password_hint`、`has_preferences`。
6. **§3 偏好数据导出**：明确定义 HKDF 密钥派生方案。
7. **优先级调整**：标签筛选降为 P1，附件导出（基于当前 properties 方案）降为 P1。

### 应坚持的文档条款（代码需要补齐）

1. **导出密码≠主密码校验**：代码应立即补上。
2. **RelationProperty 降级处理**：代码应在导入流程中实现。
3. **密钥派生标准方案**：代码应替换 `"{}_prefs_salt"` 为 HKDF。
