# 导入导出功能：实现与文档规范差距分析报告

> **分析日期**：2026-06-08
> **分析范围**：`tauri/src-tauri/src/commands/export_import.rs` + `tauri/src/pages/settings/ExportImportPage.tsx` + `tauri/src-tauri/src/lib.rs`
> **对照文档**：`docs/design_map/tauri_dev_plan/17_导入导出功能设计.md`（v3.0，2026-06-07）
> **优先级说明**：差距按 P0（必须）/ P1（重要）/ P2（增强）/ 其他 分类

---

## 一、P0 级差距（必须修复，影响核心功能正确性）

### 1.1 IPC 命令签名与文档规范不一致

| 命令 | 文档签名 | 实际代码签名 | 差距说明 |
|------|---------|-------------|---------|
| `export_execute` | `(scope, password, password_hint, save_path)` 扁平参数 | `(account_id, req: ExportRequest)` 打包参数 | 前端调用时必须构造 `req` 对象，与文档定义的扁平参数不符。类型契约不一致。 |
| `import_execute` | `(source_path, password)` | `(account_id, file_path, password)` | 多了 `account_id` 参数，且参数名 `source_path` → `file_path`。 |
| `import_execute_advanced` | `(selections, preference_strategy, source_path, password)` 扁平参数 | `(account_id, req: AdvancedImportRequest)` 打包参数 | 与 `export_execute` 类似，参数被过度打包。 |
| `export_estimate_size` | `(scope)` | `(account_id, scope)` | 多了 `account_id` 参数。 |

**影响**：若后续有第三方客户端或 SDK 按文档调用，会产生兼容性问题。

### 1.2 P0 导入策略与文档严重矛盾

- **文档定义**（P0 导入流程第③步）：
  > ③ 确认导入（**全量覆盖当前账户数据**）

- **实际代码**：
  `import_execute` 内部调用 `import_execute_internal(..., ImportStrategy::SkipExisting, None)`，即**跳过所有已存在的对象**，不是覆盖。

- **矛盾点**：文档说"全量覆盖"，代码实际做"全量跳过"。这会导致用户以为导入会覆盖现有数据，结果旧数据原封不动，新数据也未写入。

**建议**：P0 的 `import_execute` 应使用 `Overwrite` 策略，以匹配文档描述的"全量覆盖"。`SkipExisting` 应仅作为 P2 高级导入的选项之一。

### 1.3 导出密码未校验"与主密码不同"

- **文档要求**（设计原则 & 关键决策 #2）：
  > 导出密码**必须与主密码不同**。导出文件离开本地后，如果复用主密码，导出包泄露 = 主密码泄露。

- **实际代码**：`export_execute` 仅校验：
  - 长度 ≥ 8
  - 包含至少一个字母和一个数字
  - **没有与 Vault 主密码的比对逻辑**

**影响**：用户可以将导出密码设为与 Vault 主密码相同，违反安全底线。

### 1.4 `export_scope` 值域超出规范定义

- **文档定义**：`"partial" | "full"`
- **实际代码**：当 `selected_page_ids` 和 `selected_object_ids` 都为空时，写入 `"none"`

```rust
"export_scope": if req.scope.selected_page_ids.is_empty() && req.scope.selected_object_ids.is_empty() { "none" } else { "partial" },
```

**问题**：虽然空选择在前后端都被拒绝（不会实际生成文件），但代码路径中出现了规范未定义的 `"none"` 值。若未来前端校验放松，可能生成不符合规范的 manifest。

### 1.5 跨范围 RelationProperty 引用处理完全缺失

- **文档要求**（§4 跨范围引用处理）：
  > 对象级导出时，RelationProperty 的目标对象可能不在导出范围内 → **导入时转为 `[引用对象未导出: {id}]` 文本备注**。

- **实际代码**：导出时直接序列化 `properties` 字段，导入时直接写入。没有任何对 `RelationProperty` 的检测、转换或降级处理。

**影响**：导入后，RelationProperty 指向不存在的对象，可能导致前端渲染错误、数据完整性问题。

### 1.6 `import_execute` 未通过 `object_create` 接口导入

- **文档要求**（§8 完成标准）：
  > `import_execute` 解密 payload → **通过 object_create 导入**

- **实际代码**：直接调用 `vault.save_object(&record)`，绕过了 `object_create` 命令/服务层。

**影响**：若 `object_create` 未来加入验证、审计、事件触发等逻辑，导入流程将绕过这些机制。

## 二、P1 级差距（重要，影响体验或安全合规）

### 2.1 标签筛选导出（`selected_tags`）：后端已支持，前端 UI 缺失

- **文档要求**：对象级导出支持按 `tags_json` 标签筛选。
- **后端**：`ExportScope` 有 `selected_tags` 字段，`collect_scope_objects` 已实现了标签交集过滤。
- **前端**：`ExportImportPage.tsx` 中 `selectedTags` 始终传空数组 `[]`，且 UI 中**没有任何标签筛选控件**。代码注释甚至写道：
  ```typescript
  // tags are on the ObjectSummary type but we don't have them in frontend type yet
  ```

**状态**：后端就绪，前端未实现。属于 P2 功能但后端已提前实现，前端拖后腿。

### 2.2 密码提示词明文存储：已实现但缺少内容校验

- **文档要求**：明文存储于 `manifest.json`，提示词**不包含密码本身**，最大 200 字符。
- **实际代码**：已存储，长度由前端 `maxLength={200}` 限制，但**没有校验提示词内容是否包含密码本身**。

**风险**：用户可能在提示词中直接写入密码，违反"安全可控"原则。

### 2.3 导入预览冲突检测：基本实现，但策略展示与文档流程有偏差

- **文档 P1 流程**：
  1. 读取密码提示词（无需密码）
  2. 输入密码 → 解密预览 → 展示对象数量 + 名称列表 + **冲突标记**
  3. 导入策略选择（P2）

- **实际实现**：
  - 密码提示词展示 ✓
  - 解密预览 + 对象列表 ✓
  - 冲突标记 ✓
  - **但策略选择器（SkipExisting / Overwrite / Merge）被标为 P2 并已实现**，而文档将其列为 P2。这部分实际上是超前实现，不算差距。

### 2.4 敏感度警告横幅：前端已实现，但未联动到加密强度

- **文档要求**：导出包含 `sensitive`/`critical` 级别字段时，显示警告横幅，且"导出文件使用密码加密"。
- **前端**：已实现 `hasSensitiveData` 检测和警告 UI。
- **差距**：警告仅在前端展示，后端 `export_execute` 没有因为包含敏感数据而拒绝弱密码或强制更强的加密参数。这是一个纯前端提示，后端未参与安全强化。

## 三、P2 级差距（增强功能，当前不影响主干）

### 3.1 附件层导出：部分实现但依赖非正式接口

- **文档要求**：选中对象的附件打包入 ZIP 的 `attachments/` 目录。
- **实际代码**：
  - 后端通过 `load_attachments` 从 `properties["__attachments"]` 读取附件元数据，这不是正式的附件系统接口。
  - 附件路径解析有 `vault_path` → `src_path` → `base_dir` 的三层回退逻辑，文档未定义。
  - 文档明确说明：附件导入导出依赖附件存储模块就绪。当前实现是一个临时方案。

### 3.2 偏好数据导出：密钥派生方式不标准

- **文档要求**：P2 支持 `preferences.enc`。
- **实际代码**：已支持，但使用了自定义的密钥派生：
  ```rust
  let prefs_key = derive_export_key(&format!("{}_prefs_salt", password), &salt)?;
  ```
  这是将用户密码拼接字符串 `"_prefs_salt"` 后再次派生密钥。

**安全隐患**：
1. 这不是标准的 HKDF 或类似密钥分离方案，只是简单的字符串拼接。
2. 如果攻击者知道派生逻辑，可能通过主 payload 密钥推导出 preferences 密钥（或反之）。
3. 文档未定义此派生逻辑，属于实现者自行决定的方案。

**建议**：使用标准 HKDF 从主密钥派生 preferences 子密钥，或文档应明确此派生方案。

### 3.3 `includeBehavioral` 完全缺失

- **文档接口**：`ExportScope.includeBehavioral: boolean`
- **实际代码**：前后端均无此字段。

## 四、类型定义不一致

### 4.1 `PageGroup` 字段差异

| 字段 | 文档 | Rust 代码 | 前端代码 |
|------|------|----------|---------|
| `sectionType` | ✓ | ✓ | ✓ |
| `pageName` | ✓ | ✓ | ✓ |
| `objects` | ✓ | ✓ | ✓ |
| `objectCount` | ✗ | ✓（多余字段） | ✓ |

**建议**：文档更新加入 `objectCount`，或代码移除该字段以匹配文档。

### 4.2 `ObjectSummary` 字段差异

| 字段 | 文档 | Rust `solosoul_vault::ObjectSummary` | 前端代码 |
|------|------|-------------------------------------|---------|
| `id` | ✓ | ✓ | ✓ |
| `name` | ✓ | ✓ | ✓ |
| `tags` | ✓ | ✓ | ✓（可选 `tags?: string[]`） |
| `sensitivityLevel` | ✓ | ✓ | ✓ |
| `updatedAt` | ✓ | ✓ | ✓ |
| `collection_type` / `section_type` | — | ✓ | 有但不用于文档定义的接口 |

**差距**：文档中 `ObjectSummary` 用于 `PageGroup.objects` 和 `DecryptedImportPreview.objects`，但 Rust 的 `ObjectSummary` 还包含 `collection_type`、`is_deleted`、`properties` 等字段，前端类型未完全对齐。

### 4.3 `ImportPreview` 类型命名

- **文档**：`ImportPreview`
- **代码**：`ImportPreviewResponse`

字段基本一致（代码多一个 `file_path`），属于命名不一致。

### 4.4 `import_execute` 返回值类型

- **文档**：`Result<bool, String>`
- **代码**：`Result<usize, String>`（返回实际导入的对象数量）

**建议**：文档应更新为 `usize`，因为返回导入数量对用户体验更有价值。

## 五、其他实现细节问题

### 5.1 `export_get_scope_tree` 的回退逻辑未在文档中定义

代码中对 `section_type` 为空的对象做了以下回退：
```rust
let st = if obj.section_type.is_empty() {
    if obj.collection_type.is_empty() {
        "identity".to_string()  // 硬编码默认
    } else {
        obj.collection_type.clone()
    }
} else {
    obj.section_type.clone()
};
```

**问题**：文档未提及此回退逻辑。`"identity"` 作为硬编码默认值可能在数据模型变化时失效。

### 5.2 `export_estimate_size` 对 preferences 的估算过于粗糙

```rust
if scope.include_preferences {
    estimated_bytes += 4096; // rough guess
}
```

**问题**：P2 功能使用固定值估算，不够准确。应读取实际 preferences 数据大小。

### 5.3 `export_execute` 中 manifest 的 `has_preferences` 字段不在文档规范中

文档定义的 manifest 字段中没有 `has_preferences`，代码中新增了该字段。虽然合理，但属于规范外扩展。

## 七、修复建议优先级

### 立即修复（本周）
1. **#2**：将 `import_execute` 默认策略改为 `Overwrite`，或修改文档将 P0 定义为"增量导入（SkipExisting）"。**建议改代码**，因为"全量覆盖"是更常见的 P0 预期。
2. **#3**：在 `export_execute` 中加入主密码比对校验，拒绝与主密码相同的导出密码。
3. **#5**：在导入流程中加入 RelationProperty 检测与降级处理。

### 短期修复（下次迭代）
4. **#1**：统一 IPC 命令签名风格（建议按文档改为扁平参数，或更新文档为打包参数）。
5. **#6**：将 `import_execute` 改为调用 `object_create` 命令或服务层接口。
6. **#7**：前端补充标签筛选 UI。

### 中期优化
7. **#9**：使用标准 HKDF 替代 `"{}_prefs_salt"` 的密钥派生。
8. **#4, #12, #13, #14, #15**：文档与代码对齐。
