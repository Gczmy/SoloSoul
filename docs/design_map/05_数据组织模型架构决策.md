# 05 — 数据组织模型架构决策（扁平 vs 层级）

> **前置阅读**：`06_数据库与服务层.md`、`10_跨平台视觉规范与主题系统.md`、`23_外部产品设计借鉴与术语规范.md`
> **Manifesto 对齐**：最少惊喜 | 本地优先
> **文档定位**：定义 SoloSoul 核心数据组织模型的架构决策——页面与对象之间是否引入"集合/分组"中间层。此决策影响数据库 Schema、前端 UI、用户心智模型和长期维护成本。

---

## 1. 决策结论

**SoloSoul 采用扁平模型（Flat Model）：页面直接包含对象列表，不引入集合/分组中间层。**

在此基础上，通过**智能筛选视图（Smart Filter）**满足用户的分组查看需求——对象添加可选标签字段，前端按标签条件做动态筛选，数据结构本身保持扁平不变。

```
扁平模型（采纳）：

Travel Page
  ├─ 护照 · 张三        ← 直接就是对象列表
  ├─ 签证 · 日本
  ├─ 机票 · 东京
  ├─ 酒店 · 新宿
  └─ ...

层级模型（否决）：

Travel Page
  ├─ 📁 2025 日本旅行      ← 集合（不采纳）
  │    ├─ 护照 · 张三
  │    ├─ 签证 · 日本
  │    └─ 机票 · 东京
  ├─ 📁 2024 欧洲出差
  │    ├─ 护照 · 张三
  │    └─ 申根签证
  └─ 📁 常用证件
       └─ 护照 · 张三
```

---

## 2. 主流应用对比

| 应用 | 数据模型 | 层级深度 | 典型数据量 | 与 SoloSoul 对齐度 |
|------|---------|---------|-----------|------------------|
| 1Password | Category → Item → Field | 扁平——分类下直接是条目 | 500+ 密码 | 高（个人数据管理） |
| Apple 钱包/健康 | Category → Record | 扁平——无中间分组 | 10-50 条记录 | 高（原生系统级） |
| Notion | Page → Block | 扁平——页面直接含块 | 不定 | 中（通用笔记） |
| Anytype | Object → Type → Set/Collection | 层级——集合是动态查询视图 | 不定 | 低（复杂知识库） |
| Airtable | Base → Table → Record → Field | 层级——表是必要的分组层 | 1,000+ 记录 | 低（数据库工具） |
| Bear / Apple Notes | Folder → Note | 扁平——文件夹直接装笔记 | 50-500 笔记 | 高（个人笔记） |

> **观察**：个人数据管理类应用（1Password、Apple 钱包/健康、Bear）均采用扁平模型，即使数据量达到 500+ 仍不使用层级分组。搜索和扫描比导航子文件夹更高效。

---

## 3. 方案详细对比

### 3.1 方案 A：扁平模型（当前模型）

```
Travel Page → [护照, 签证, 机票, 酒店, 保险, ...]
              ↑
              直接就是对象列表，无中间层
```

**数据结构**：

```sql
-- 对象直接归属页面（通过 section_type 字段）
CREATE TABLE objects (
    id TEXT PRIMARY KEY,
    account_id TEXT NOT NULL,
    name TEXT NOT NULL,
    section_type TEXT NOT NULL,  -- 'identity' | 'travel' | 'financial' | 'professional'
    section_data_json TEXT NOT NULL,
    tags_json TEXT DEFAULT '[]', -- 可选标签，用于智能筛选
    sensitivity_level TEXT DEFAULT 'internal',
    created_at TEXT, updated_at TEXT, deleted_at TEXT
);
```

### 3.2 方案 B：三层模型（集合层）

```
Travel Page
  ├─ 📁 2025 日本旅行
  │    ├─ 护照 · 张三
  │    ├─ 签证 · 日本
  │    └─ 机票 · 东京
  └─ 📁 常用证件
       └─ 护照 · 张三
```

**数据结构**：

```sql
-- 需要新增 collections 表
CREATE TABLE collections (
    id TEXT PRIMARY KEY,
    page_id TEXT NOT NULL,
    name TEXT NOT NULL,
    sort_order INTEGER
);

-- objects 表需要指向 collection 而非 page
CREATE TABLE objects (
    id TEXT PRIMARY KEY,
    collection_id TEXT NOT NULL,  -- 变更：从 page 指向 collection
    -- ...
);
```

## 4. 关键判断因素

### 4.1 对象唯一性冲突（否决方案 B 的核心原因）

**真实场景**：用户的"护照"对象同时需要出现在：
- "旅行"页面的"2025 日本旅行"集合中
- "旅行"页面的"常用证件"集合中

**方案 B 的问题**：
- 每个对象只能属于一个集合，物理上无法同时存在于两个集合
- Anytype 通过 Relation（关联）解决此问题——对象可以"关联"到多个集合，但本身只属于一个类型
- 这要求用户理解"属于"vs"关联"的区别，学习成本显著增加

**方案 A 的解决**：
- 对象扁平存储于页面下，通过 `tags_json` 字段标记多个标签
- "护照"对象的 `tags` = `["常用证件", "2025日本"]`
- 前端筛选时，同一对象可以同时出现在"常用证件"筛选视图和"2025日本"筛选视图中
- 用户无需理解"属于"vs"关联"的区别——只需要打标签

### 4.2 用户实际数据量（支持扁平模型的核心依据）

一个典型 SoloSoul 用户的数据量：

| 页面 | 对象数量 |
|------|---------|
| 身份页面 | 3-8 个（身份证、驾照、社保卡...） |
| 旅行页面 | 5-20 个（护照、签证、机票、酒店...） |
| 财务页面 | 5-15 个（银行卡、信用卡、税务号...） |
| 职业页面 | 5-15 个（学历、工作经历、技能证书...） |
| **总计** | **~20-60 个对象** |

**结论**：每个页面不超过 20 个对象。在这种规模下，**扫描比点击进子文件夹更快**。1Password 用户可能有 500+ 密码，但它仍然用扁平分类模型，因为搜索比导航快。

> **反例论证**：如果未来用户数据量增长到每个页面 100+ 对象，扁平模型的扫描效率会下降。但当前架构可以通过"智能筛选"解决，无需引入集合层。若未来确实需要集合层，扁平模型的 `tags` 字段可以平滑迁移为正式集合关联（向后兼容）。

### 4.3 用户真实需求分析

用户确实有"把某次旅行的所有东西放在一起看"的需求。但这个需求的本质是**多视角查看同一批对象**，而非**物理上把对象装进不同容器**。

```
需求本质对比：

❌ "把护照放进 2025日本旅行文件夹"
   → 物理移动对象 → 需要集合层 → 对象唯一性冲突

✅ "给护照打上 2025日本 标签，筛选时看到它"
   → 不改变对象存储位置 → 不需要集合层 → 同一对象可多标签
```

## 5. 推荐方案：扁平 + 智能筛选

### 5.1 核心设计

在扁平模型基础上，给对象增加可选的 `tags` 字段，前端提供预设筛选器：

```
Travel Page
  [全部 ▼]  ← 筛选器下拉

  [护照] [签证] [机票] [酒店] [保险]
  
  筛选器选项：
    "全部"      → 显示页面内所有对象
    "即将过期"  → 动态条件：expiration_date <= 30 天
    "2025日本"  → tag == "2025日本"
    "常用证件"  → tag == "常用证件"
    ...
```

### 5.2 数据结构变化（最小化）

```sql
-- objects 表：仅需新增 tags_json 字段
CREATE TABLE objects (
    id TEXT PRIMARY KEY,
    account_id TEXT NOT NULL,
    name TEXT NOT NULL,
    section_type TEXT NOT NULL,  -- 页面分类：identity/travel/financial/professional
    section_data_json TEXT NOT NULL,
    tags_json TEXT DEFAULT '[]', -- ["2025日本", "常用证件"]
    -- 动态筛选字段（根据 section_type 不同）
    expiration_date TEXT,        -- 护照/签证过期日期，用于"即将过期"筛选
    created_at TEXT, updated_at TEXT, deleted_at TEXT
);

-- 无需新增 collections 表
```

### 5.3 预设筛选器定义

| 筛选器类型 | 实现方式 | 示例 |
|-----------|---------|------|
| **标签筛选** | `tags_json` 包含指定标签 | `"2025日本"`、`"常用证件"` |
| **时间筛选** | 动态条件计算 | `expiration_date <= now + 30d` |
| **敏感度筛选** | `sensitivity_level` 字段 | `sensitivity == 'sensitive'` |
| **类型筛选** | `section_data_json` 中的 type 字段 | `type == 'passport'` |

筛选器配置存储于用户偏好（`ui.enc`），用户可自定义筛选条件。

### 5.4 与 Anytype Set/Collection 的区别

| 维度 | Anytype Set/Collection | SoloSoul 智能筛选 |
|------|----------------------|------------------|
| 数据结构 | 需要独立的 Set 表和 Relation 表 | 仅需 `tags_json` 字段 |
| 查询复杂度 | 多表 JOIN + Relation 解析 | 单表 WHERE + JSON 包含 |
| 学习成本 | 高（需理解 Type、Set、Relation 三层概念） | 低（标签 = 文件夹，筛选 = 查看条件） |
| 对象多视角 | 通过 Relation 关联实现 | 通过多标签天然实现 |
| 动态条件 | Set 查询支持动态条件 | 前端计算 + 单表过滤 |

---

## 6. 综合对比

| 维度 | 扁平 + 智能筛选（推荐） | 层级 + 集合（否决） |
|------|----------------------|-------------------|
| 学习成本 | 低——像文件夹装文件 | 高——需理解页面/集合/对象三层 |
| 数据量 < 50 | 完全够用，扫描比导航快 | 过度设计，增加无意义点击 |
| 同对象多视角 | 天然支持（多标签） | 需引入 Relation 概念 |
| 开发维护 | 简单——单表查询 | 复杂——多表 JOIN + 关联管理 |
| 数据库 Schema | 最小变更（仅加 `tags_json`） | 新增 collections 表，修改 objects 外键 |
| 设计文档对齐 | 与 §17 的 Collection 概念一致（前端视图层） | 偏离 §17，需重写数据模型 |
| Notion/1Password 对齐 | ✅ | ❌ |
| Anytype 对齐 | ❌（有意偏离，降低复杂度） | ✅ |
| 未来扩展性 | `tags` 可平滑迁移为正式集合关联 | 一旦引入集合，回退成本高 |

## 7. 对现有文档的影响

### 7.1 06 数据库文档

- `objects` 表新增 `tags_json` 字段（默认 `'[]'`）
- 不新增 `collections` 表
- `section_type` 字段继续作为页面分类（`identity`/`travel`/`financial`/`professional`）

### 7.2 09 视觉规范

- 页面内对象列表采用网格/列表布局（扁平展示）
- 页面顶部提供筛选器 Dropdown（智能筛选 UI）
- 对象卡片支持标签展示和标签编辑

### 7.3 对象创建/编辑交互

- 创建对象时，可选填写标签（多选，从已有标签中选取或新建）
- 编辑对象时，可增删标签
- 标签管理：设置页提供"标签管理"入口，可重命名/合并/删除标签

---

## 8. 边界情况与回退策略

### 8.1 数据量增长边界

若未来单个页面对象数量超过 100：
- **第一阶段**：优化智能筛选（增加搜索框、更丰富的筛选条件）
- **第二阶段**：引入"虚拟集合"——基于标签的视图保存为快捷入口（UI 层，非数据层）
- **第三阶段**（极端情况）：若确实需要物理集合层，`tags_json` 中的标签可迁移为正式的 collection 关联， objects 表新增 `collection_id` 字段，保持向后兼容

### 8.2 用户误操作防护

- 删除标签时：若标签被对象引用，提示"该标签被 N 个对象使用，删除后对象仍保留"
- 合并标签时：提供预览，显示合并后各对象的标签变化
