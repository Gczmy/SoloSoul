# 01 — 技术选型确认与架构决策

> **前置阅读**：`00_总览与阅读指南.md`
> **Manifesto 对齐**：依赖最小化 | 本地优先 | 隐私优先
> **源文档**：`tauri_refactor/技术选型重新评估.md`

---

## 1. 决策结论

**SoloSoul 重构采用 Tauri + Rust 作为主技术栈。**

| 维度 | 选型 |
|------|------|
| 桌面框架 | Tauri v2 |
| 后端语言 | Rust（原生集成，无需 FFI 桥接） |
| 前端框架 | React 19 + TypeScript 5.7 |
| 构建工具 | Vite 6 |
| UI 渲染 | OS WebView（macOS=WKWebView, Windows=WebView2, Linux=WebKitGTK） |
| 跨平台范围 | macOS / iOS / Android / Windows / Linux |

---

## 2. 硬约束（不可妥协）

任何技术选型必须满足以下硬约束，按优先级：

| # | 约束 | 原因 |
|---|------|------|
| 1 | **跨五平台** | macOS / iOS / Android / Windows / Linux |
| 2 | **Rust 原生密码学** | Argon2id + AES-256-GCM 是核心竞争力，必须用 Rust 实现 |
| 3 | **本地优先** | 100% 核心功能在无网络环境下可用 |
| 4 | **零知识加密** | 端到端加密、内存安全、Zeroize 缺一不可 |
| 5 | **系统级集成** | Keychain、生物识别、文件系统、通知、原生菜单 |
| 6 | **长期可维护性** | 个人数据管理软件的生命周期是 10 年+ |
| 7 | **开源可控** | MIT / Apache 2.0 许可 |

---

## 3. 为什么是 Tauri + Rust（不是 Flutter + Rust FFI）

### 3.1 Flutter + Rust FFI 的已知问题（保持现状方案的排除理由）

| 问题 | 影响 |
|------|------|
| **FFI 开销** | 序列化/反序列化开销，调试困难 |
| **桌面端体验差距** | macOS 菜单、窗口管理、原生行为一直有 gap |
| **包体积** | 动辄 50MB+ |
| **长期维护** | FFI 层是持续的技术债务 |
| **与重构目标冲突** | 当前重构方向明确是 Tauri |

### 3.2 Tauri + Rust 的核心优势

| 维度 | Tauri + Rust |
|------|-------------|
| **桌面端性能** | ⭐⭐⭐⭐⭐ 极佳。3-15MB 包体积，20-80MB 内存，200-500ms 冷启动 |
| **安全性** | ⭐⭐⭐⭐⭐ Rust 内存安全 + OS WebView 沙箱 + 最小攻击面 |
| **Rust 兼容性** | ⭐⭐⭐⭐⭐ 原生集成，无需 FFI，直接复用 crypto crate |
| **跨平台覆盖** | ⭐⭐⭐⭐⭐ 一套代码覆盖五平台 |
| **资源效率** | ⭐⭐⭐⭐⭐ 无 Chromium 捆绑，更新包仅 1-5MB（delta） |
| **开源许可** | ⭐⭐⭐⭐⭐ MIT / Apache 2.0 |

### 3.3 Tauri 的已知弱点与缓解措施

| 弱点 | 影响 | 缓解措施 |
|------|------|---------|
| 移动端成熟度 | 手势、原生组件不如 Flutter | 移动端定位"数据查看+轻量编辑"，复杂操作引导到桌面端 |
| Liquid Glass UI 需重写 | 中高 | CSS backdrop-filter + WebGL 毛玻璃效果 |
| Rust 人才招聘 | 薪资高，人才池小 | 前端用 TypeScript/React（人才丰富），Rust 后端仅维护核心模块 |
| 移动端测试工具不成熟 | 中 | 桌面端用 `tauri-driver`，移动端用 Appium，核心逻辑用 Rust 单元测试覆盖 |
| WebView 跨平台渲染差异 | 中 | 跨平台视觉回归测试 + CSS 特性检测 + 渐进增强 |

---

## 4. 已排除的候选方案及排除理由

| 方案 | 排除理由 |
|------|---------|
| **React Native + Rust** | 桌面端基本不支持（硬约束违反） |
| **Kotlin Multiplatform + Compose** | 桌面端支持不足（2026 年），Rust 集成路径不清晰 |
| **纯原生开发** | 3-4 套代码，维护成本不可接受，与"Centralized Schema definition"冲突 |
| **Electron + Rust** | 包体积 120-250MB，移动端完全不支持，攻击面巨大 |

---

## 5. 备选策略：如果移动端变得更重要

如果未来移动端用户占比显著提升（超过 40%），考虑分层策略：

```
桌面端：Tauri + Rust（完整功能）
  ├── 复杂数据录入、批量导入导出、同步设置、附件管理、插件管理

移动端：Tauri + Rust（轻量功能）或 Flutter + Rust FFI
  ├── 查看数据、简单编辑、接收通知、二维码配对码同步
```

**触发条件**：移动端用户占比超过 40% 或 Tauri 重构完成 1 年后重新评估。

---

## 6. 关键架构决策（非技术选型但影响全局）

| # | 决策 | 理由 |
|---|------|------|
| 1 | 前端使用 **React 19 + TypeScript** | Web 生态最成熟，人才最丰富，Tauri 官方首推 |
| 2 | 状态管理使用 **Zustand** | 无 Provider、细粒度订阅、TypeScript 完美支持（详见文档 12） |
| 3 | 样式使用 **CSS Modules + 全局 CSS** | 不用 Tailwind（团队无经验，与 Liquid Glass 不兼容），不用 CSS-in-JS（运行时开销） |
| 4 | 路由使用 **React Router 7** | 标准选择，支持嵌套路由和参数 |
| 5 | IPC 类型生成使用 **tauri-specta** | Rust → TypeScript 自动类型生成，消除手工维护 |
| 6 | 密码学**仅在 Rust 侧** | 前端绝不接触原始密钥（详见文档 05） |
