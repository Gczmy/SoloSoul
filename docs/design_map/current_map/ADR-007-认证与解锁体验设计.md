# ADR-007: 认证与解锁体验设计

> **状态**: 已采纳  
> **日期**: 2026-06-04  
> **决策人**: 产品 + 安全架构  
> **影响范围**: 认证流程、Vault 加密、导出/导入、生物识别集成、敏感度分级系统

---

## 1. 背景与问题

在 Tauri 重构期间，我们对比了 Anytype 的"打开即用"体验，产生了是否应该去掉主密码的争论。

**主张去掉密码的理由**：
- 用户在自己的设备上，不需要"防着自己"
- 去掉密码后所有敏感度字段无需遮盖和二次验证，体验更流畅
- 类似 Anytype，使用系统钥匙串 + 恢复短语即可

**反对去掉密码的理由**：
- SoloSoul 的数据类型（护照、银行卡、身份证）比 Anytype（笔记、任务）敏感度高一个量级
- 去掉主密码后导出包将失去加密保护，任何人拿到即可查看
- 设备共享场景（借用电脑、家庭 iPad）下数据完全暴露
- 敏感度分级系统（public/internal/private/sensitive/restricted/critical）将失去意义

## 2. 决策

**保留主密码，但大幅优化解锁体验**。

具体设计：

1. **首次安装/恢复**：用户必须设置/输入主密码（Argon2id 派生）
2. **日常解锁**：Touch ID / Face ID 快速解锁，无需输入密码
3. **敏感操作**：生物识别确认（无需重新输入密码，1 分钟缓存）
4. **导出数据**：强制主密码加密（或生物识别确认后加密）
5. **新设备导入**：必须输入主密码解密
6. **多账户**：保留，但切换用生物识别确认，不要求完整密码

## 3. 威胁模型对比

| 威胁 | Anytype 的应对 | SoloSoul 的应对（本决策） |
|---|---|---|
| 云端/第三方窃取 | 零知识加密 | 零知识加密 ✅ |
| 网络嗅探 | P2P + E2EE | P2P + E2EE ✅ |
| 设备物理丢失 | 设备密码 + 磁盘加密 | 设备密码 + 磁盘加密 ✅ |
| **设备被临时借用** | 无隔离（笔记数据可接受） | **主密码保护 Vault** ✅ |
| **导出包泄露** | 导出为 Markdown/PDF（非加密） | **导出包 Argon2id + AES-256-GCM 加密** ✅ |
| **取证软件提取** | 打开软件即可看 | **需要破解 Argon2id** ✅ |
| **家人/同事看到数据** | 可接受 | **不可接受** → 主密码隔离 ✅ |

## 4. 为什么不照搬 Anytype

Anytype 不设应用级密码的前提是：
- 数据是笔记/任务，泄露后果可控
- 用户不共享设备
- 威胁模型中"设备被入侵"是不可防护的（官方承认）
- 单账户足够

SoloSoul 不满足这些前提：
- 身份数据泄露 = 身份盗用、金融诈骗
- 家庭 iPad、借用电脑是常见场景
- 导出是加密备份包（不是 Markdown），必须保护
- "数字孪生"定位要求更高的安全边界

## 5. 技术设计

### 5.1 密钥分层

```
用户主密码
    ↓
Argon2id (8/64 MiB) → 主密钥 (32-byte)
    ↓
├─→ 用于 Vault 数据加密（SQLite 数据库）
├─→ 用于导出包加密
└─→ 派生系统钥匙串存储的"会话密钥"

会话密钥（存储在 OS Keychain）
    ↓
用于日常自动解锁（无需主密码）
生物识别验证后从 Keychain 读取会话密钥
```

### 5.2 解锁流程

```
首次安装:
    用户输入主密码 → Argon2id 派生主密钥 → 创建 Vault
    → 派生会话密钥 → 存入 OS Keychain

日常打开:
    检测会话密钥是否存在
    ├─ 存在 → 请求 Touch ID / Face ID → 从 Keychain 读取会话密钥 → 解锁 ✅
    └─ 不存在 → 要求输入主密码 → 重新派生

后台锁定（App 进入后台超时）:
    → 清除内存中的会话密钥
    → 下次进入前台：重新生物识别

切换账户:
    → 生物识别确认 → 从 Keychain 读取对应账户的会话密钥
```

### 5.3 敏感操作分级

| 操作 | 验证方式 |
|---|---|
| 打开应用查看 public/internal 数据 | 生物识别（Touch ID/Face ID） |
| 查看 sensitive/restricted/critical 字段 | 生物识别（1 分钟缓存） |
| 修改/删除 sensitive+ 数据 | 生物识别（1 分钟缓存） |
| 导出数据 | 生物识别 + 主密码派生密钥加密 |
| 修改主密码 | 必须输入原主密码 |
| 删除账户 | 必须输入主密码 |
| 新设备导入 | 必须输入主密码 |

### 5.4 与当前设计的差异

| 场景 | 当前 Flutter 实现 | Tauri 重构后 |
|---|---|---|
| 打开应用 | 输入主密码 | Touch ID / Face ID |
| 查看敏感字段 | 输入密码重新验证 | 生物识别（已解锁状态下无感） |
| 切换账户 | 输入密码 | 生物识别确认 |
| 导出数据 | 主密码加密 | 主密码加密（保持） |
| 后台锁定 | 倒计时后要求密码 | 倒计时后要求生物识别 |

## 6. 副作用

- 用户仍需要**记住一个主密码**（仅在导出、新设备、修改密码时使用）
- 依赖 OS Keychain / Credential Manager（重装系统会丢失会话密钥，但主密码仍可用）
- 需要在 Tauri 侧实现生物识别集成（`tauri-plugin-biometric` 或原生 API）

## 7. 备选方案（已否决）

| 方案 | 否决理由 |
|---|---|
| 完全去掉主密码（Anytype 风格） | 导出包无保护，设备共享场景数据暴露 |
| 恢复短语模式（BIP39） | 不适合多账户，用户体验不符合 SoloSoul 场景 |
| 两套加密（日常钥匙串 + 敏感主密码） | 架构过于复杂，维护成本高 |

## 8. 结论

**"防自己"是伪需求，但"防他人"是刚需。**

SoloSoul 的数据敏感度决定了不能照搬 Anytype 的"无密码"设计。通过将主密码的使用场景缩减到"导出/新设备/密码修改"，日常用生物识别替代，可以在**不牺牲安全性的前提下大幅提升体验**。
