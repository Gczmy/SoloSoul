## 1. 设计原则

### 后台导入导出的会话边界（RF-003）

Tauri 导入/导出入口捕获 `VaultSession`；云同步复用起始会话的可恢复导入入口 `import_execute_resumable_for_session` 与 Core `execute_encrypted_export`，不能在网络、ZIP 或 KDF 等待后重新获取当前账户句柄。附件密钥由原会话安全复制后派生，锁定和重新解锁都会使原令牌失效。

`ImportResult.sessionGeneration` 标识本次导入绑定的后端会话代次（与前端本地请求计数不同）；手动云水线提交回传此值，确保导入和后续提交属于同一次解锁。

GUI 和 CLI 使用共享 `ImportTarget::Session`：模板、对象、历史及 HLC 由一个数据库批次在原 `VaultSession` 门闩内提交；偏好及审计仍独立核验原会话。CLI 在打开密码提示前捕获会话及 `Zeroizing` 附件密钥，锁定、切换账户或同账户重新解锁后，旧提示不能写入；共享 Core 的 `import_vault` 仍保留 `ImportTarget::Direct` 兼容入口。附件的解密/加密在临时文件中完成，发布到最终随机附件目录以及元数据提交时分别核验会话。GUI 会话失效后的已提交计数由 RF-020 返回；RF-022 另外记录账户加密 journal 与附件阶段，短期明文临时文件仍随真实 worker Drop 清理。

### 附件导出范围（RF-015）

共享 Core 类型 `AttachmentExportScope` 表示 `None / All / Selected(ids)`。Host 和 Core 的附件收集器只解释此类型；范围始终限制在已经选中的未删除对象内，并排除已删除附件。

| 入口 | 附件范围 |
|------|----------|
| GUI 既有 IPC `includeAttachments=false` | `None`，忽略传入 ID |
| GUI `includeAttachments=true` | `Selected(selectedAttachmentIds)`；空数组仍为零选中，重复/未知 ID 不新增附件 |
| Core 兼容导出与 CLI `--include-attachments` | 开关关闭为 `None`，开启为所选对象附件的 `All` |
| 云全量快照、恢复传输包 | 后台显式传入 `All`，不再预先枚举 ID 来模拟全选 |

IPC 的字段、camelCase 和默认值不变，不将空数组或 `null` 解释为全选。估算也使用同一范围：`None` 的可用/已选附件计数均为零；`Selected(empty)` 仍显示可用附件数，已选数和附件字节数为零；`All` 只统计对象范围内的有效附件元数据。文件缺失和旧元数据解析行为、100 MiB 单附件及1 GiB总量限制、包格式与原会话发布保护保持。

RF-023 将完整导出用例迁入 Core；GUI/云/恢复使用 Advanced 策略，旧 CLI/Core公开接口使用 LegacyDirect 策略，并共用原子 writer。CLI 已获得失败保留原目标的发布保护，但其兼容接口仍不传 SOLC 源附件密钥。附件范围回归见 [RF-015证据](../verification/rf015-explicit-attachment-export-scope-2026-10-01.json)，完整用例见 [RF-023证据](../verification/rf023-core-encrypted-export-2026-10-01.json)。

### 为什么细化到"对象层"为止，不开放字段级别？

1. **数据完整性**：护照对象包含姓名、国籍、护照号等字段，共同构成完整记录。导出"只有姓名和国籍的护照"无意义。
2. **关系完整性**：对象可能包含 RelationProperty 指向其他对象，字段级导出会产生孤立引用。
3. **用户体验**：字段级选择让导出 UI 极其复杂（每个对象展开几十个字段），违背"最少惊喜"。
4. **粒度足够**：对象级导出已满足"只导出护照"的实际需求。

### 导出范围的三层结构

```
身份数据
├── 页面层 → "导出我的所有旅行数据"
├── 对象层 → "导出我的护照"（可勾选多个对象）
└── 附件层 → "只导出扫描件，不导出照片"

偏好数据
├── 视觉偏好（主题、颜色、字体）
├── 行为偏好（锁定超时、生物识别、删除确认）
├── 内容偏好（语言、日期格式、时区）

行为记录
├── 操作日志（CRUD、敏感度变更）
├── 搜索历史
├── AI 对话历史
```

### 对象选择机制

扁平模型下，页面内的对象列表支持以下选择方式：

| 选择方式 | 说明 |
|---------|------|
| **手动勾选** | 页面列表中逐项勾选/取消 |
| **全选/反选** | 页面的批量操作按钮 |
| **按标签筛选后勾选** | 先按 `tags_json` 筛选（如"只显示标签为 `2025日本` 的对象"），再对筛选结果勾选 |
| **选择所有** | 勾选"页面"即选中该页面下的全部对象 |

```typescript
interface ExportScope {
  selectedPageIds: string[];          // 整页全选（section_type，如 travel/financial）
  selectedObjectIds: string[];        // 手工勾选的对象 ID
  selectedTags: string[];             // 按标签筛选（与 selectedObjectIds 交集生效）
  includeAttachments: boolean;        // 是否包含附件
  includePreferences: boolean;        // 偏好数据（P2）
  includeBehavioral: boolean;         // 行为记录（未来）
}
```

### 数据安全提示（P1）

导出包含 `sensitive`/`critical` 级别字段时，在导出确认界面显示警告横幅：
```
所选数据包含高敏感度字段，导出文件使用密码加密，请妥善保管。
```
LLM API 密钥作为 `critical` 级别字段，由通用敏感度警告覆盖，不单独处理。

### 实现优先级

| 功能 | 优先级 | 理由 |
|------|--------|------|
| 页面层 + 对象层导出（加密） | **P0（必须）** | 用户数据的核心备份/迁移路径 |
| 导入对象数据（含解密） | **P0（必须）** | 与导出配对，构成完整迁移闭环 |
| 导出密码（自定义密码） | **P0（必须）** | 导出文件加密安全底线 |
| 导入默认策略为 SkipExisting（防御性默认） | **P0（必须）** | 避免意外覆盖用户现有数据 |
| 敏感度警告 | **P1（重要）** | 安全合规，但缺了不影响功能 |
| 导入密码提示词展示 | **P1（重要）** | 帮助用户回忆密码 |
| 导入预览 + 冲突检测 | **P1（重要）** | 提升导入 UX，避免数据覆盖 |
| 导入策略选择（保留当前/覆盖/合并） | **P1（重要）** | 用户掌控数据命运 |
| 标签筛选导出（selected_tags） | **P1（重要）** | 后端已就绪，前端补充 UI 即可闭环 |
| 附件层导出 | **P1（重要）** | 基于当前 properties 中的附件元数据实现，提供即时价值 |
| 偏好/行为数据导出 | **P2+** | 数据边界还在定义中，不应绑定导入导出 |
| 明文 JSON 导出（三重确认） | **未来** | 合规场景，当前无实际需求 |
| 导入前自动创建静默备份 | **未来** | 备份功能独立，不应耦合在导入流程 |

## 2. 导出包格式

### P0 核心版

```
{scopeName}_export.solosoul (ZIP)
├── manifest.json           # 明文：版本、范围、时间、应用版本
│   ├── version: "2.0"
│   ├── export_scope: "partial" | "full"
│   ├── selected_pages: string[]
│   ├── selected_objects: string[]
│   ├── export_time: string
│   ├── export_platform: string
│   ├── export_app_version: string
│   ├── salt_hex: string              # 解密 payload.enc 必需的 salt
│   ├── password_hint: string         # 可选，帮助用户回忆密码
│   ├── has_attachments: boolean
│   ├── has_preferences: boolean      # 扩展字段，指示是否包含 preferences.enc
│   └── extra_files: string[]         # 扩展文件清单
├── payload.enc             # 加密：所有选中对象的 JSON 数据（单文件，统一加密）
└── attachments/             # 可选（P1 实现，详见 §10）
    └── {objectId}/          # 按对象分组
        └── {attachmentId}.enc   # 加密附件（AES-256-GCM，详见 §10.2）
```

**简化理由**：加密 payload 即可保证数据安全，细分多个加密文件（preferences.enc、audit_log.enc、search_history.enc、ai_conversation.enc、sensitivity_map.enc 等）增加了开发成本和导入解析复杂度，收益微薄。P0 统一使用单一 `payload.enc`，未来扩展时如需新增数据类别，在 `manifest.json` 中通过 `extra_files` 字段声明。

### manifest.json 最小定义（开放结构）

manifest.json 采用**最小必需字段 + 向后兼容扩展**的开放结构。以下字段为必需：

```json
{
  "version": "2.0",
  "export_scope": "partial",
  "selected_pages": ["travel", "financial"],
  "selected_objects": ["obj_abc123", "obj_def456"],
  "object_count": 2,
  "export_time": "2026-06-07T14:30:00Z",
  "export_platform": "macos",
  "export_app_version": "2.1.0",
  "salt_hex": "a1b2c3d4...",
  "password_hint": "",
  "has_attachments": false,
  "has_preferences": false,
  "extra_files": []
}
```

**开放结构原则**：
- 解析器必须识别上述必需字段
- 解析器应**忽略**不认识的字段（forward compatibility）
- 新增字段时，minor version 递增（如 `"2.1"`）
- `salt_hex` 为 P0 必需字段，用于解密 `payload.enc`

### 未来扩展版（P2+）

当需要支持 preferences、audit log 等额外数据时，在 ZIP 中新增对应加密文件：

```
{scopeName}_export.solosoul (ZIP)
├── manifest.json           # 新增 extra_files 描述所含文件清单
├── payload.enc             # 核心：所有对象的 JSON 数据
├── preferences.enc         # 用户偏好（可选）
├── audit_log.enc           # 审计日志（可选）
├── ai_conversations.enc    # AI 对话历史（可选）
├── attachments/
│   └── {fileId}.enc
```

> **附件支持说明**：P1 附件导入导出基于对象 `properties` 中的 `__attachments` 元数据实现。该方案在当前数据模型下可工作，未来附件存储系统重构时，仅需替换元数据读取逻辑，导出包格式（`attachments/` 目录结构）保持不变。

## 3. 导出密码设计

### 密码模式（P0 仅支持自定义密码）

| 模式 | 优先级 | 说明 |
|------|--------|------|
| **使用自定义密码** | **P0** | 必须与主密码不同。最小 8 位。加密导出包的密钥由此密码派生 |
| **使用主密码** | **未来** | 复用 Vault 主密码。需评估导出包泄露风险 |

> **关键决策**：P0 仅支持自定义密码模式。导出文件离开本地设备后，如果复用主密码，导出包泄露 = 主密码泄露。导入导出应始终使用独立密码。

### 密码提示词（P1）

- 可选字段，最大 200 字符
- **明文**存储于 `manifest.json` 的 `password_hint` 字段（不加密），方便导入时展示
- 提示词**不得包含密码本身**（前后端均需做基础校验，如提示词与密码的相似度检测）

### 校验规则

| 场景 | 规则 |
|------|------|
| 自定义密码 | 最小 8 位，必须含字母+数字，**与 Vault 主密码不同**，两次输入一致 |
| 密码强度提示（P1） | 弱/中/强，弱密码需二次确认 |

### 明文导出（未来）

> **审批决策（2026-06-05）**：明文 JSON 导出需经过三重确认，且文件自动设置 `chmod 600`。

当前无实际需求，降级为未来。待需要时可参考以下流程实现：

```
用户选择"明文 JSON 导出"
    ↓
第一重：风险警告对话框
  "[警告] 明文导出意味着您的数据将以未加密的 JSON 格式保存..."
  [取消]  [我了解风险，继续]
    ↓
第二重：密码重新验证
  "请输入主密码以确认明文导出"
    ↓
第三重：审计日志记录
  明文导出操作写入 audit_log
    ↓
导出完成 → chmod 600
```

## 4. 导入功能

### P0 导入流程（防御性默认）

```
① 选择 .solosoul 文件
② 输入导出密码 → 解密 payload.enc
③ 确认导入（增量导入：跳过已有对象，保留现有数据）
④ 完成
```

**关键决策**：P0 导入的默认策略为 **SkipExisting**（跳过已有对象）。这是防御性默认（defensive default）：在缺乏撤销机制且"导入前自动静默备份"尚未实现的情况下，默认覆盖是数据丢失的单向门。`SkipExisting` 的最坏情况是"某些对象未被更新"，而不是"丢失了现有对象"。前者可修复，后者不可逆。

### 模板重建的失败边界（RF-018）

按内容哈希复用已有模板；需要保留原始 ID 或派生新 ID 时，查询错误必须向上传播，不能当作“模板不存在”。RF-021 将新增模板与对象、历史、HLC 一起提交：映射只引用冻结视图中已存在的模板或本批次已计划的新增模板；任一数据库写入失败，先前本批模板也全部回滚，不进入附件阶段。

### 导入结果与部分提交（RF-020）

`import_execute_advanced` 与内部导入返回 `ImportResult`：保留 `objectCount` / `attachmentCount`，增加 `status`（`complete` / `partial` / `notCommitted`）、`templateCount`、`snapshotCount`、`preferencesImported`、`attachmentFilesWritten`、`failureStage` 和固定 `errorCode`。对象、模板和快照仅在数据库 COMMIT 成功后发布计数；附件只有对象元数据保存成功才计入 `attachmentCount`，已写文件单独计数，不能据此宣称关联成功。失败阶段覆盖读取解密、模板、对象、历史、附件、偏好设置，不将原始数据库错误、路径或包内字段值放入结果。

数据库批次任一步失败均返回 `notCommitted`，本批模板、对象、快照计数为零；旧对象、旧历史及 HLC 保持。批次提交之后的附件、偏好设置失败仍报告真实已提交结果并可为 `partial`，不承诺整包原子性；RF-022 的持久恢复只续执行冻结任务的剩余阶段，不能将已提交数据库回退为未提交。旧包中不可解析的历史条目继续按既有兼容规则跳过，存储失败则不可跳过。

普通导入在部分完成时刷新已提交数据、显示实际数量，保留源包与选择；只有完整成功才清理导入缓存并显示成功。云端自动/手动导入只有 `complete` 才推进水线并清理待导入源。恢复结果携带同一状态，部分完成保留账户和源包，不发送 `done` 或弹出恢复成功提示。账户创建与导入是独立阶段，`notCommitted` 表示导入阶段未提交数据。

选择契约：`selections: null` 表示全量对象，`[]` 表示不选对象；普通界面发送显式选择数组。`selectedAttachmentIds` 同理，`objectStrategies` 使用对象（无覆盖时 `{}`）。

### GUI KeepBoth 的选择与引用映射（RF-1063）

GUI 的单对象覆盖只发送与全局策略不同的项。预建新 ID 映射必须采用与对象导入主循环相同的 `objectStrategies[id] ?? strategy`，只包含本次实际选中的非空源 ID。全局 KeepBoth 配合空 `{}` 覆盖表，也必须先建立统一映射。

父子 ID、嵌套关系字段与已选择附件共用此映射；一个包中重复源 ID 继续使用同一最终映射，按原包顺序写记录、附加历史和递增名称。`selections: null` 为全量，`[]` 无映射；未勾选对象不生成新 ID，已选对象指向本地未选目标时保留其原 ID，未选对象的记录、历史及实体附件保持。

英文名称使用 ` (Imported)`，中文使用 `（导入）`，同名后续条目在完整后缀后加 ` 2` 等序号。本项不更改数据库提交顺序、Core/CLI 策略或附件恢复幂等。未选目标原本不在本地时的跨范围引用策略仍保留原行为，不由此声称已解决。验证见 [RF-1063 执行记录](../REFACTOR_EXECUTION_REPORT_2026-09-25.md#rf-1063)。

### 数据库批次与准备视图（RF-021）

KDF、ZIP 解密、包解析、模板映射、对象名称和历史操作在事务外准备。Vault 捕获同一只读事务中的加密原始行与元数据，视图不保留数据密钥；严格解析由实际策略按旧读取边界触发。未使用的坏对象、软删除记录或模板不能新增导入失败；KeepBoth 的活跃对象列表、Core Skip 的原 15 列 metadata 查询及必需的模板读取仍严格传播错误，不能默认成空集合。

最终写入同时验证原会话、原 VaultStore 实例与账户、同连接 `total_changes` 和外部连接 `main.data_version`。准备后数据变化则拒绝旧计划，不能重新选择新账户或覆盖新数据。一个 `BEGIN IMMEDIATE` 事务依次写新增模板、有序对象、历史 Append/Replace、对应 HLC，最后 COMMIT；故障、历史删除或 COMMIT 失败都回滚整个数据库批次。相同主键属于其他账户时明确拒绝。 空选择或全 Skip 的空数据库批次仍验证实例、账户、原会话、解锁及修订并显式提交，但不读取无关的 local node/HLC；非空批次仍严格拒绝损坏 HLC。

GUI 三种策略与逐对象 override 保持，重复源 ID 按原包顺序在准备中的记录上继续判断、命名和替换；KeepBoth 共用 RF-1063 映射与原中英文后缀。Overwrite 只有存在有效包历史时才替换完整旧历史；缺失、空或全坏包历史只追加初始快照。GUI 计数为提交后的唯一对象 ID、新增模板 ID 和实际快照 INSERT 数，后续同 ID Replace 删除的本批快照仍属于已执行 INSERT。

Core/CLI 保留 Skip 的批前活跃 ID 判断、Overwrite 与 Merge 等价、重复新 ID 每次写操作计数以及旧历史保持，不导入包历史。Core 的 `usize`/`Err` 返回契约继续存在，数据库提交后附件或偏好失败仍可能返回 Err；未将其误称为 GUI 的结构化部分完成结果。准备视图增加的内存与大账户耗时尚未实测。

### 持久附件导入任务（RF-022）

普通导入、手动/自动云快照和 CLI 生产入口使用稳定操作 ID。源 proof 的 SHA256/长度来自 Native 拥有的同一加密字节副本，后续包解析读取该副本；不能先 hash 原路径，再重新打开原路径导入。请求 fingerprint 固定策略、范围、逐对象覆盖和 locale，区别 `null` 与 `[]`，不包含口令或 Native 路径。Host 请求不包含展示源名；CLI 保留源文件名作为其冻结选项。Resume 可重新选择相同 proof 的包，且不重新解释选项。

标准 Fresh 在原 `VaultSession` 门闩内用同一 SQLite COMMIT 接纳业务批次与 journal，包含 KeepBoth 映射、按 ZIP ordinal 稳定生成的目标附件 UUID、安全文件名及本地附件基线。敏感计划、结果和 steps 随账户密钥加密；密码、包密钥和会话密钥不持久化。数据库阶段保留旧对象可用的本地附件集合，新对象不直接启用包内来源路径；零附件选择保持原集合。

附件先写账户密钥加密 staging，记录实际密文 proof 和明文长度；按原 ZIP 顺序完成文件发布后才按 owner 激活集合。发布使用不覆盖目标的文件动作，重试校验归属 marker、当前附件钥 AEAD、密文 hash/长度及存储 epoch；未知目标不能覆盖。元数据提交读取当前对象，仅更新 `__attachments`、版本/时间和 HLC，保留同时改变的其他字段；账户、删除状态或附件基线冲突拒绝旧计划。发布已成功但阶段 SQL COMMIT 失败时，结果仍记录实际已落盘文件，不能把文件数算作已激活附件。

阶段为 `recordsCommitted → attachments → preferences → complete`，无对应工作时可跳过中间阶段。accepted 的空业务批次 journal 后续失败同样是 `partial`。一致请求的同一 ID 不重复对象、历史或附件，Complete 只返回该任务原完成结果，不重新创建用户随后删除的文件；这些数量是任务提交进度，不能当作当前仍存在的实体数。独立新 Fresh ID 的 KeepBoth 继续创建副本。GUI 对象/模板计数为唯一提交 ID；CLI 来源保留原 Core 每次写操作计数；CLI 续接其他来源时保留 Host 的唯一对象计数，旧 Direct/无附件 key 的一次性 API 保留原兼容行为，不获得持久恢复保证。GUI 对象策略与包历史迁移仍由 RF-024 承接。

IPC `import_operations_list({accountId})` 只列 pending；`import_operation_get({accountId,operationId})` 可读 Complete；`import_operation_resume({accountId,operationId,sourcePath:null|string,password:null|string})` 不接收新策略或选择。摘要只返回操作 ID、展示源名、阶段、来源 kind、时间、已提交结果与 `sourceRequired/passwordRequired`，不公开 Native plan、root、路径写许可或密钥。普通任务尚有 Planned 附件或待解包偏好时需要同 proof 的源和口令；所有所需材料已独立保留时不再索取。锁定/换账户会使旧 worker 令牌失效；重新解锁后用新 Session 对同一任务恢复。

Recovery 随机包口令不能通过现有协议重新取得。专用 handoff 必须在业务/journal COMMIT 之前完整准备所有账户加密 stages 和偏好材料；读取、AEAD 或准备失败直接返回，未产生业务提交。接纳后的 journal 不依赖原随机包口令。ready 前丢失凭证需要重新认证主机，并以新 Fresh 包导入已解锁的匹配账户；不能创建/覆盖账户、重设密码或把新 source proof 当作旧任务 Resume。现有传输协议不因此扩展。

已接入 worker 的 root activity 随真实 worker/准备材料寿命保持，目录维护不只读取一次 pending 计数。未完成任务阻止改密、KDF 升级及账户删除；换钥重写 journal 的全部加密域，探针包含仅有 journal 密文的库。Complete 和 Abandoned 中 MetadataCommitted 附件纳入受控换钥；Abandoned 未激活文件跳过，不冒充已可用附件。

本项没有 root relocation 协议。目录切换遇到任何本项 journal 返回绑定目录错误，Complete/Abandoned 也不移动；SAF 失效时原 cache root 保留，避免拆开 journal、stages、marker 和附件引用。首启初始化由 Native 限为 placeholder，首同步失败恢复可重试状态。此准入仅协调已接入的本进程 RF022 任务，不替代 RF905 的全路径/跨进程排他；旧未标记文件归属仍属 RF903。

验证状态见 [RF-022 执行任务](../REFACTOR_EXECUTION_REPORT_2026-09-25.md#rf-022)。SQL 故障与实际 child checkpoint 退出/重开分别提供证据；Windows Rust、Hook 和组件测试不证明 Android SAF、真实文件选择器或多端 UI 已运行，未执行的平台条件不改成通过。

## 6. 加密与密钥派生

### 主 Payload 加密（P0）

- 算法：AES-256-GCM
- 密钥派生：Argon2id（通过 `solosoul_crypto::kdf::derive_key`）
- Salt：随机 16 字节，明文存储于 `manifest.json` 的 `salt_hex` 字段

### 偏好数据加密（P2）

`preferences.enc` 的密钥必须通过 **HKDF-SHA256** 从主导出密钥派生，禁止直接使用密码拼接字符串的自定义方案。

```
prefs_key = HKDF-SHA256(
    master_key = derive_export_key(password, salt),
    salt = salt,
    info = "solosoul:preferences:v1"
)
```

**理由**：
- 标准 HKDF 提供密码学安全的密钥分离
- `info` 参数确保 preferences 密钥与 payload 密钥在密码学上独立
- 避免实现者自行设计 `"{}_prefs_salt"` 等非标准派生逻辑

### 附件加密（P1）

附件统一使用 HKDF-SHA256 从主导出密钥派生子密钥，所有附件共享该密钥但每附件使用独立 nonce。

```
attachments_key = HKDF-SHA256(
    master_key = derive_export_key(password, salt),
    salt = salt,
    info = "solosoul:attachments:v1"
)
```

- 加密格式：`[12-byte nonce] + [AES-256-GCM ciphertext] + [16-byte auth tag]`
- 流式加密：附件 > 10 MB 时采用 64 KB 分块流式加密（详见 §10.2.4 与 §10.7.3）

## 7. 与备份服务的区别

| 维度 | 备份服务 | 导出服务 |
|------|---------|---------|
| 目的 | 本地时间点恢复 | 跨设备迁移、分享给第三方 |
| 范围 | 当前 Vault 的全部 Profile 条目，不包含对象、模板或附件文件 | 可选（页面/对象（含附件）） |
| 文件保护 | 2.0 JSON 清单，无单独加密；GUI 为 `data_b64`，CLI 为 `data` 字节数组，Base64 仅为编码 | 使用独立导出密码加密（必须与主密码不同） |
| 存储位置 | `~/.solosoul/backups/` | 用户选择任意路径 |

---

### 7.1 Profile 备份共享格式与恢复边界

RF-013 由 `solosoul_core::backup` 统一清单、条目和编解码规则。编码器接收完整 Profile 集合及时间，GUI 选择 Base64，CLI 选择字节数组；两端都继续写 `version: "2.0"`，每条只写所选的载荷键，`profile_count` 由实际集合长度产生。文件路径、备份确认、CLI 私有文件写入权限与列表摘要的最佳努力展示留在各端适配器。

| 恢复输入 | 共享规则 |
|---|---|
| 清单头 | `version`、`created_at`、`profile_count` 必填，另需 `profiles` 数组；数量必须与条目数一致 |
| 版本 | 字符串 `1.0`、`2.0` 使用同一已知条目结构，其余拒绝；编码类型不用于推断版本 |
| 载荷 | 非空 `data_b64` 优先，损坏不回退；空字符串回退 `data`；显式空字符串/空数组可表示合法空内容 |
| 缺失与类型 | 两种载荷都缺失/null 时拒绝；所有已提供字段必须符合类型和字节范围，即使另一载荷具有优先级 |
| 时间与内容 | 不解释 Profile.data 内部格式，任意二进制及空内容保留；Profile 无效日期统一使用调用方传入的恢复时间，header 时间保留原字符串 |
| 顺序与 ID | 保留条目顺序、原 ID/name/version；重复 ID 按顺序保存，返回条目数量；空清单不清空 Vault |

仓库内 GUI/CLI 最初均写 2.0/数组；GUI 后续只切换为 Base64，没有变更备份版本。1.0 是本项明确接受的同结构兼容输入，并由新合成夹具验证；它不代表历史 Flutter 加密 `.backup` 或附件 sidecar 的解码支持。header、版本与数量拒绝规则是 RF-013 新增的完整性边界，不应描述成既有检查。

共享解码器不操作文件或数据库。两端完整解码成功后，按原顺序逐条调用 `save_profile`：已存在行保留原 created_at，updated_at 在保存时更新；新行使用清单 created_at；未出现的行不删除，主 Profile 不更换 ID。后续条目格式错误不再导致前缀覆盖；后续数据库写入失败仍可能留下已写入前缀，本项没有增加批量恢复事务。这里的完整性只验证清单结构、支持版本、数量和可解码性，旧格式没有校验和或签名。

## 8. 关键决策记录

| # | 决策 | 优先级 | 理由 |
|---|------|--------|------|
| 1 | 导出包统一使用单文件 `payload.enc`，不拆分多个加密文件 | **P0** | 降低开发成本和导入复杂度，数据安全不低于拆分方案 |
| 2 | 导出密码必须与主密码不同，不支持"复用主密码"模式 | **P0** | 导出文件离开本地后，复用主密码 = 主密码泄露 |
| 3 | 对象级导出不自动包含关联对象 | **P0** | 避免超出预期的数据泄露 |
| 4 | **P0 导入默认策略为 SkipExisting（跳过已有）** | **P0** | 防御性默认：在缺乏撤销机制时，避免意外覆盖导致数据丢失 |
| 5 | **IPC 命令参数使用 Struct 打包** | **P0** | 向后兼容、参数顺序安全、与前端 JSON 风格一致 |
| 6 | **导入使用 UPSERT（save_object）保留原始 ID** | **P0** | `object_create` 强制生成新 UUID 会破坏 parent_id / RelationProperty 关联 |
| 7 | manifest.json 采用开放结构（最小必需 + 兼容扩展） | **P0** | 允许向后兼容的字段扩展，如 `has_preferences`、`object_count` |
| 8 | 密码提示词明文存储于 manifest.json | **P1** | 帮助用户回忆密码，不包含密码本身 |
| 9 | 不支持增量导出 | **当前** | 复杂度收益比不高 |
| 10 | 偏好/行为数据导出降级为 P2+/未来 | **P2+** | 数据边界还在定义中，不应绑定导入导出 |
| 11 | 导入前自动静默备份从导入流程中剥离 | **未来** | 备份功能独立，不应耦合在导入流程 |
| 12 | **附件导出基于当前 properties 元数据实现（P1）** | **P1** | 等待"附件模块完全就绪"会无限期延迟功能交付；临时方案提供即时价值 |
| 13 | **附件统一加密（方案 B），HKDF 派生子密钥** | **P1** | 与 preferences.enc 模式一致，安全性足够，实现复杂度可控 |
| 14 | **附件大小限制（100MB/50个/1GB/10MB）** | **P1** | 内存安全、properties 膨胀防护、磁盘空间保护、流式加密触发 |
| 15 | **附件导出遵循页面-对象-附件三级树形 UI** | **P1** | 附件必须依附对象存在，对象级选择决定附件导出范围 |

## 10. 附件导入导出子系统

> **前置阅读**：本章是导入导出功能在附件维度的详细扩展。附件元数据存储于对象 `properties["__attachments"]` 中，由 `commands/attachment.rs` 管理。

### 10.1 设计目标

附件（护照扫描件、银行对账单、合同 PDF 等）是 SoloSoul 用户数据中最敏感的部分之一。本规范明确附件在导入导出流程中的：

1. **加密方案**（必须加密，不可明文存储于导出包）
2. **密钥派生**（与 payload 密钥独立）
3. **UI 结构**（页面 → 对象 → 附件列表，三级树形，每行单独勾选）
4. **导入策略**（附件依附对象存在，对象级策略决定附件命运）
5. **删除/恢复机制**（与现有对象级附件回收站对齐）
6. **大小限制**（单附件 100MB / 单对象 50 个 / 单次导出 1GB / 流式加密阈值 10MB）

---

### 10.2 附件加密方案比较与决策

#### 10.2.1 方案对比

| 维度 | 方案 A：每个附件独立加密 | 方案 B：附件统一加密（推荐） | 方案 C：附件不加密 |
|------|----------------------|------------------------|----------------|
| **加密粒度** | 每个附件独立的 AES-256-GCM 密钥 | 所有附件共享一个 AES-256-GCM 密钥 | 不加密 |
| **密钥派生** | 每个附件通过 HKDF 独立派生 | 一次性派生附件总密钥 | 无 |
| **nonce 管理** | 每个附件需独立存储 12-byte nonce | 每个附件独立随机 nonce，附加在文件开头 | 无 |
| **安全性** | ⭐⭐⭐ 最高 | ⭐⭐☆ 足够 | ⭐☆☆ 最差 |
| **性能** | 文件数量多时派生开销大 | 派生一次即可，线性加密 | 最优 |
| **实现复杂度** | 高 | 中 | 低 |

#### 10.2.2 决策：采用方案 B（附件统一加密）

**理由**：
1. **与现有架构一致**：preferences.enc 已使用 HKDF 派生子密钥模式，附件沿用同一模式可降低心智负担。
2. **安全收益足够**：附件密钥通过 HKDF 与 payload 密钥在密码学上独立。
3. **实现成本可控**：独立加密的 nonce 管理和多密钥存储会显著增加 manifest 复杂度，而收益边际递减。
4. **用户体验**：统一加密意味着导入时只需派生一次附件密钥即可批量解密。

#### 10.2.3 密钥派生规范

```
attachments_key = HKDF-SHA256(
    master_key = derive_export_key(password, salt),
    salt       = salt,
    info       = b"solosoul:attachments:v1"
)
```

#### 10.2.4 单个附件的加密格式

```
attachments/{objectId}/{attachmentId}.enc
┌─────────────────────────────────────────┐
│  12 bytes   │  N bytes        │ 16 bytes │
│  nonce      │  ciphertext     │ auth tag │
└─────────────────────────────────────────┘
```

- **总大小**：原始文件大小 + 28 字节（12 nonce + 16 tag）

### 10.5 后端实现规范

#### 10.5.1 ExportScope 扩展

```rust
    pub include_preferences: bool,
    pub include_behavioral: bool,
}
```

#### 10.5.2 附件导出流程

1. 收集选中对象 → `collect_scope_objects()`
2. 对每个对象，读取 `properties["__attachments"]` 元数据
3. 过滤附件：跳过 soft-deleted；如 `selected_attachment_ids` 非空，仅保留列表中的附件
4. 派生附件密钥：`derive_hkdf_key(&master_key, &salt, b"solosoul:attachments:v1")`
5. 对每个附件：读取原始文件 → 生成 nonce → AES-256-GCM 加密 → 写入 ZIP
6. 更新 manifest

#### 10.5.3 附件导入流程

1. 解析 manifest，检查 `has_attachments`
2. 派生附件密钥
3. 对每个导入对象：从 `properties["__attachments"]` 获取附件列表 → 逐个解密 → 写入 vault 存储目录 → 更新 `vault_path`
4. 对象被 SkipExisting 跳过 → 其附件整体跳过

#### 10.5.5 解密预览调度与会话边界（RF-026）

`import_decrypt_preview` 先将密码转为 `Zeroizing<String>`，完成路径授权后保留桌面 resolver 返回的规范路径，再捕获当前账户的原 `VaultSession`。请求与密码移入 `spawn_blocking`，KDF、ZIP 流式解密、JSON 解析、摘要映射和本地冲突读取都在阻塞线程执行；服务读锁及会话门闩仅用于短校验，不覆盖这些耗时阶段或 `.await`。

worker 在解密前、解密后读取本地冲突前校验原会话；调度器等待结束后再次通过同一原会话接纳 DTO。锁定、切换账户或同账户重新解锁均使旧请求失败，不能转而读取新 Vault，也不能返回已构建的旧成功预览。返回之后前端消费时的请求守卫属于独立窗口，本契约只覆盖后端接纳点。

临时明文仍在原账户 Vault 目录内，沿用流式解密的 `TempDir` / `NamedTempFile` 与派生密钥擦除；预览不执行孤儿目录清扫。取消等待不会停止已经启动的阻塞任务，清理由实际 worker 结束时完成。规范路径避免再次解析原始别名，但不等同于已打开文件句柄，不提供任意同用户文件替换的排他保护。

原有密码/ZIP/密文/JSON 错误继续透传；Join 失败固定返回“导入预览任务执行失败”，不返回空预览或拼接 panic 内容。对象顺序、同名/本地改名冲突、软删对象不算冲突、软删附件过滤、preferences 声明及 `has_audit_log=false` 保持；既有批量冲突读取失败的空映射回退没有在本项收紧。该命令仍只预览，不保存对象、历史、审计或同步状态。

#### 10.5.6 高级导入调度与完成结果（RF-027）

`import_execute_advanced` 在调度前将密码移入 `Zeroizing<String>`，保留授权返回的规范源路径，捕获指定账户的原 `VaultSession`；请求中的对象选择、附件选择、全局/逐对象策略和 locale 原样移入 `ImportJob`。worker 在阻塞池内获取服务读锁，直接使用原会话调用同步导入核心；KDF、解密、解析及写入均不占用异步运行时工作线程，同步锁不跨 `.await`。同步核心继续按每次提交校验原会话，排队期间失效的旧请求不会重新捕获新账户或新解锁会话。

核心返回的 `ImportResult` 全字段保持，包括 `sessionGeneration`、三种状态、各类提交计数、失败阶段及错误码。`Some([])` 仍表示空选择，正常完成的空导入可以是 `complete` 且对象计数为 0；不能根据数量替换状态。只有 `complete` 才在短 `with_session` 校验内尝试发送现有 SAF Debounce 通知。返回结果等待期间会话失效，或完成检查时服务锁损坏，只抑制该通知，仍返回已经提交的真实结果；`partial` / `notCommitted` 不发送完成通知。此校验保护排队时点，消息队列仍为尽力发送，后续 SAF 消费任务并未因此绑定到原会话。

入口与核心的既有业务错误保持；Join 失败固定返回“导入任务执行失败”，不携带 panic 内容。此时提交情况未知，不能构造空成功或 `notCommitted` 来声称零提交。RF-021 将模板、对象、快照与 HLC 收敛为一个数据库批次；提交后的附件、偏好仍遵循 RF-020，不新增整包事务、成功事件或进度协议。

worker 仍在整段同步导入期间持服务读锁，本项不缩短目录切换等待；取消等待也不会停止已启动的 worker。临时明文的根目录、孤儿清扫及 RAII 行为保持，未将目录清扫视为并发请求的所有权隔离保证；相关并发清扫疑点另行复现。路径规范化不是打开文件句柄，不提供同用户文件替换的排他保证。

### 10.6 附件删除/恢复机制

#### 10.6.1 设计原则

与对象级回收站对齐：
1. **Soft Delete**：保留元数据，`deleted_at` 标记，物理文件不删除
2. **Hard Delete**：从 `__attachments` 移除条目，物理文件删除
3. **Restore**：清除 `deleted_at`
4. **孤儿清理**：`attachment_cleanup_orphans` 扫描删除无引用物理文件

#### 10.6.2 导出时的删除状态处理

| 场景 | 行为 |
|------|------|
| 附件已 soft-delete | **不导出** |
| 对象已 soft-delete | 对象不出现在导出列表，其附件自然不导出 |
| 导入包中的附件 | 导入后均为活跃状态（`deleted_at = null`） |

#### 10.6.3 导入时的冲突处理

遵循对象级策略：SkipExisting → 附件跳过；Overwrite → 附件覆盖；Merge → 附件列表合并。

### 10.7 附件大小限制

#### 10.7.1 限制规则（已生效）

| 限制类型 | 阈值 | 超限行为 |
|---------|------|---------|
| **单附件大小上限** | 100 MB | 拒绝导出，返回错误 |
| **单对象附件总数** | 50 个 | `attachment_save` 拒绝新增；导出跳过超出部分 |
| **单次导出总大小** | 1 GB | `export_execute` 拒绝执行 |
| **流式加密阈值** | 10 MB | ≤10MB 全量加密；>10MB 流式分块加密（64KB 块） |

#### 10.7.2 设计理由

1. **单附件 100MB**：防止内存溢出（加密需读入内存）
2. **单对象 50 个附件**：防止 `properties` JSON 膨胀
3. **单次导出 1GB**：防止 ZIP 创建耗尽磁盘空间
4. **流式加密 10MB**：保持应用响应性

#### 10.7.3 流式 AES-256-GCM 加密规范

当附件大小 > 10 MB 时，采用分块流式加密：

```
attachments/{objectId}/{attachmentId}.enc
┌──────────────────────────────────────────────────────────┐
│ 12 bytes │ 8 bytes     │ N × (64KB + 16 bytes) │ 0~64KB+16 │
│ nonce    │ chunk_count │ chunk ciphertexts     │ final chunk│
└──────────────────────────────────────────────────────────┘
```

- **chunk_size**：64 KB
- **chunk_count**：大端序 u64，附加在 nonce 之后
- **每块格式**：`[ciphertext] + [16-byte auth tag]`
- **nonce 处理**：base_nonce XOR chunk_index，确保每块独立认证

#### 10.7.4 大小校验位置

| 校验点 | 代码位置 |
|--------|---------|
| 单对象附件总数 | `attachment_save` |
| 单附件大小 | `export_execute` 附件收集阶段 |
| 单次导出总大小 | `export_execute` 附件收集完成后 |
| 流式加密分支 | `export_execute` 单个附件加密时 |

#### 10.7.5 导出文件发布（RF-017）

Core `execute_encrypted_export` 与 LegacyDirect 兼容入口在最终目标的同一目录创建随机临时输出，继续流式加密写入 ZIP。附件校验与加密、ZIP `finish`、文件 `flush` / `sync_all` 全部成功并关闭写句柄后，才在原会话的短时 `with_session` 校验内替换目标；成功审计记录在替换之后。

准备、写入、收尾、同步或发布返回错误时，已有目标字节保持不变，临时输出由 RAII 清理。Windows 使用支持替换的同卷移动；目标被其他进程禁止删除共享时返回失败，不能先删除原文件或退化为复制覆盖。会话已失效同样拒绝发布，不记录成功导出。

此契约覆盖 Host 手动导出、云快照、恢复包共用的本地文件阶段；移动端只覆盖本地 staging，不包含后续 SAF 复制。RF-023 后旧 CLI 兼容导出共用同一原子 writer；Direct入口的发布无Session门闩，原会话校验仅适用于GUI/云/恢复。本项保证调用失败时不破坏原目标，不承诺突然断电后的目录项持久性，也不改变附件选择、包格式或大小上限。

#### 10.7.6 GUI 导出调度（RF-025）

`export_execute` 在首次等待前完成路径授权并捕获原 `VaultSession`，随后将 owned 请求（含密码）、授权路径和服务 Arc 移入阻塞线程池。密码验证/KDF、数据库读取与解密、序列化、加密压缩和文件写入均在 `spawn_blocking` 内完成；同步服务读锁仅在准备作用域和 worker 内持有，不跨越 `.await`。worker 沿用 RF-017 的原会话发布校验，排队期间锁定、切换账户或同账户重新解锁均不能使旧任务改读新会话。

业务错误保持原返回值；任务 Join 失败返回固定“导出任务执行失败”，不回传 panic 内容或成功路径。worker 仍在整个同步导出期间持服务读锁，因此本项不缩短目录热切换所需的写锁等待。当前 GUI 导出仅等待 IPC 结果，没有 `export-progress` 事件或运行中取消接口；丢弃等待不会停止已经运行的阻塞任务。临时文件仍由实际 worker 持有和清理，移动端成功后的 SAF 复制保持原流程。
