# 16 — 导入导出功能设计

> **前置阅读**：`06_数据库与服务层.md`、`13_用户数据边界与加密存储.md`、`05_数据组织模型架构决策.md`
> **架构说明**：本规范中"对象"指 objects 表中的记录（见 05_数据组织模型架构决策.md — 扁平模型），不再使用旧 Profile 概念。导出基于 VaultStore 的对象查询与序列化；导入基于 VaultStore 的 UPSERT（`save_object`）操作，保留原始对象 ID 以确保关联关系不断裂。
> **Manifesto 对齐**：用户主权 | 隐私优先 | 安全默认
> **源文档**：`tauri_refactor/导入导出功能重构设计.md`

## 1. 设计原则

### 为什么细化到"对象层"为止，不开放字段级别？

1. **数据完整性**：护照对象包含姓名、国籍、护照号等字段，共同构成完整记录。导出"只有姓名和国籍的护照"无意义。
2. **关系完整性**：对象可能包含 RelationProperty 指向其他对象，字段级导出会产生孤立引用。
3. **用户体验**：字段级选择让导出 UI 极其复杂（每个对象展开几十个字段），违背"最少惊喜"。
4. **粒度足够**：对象级导出已满足"只导出护照"的实际需求。

### 导出范围的三层结构

```
身份数据
├── 页面层 → "导出我的所有旅行数据"
├── 对象层 → "导出我的护照"（可勾选多个对象）
└── 附件层 → "只导出扫描件，不导出照片"

偏好数据
├── 视觉偏好（主题、颜色、字体）
├── 行为偏好（锁定超时、生物识别、删除确认）
├── 内容偏好（语言、日期格式、时区）

行为记录
├── 操作日志（CRUD、敏感度变更）
├── 搜索历史
├── AI 对话历史
```

### 对象选择机制

扁平模型下，页面内的对象列表支持以下选择方式：

| 选择方式 | 说明 |
|---------|------|
| **手动勾选** | 页面列表中逐项勾选/取消 |
| **全选/反选** | 页面的批量操作按钮 |
| **按标签筛选后勾选** | 先按 `tags_json` 筛选（如"只显示标签为 `2025日本` 的对象"），再对筛选结果勾选 |
| **选择所有** | 勾选"页面"即选中该页面下的全部对象 |

```typescript
interface ExportScope {
  selectedPageIds: string[];          // 整页全选（section_type，如 travel/financial）
  selectedObjectIds: string[];        // 手工勾选的对象 ID
  selectedTags: string[];             // 按标签筛选（与 selectedObjectIds 交集生效）
  includeAttachments: boolean;        // 是否包含附件
  includePreferences: boolean;        // 偏好数据（P2）
  includeBehavioral: boolean;         // 行为记录（未来）
}
```

### 数据安全提示（P1）

导出包含 `sensitive`/`critical` 级别字段时，在导出确认界面显示警告横幅：
```
所选数据包含高敏感度字段，导出文件使用密码加密，请妥善保管。
```
LLM API 密钥作为 `critical` 级别字段，由通用敏感度警告覆盖，不单独处理。

### 实现优先级

| 功能 | 优先级 | 理由 |
|------|--------|------|
| 页面层 + 对象层导出（加密） | **P0（必须）** | 用户数据的核心备份/迁移路径 |
| 导入对象数据（含解密） | **P0（必须）** | 与导出配对，构成完整迁移闭环 |
| 导出密码（自定义密码） | **P0（必须）** | 导出文件加密安全底线 |
| 导入默认策略为 SkipExisting（防御性默认） | **P0（必须）** | 避免意外覆盖用户现有数据 |
| 敏感度警告 | **P1（重要）** | 安全合规，但缺了不影响功能 |
| 导入密码提示词展示 | **P1（重要）** | 帮助用户回忆密码 |
| 导入预览 + 冲突检测 | **P1（重要）** | 提升导入 UX，避免数据覆盖 |
| 导入策略选择（保留当前/覆盖/合并） | **P1（重要）** | 用户掌控数据命运 |
| 标签筛选导出（selected_tags） | **P1（重要）** | 后端已就绪，前端补充 UI 即可闭环 |
| 附件层导出 | **P1（重要）** | 基于当前 properties 中的附件元数据实现，提供即时价值 |
| 偏好/行为数据导出 | **P2+** | 数据边界还在定义中，不应绑定导入导出 |
| 明文 JSON 导出（三重确认） | **未来** | 合规场景，当前无实际需求 |
| 导入前自动创建静默备份 | **未来** | 备份功能独立，不应耦合在导入流程 |

## 2. 导出包格式

### P0 核心版

```
{scopeName}_export.solosoul (ZIP)
├── manifest.json           # 明文：版本、范围、时间、应用版本
│   ├── version: "2.0"
│   ├── export_scope: "partial" | "full"
│   ├── selected_pages: string[]
│   ├── selected_objects: string[]
│   ├── export_time: string
│   ├── export_platform: string
│   ├── export_app_version: string
│   ├── salt_hex: string              # 解密 payload.enc 必需的 salt
│   ├── password_hint: string         # 可选，帮助用户回忆密码
│   ├── has_attachments: boolean
│   ├── has_preferences: boolean      # 扩展字段，指示是否包含 preferences.enc
│   └── extra_files: string[]         # 扩展文件清单
├── payload.enc             # 加密：所有选中对象的 JSON 数据（单文件，统一加密）
└── attachments/             # 可选（P1 实现，详见 §10）
    └── {objectId}/          # 按对象分组
        └── {attachmentId}.enc   # 加密附件（AES-256-GCM，详见 §10.2）
```

**简化理由**：加密 payload 即可保证数据安全，细分多个加密文件（preferences.enc、audit_log.enc、search_history.enc、ai_conversation.enc、sensitivity_map.enc 等）增加了开发成本和导入解析复杂度，收益微薄。P0 统一使用单一 `payload.enc`，未来扩展时如需新增数据类别，在 `manifest.json` 中通过 `extra_files` 字段声明。

### manifest.json 最小定义（开放结构）

manifest.json 采用**最小必需字段 + 向后兼容扩展**的开放结构。以下字段为必需：

```json
{
  "version": "2.0",
  "export_scope": "partial",
  "selected_pages": ["travel", "financial"],
  "selected_objects": ["obj_abc123", "obj_def456"],
  "object_count": 2,
  "export_time": "2026-06-07T14:30:00Z",
  "export_platform": "macos",
  "export_app_version": "2.1.0",
  "salt_hex": "a1b2c3d4...",
  "password_hint": "",
  "has_attachments": false,
  "has_preferences": false,
  "extra_files": []
}
```

**开放结构原则**：
- 解析器必须识别上述必需字段
- 解析器应**忽略**不认识的字段（forward compatibility）
- 新增字段时，minor version 递增（如 `"2.1"`）
- `salt_hex` 为 P0 必需字段，用于解密 `payload.enc`

### 未来扩展版（P2+）

当需要支持 preferences、audit log 等额外数据时，在 ZIP 中新增对应加密文件：

```
{scopeName}_export.solosoul (ZIP)
├── manifest.json           # 新增 extra_files 描述所含文件清单
├── payload.enc             # 核心：所有对象的 JSON 数据
├── preferences.enc         # 用户偏好（可选）
├── audit_log.enc           # 审计日志（可选）
├── ai_conversations.enc    # AI 对话历史（可选）
├── attachments/
│   └── {fileId}.enc
```

> **附件支持说明**：P1 附件导入导出基于对象 `properties` 中的 `__attachments` 元数据实现。该方案在当前数据模型下可工作，未来附件存储系统重构时，仅需替换元数据读取逻辑，导出包格式（`attachments/` 目录结构）保持不变。

## 3. 导出密码设计

### 密码模式（P0 仅支持自定义密码）

| 模式 | 优先级 | 说明 |
|------|--------|------|
| **使用自定义密码** | **P0** | 必须与主密码不同。最小 8 位。加密导出包的密钥由此密码派生 |
| **使用主密码** | **未来** | 复用 Vault 主密码。需评估导出包泄露风险 |

> **关键决策**：P0 仅支持自定义密码模式。导出文件离开本地设备后，如果复用主密码，导出包泄露 = 主密码泄露。导入导出应始终使用独立密码。

### 密码提示词（P1）

- 可选字段，最大 200 字符
- **明文**存储于 `manifest.json` 的 `password_hint` 字段（不加密），方便导入时展示
- 提示词**不得包含密码本身**（前后端均需做基础校验，如提示词与密码的相似度检测）

### 校验规则

| 场景 | 规则 |
|------|------|
| 自定义密码 | 最小 8 位，必须含字母+数字，**与 Vault 主密码不同**，两次输入一致 |
| 密码强度提示（P1） | 弱/中/强，弱密码需二次确认 |

### 明文导出（未来）

> **审批决策（2026-06-05）**：明文 JSON 导出需经过三重确认，且文件自动设置 `chmod 600`。

当前无实际需求，降级为未来。待需要时可参考以下流程实现：

```
用户选择"明文 JSON 导出"
    ↓
第一重：风险警告对话框
  "[警告] 明文导出意味着您的数据将以未加密的 JSON 格式保存..."
  [取消]  [我了解风险，继续]
    ↓
第二重：密码重新验证
  "请输入主密码以确认明文导出"
    ↓
第三重：审计日志记录
  明文导出操作写入 audit_log
    ↓
导出完成 → chmod 600
```

## 4. 导入功能

### P0 导入流程（防御性默认）

```
① 选择 .solosoul 文件
② 输入导出密码 → 解密 payload.enc
③ 确认导入（增量导入：跳过已有对象，保留现有数据）
④ 完成
```

**关键决策**：P0 导入的默认策略为 **SkipExisting**（跳过已有对象）。这是防御性默认（defensive default）：在缺乏撤销机制且"导入前自动静默备份"尚未实现的情况下，默认覆盖是数据丢失的单向门。`SkipExisting` 的最坏情况是"某些对象未被更新"，而不是"丢失了现有对象"。前者可修复，后者不可逆。

### P1+ 增强流程

```
① 选择 .solosoul 文件
② 读取密码提示词（无需密码）并展示  ← P1 新增
③ 输入导出密码 → 解密预览            ← P1 增强
   ├── 展示即将导入的对象数量 + 名称列表
   └── 冲突检测：标记与现有对象冲突的条目
④ 导入策略选择                        ← P1 新增
   ├── 保留当前（跳过冲突条目，P0 默认行为）
   ├── 覆盖（用导入包替换全量数据）
   └── 合并（导入覆盖冲突项，保留未冲突项）
⑤ 确认导入
```

### 跨范围引用处理

对象级导出时，RelationProperty 的目标对象可能不在导出范围内 → 导入时转为 `[引用对象未导出: {id}]` 文本备注。

## 5. IPC 命令

### 参数风格约定

所有 IPC 命令采用 **Struct 打包参数**风格：
- 超过 2 个业务参数的命令，统一封装为 Request Struct
- 便于向后兼容扩展（新增可选字段不影响现有调用方）
- 与前端 JSON 对象调用风格天然对应

### P0 命令集

## 6. 加密与密钥派生

### 主 Payload 加密（P0）

- 算法：AES-256-GCM
- 密钥派生：Argon2id（通过 `solosoul_crypto::kdf::derive_key`）
- Salt：随机 16 字节，明文存储于 `manifest.json` 的 `salt_hex` 字段

### 偏好数据加密（P2）

`preferences.enc` 的密钥必须通过 **HKDF-SHA256** 从主导出密钥派生，禁止直接使用密码拼接字符串的自定义方案。

```
prefs_key = HKDF-SHA256(
    master_key = derive_export_key(password, salt),
    salt = salt,
    info = "solosoul:preferences:v1"
)
```

**理由**：
- 标准 HKDF 提供密码学安全的密钥分离
- `info` 参数确保 preferences 密钥与 payload 密钥在密码学上独立
- 避免实现者自行设计 `"{}_prefs_salt"` 等非标准派生逻辑

### 附件加密（P1）

附件统一使用 HKDF-SHA256 从主导出密钥派生子密钥，所有附件共享该密钥但每附件使用独立 nonce。

```
attachments_key = HKDF-SHA256(
    master_key = derive_export_key(password, salt),
    salt = salt,
    info = "solosoul:attachments:v1"
)
```

- 加密格式：`[12-byte nonce] + [AES-256-GCM ciphertext] + [16-byte auth tag]`
- 流式加密：附件 > 10 MB 时采用 64 KB 分块流式加密（详见 §10.2.4 与 §10.7.3）

## 7. 与备份服务的区别

| 维度 | 备份服务 | 导出服务 |
|------|---------|---------|
| 目的 | 本地时间点恢复 | 跨设备迁移、分享给第三方 |
| 范围 | 全量 | 可选（页面/对象（含附件）） |
| 加密密钥 | 当前 Vault 主密钥 | 独立导出密码（必须与主密码不同） |
| 存储位置 | `~/.solosoul/backups/` | 用户选择任意路径 |

## 8. 关键决策记录

| # | 决策 | 优先级 | 理由 |
|---|------|--------|------|
| 1 | 导出包统一使用单文件 `payload.enc`，不拆分多个加密文件 | **P0** | 降低开发成本和导入复杂度，数据安全不低于拆分方案 |
| 2 | 导出密码必须与主密码不同，不支持"复用主密码"模式 | **P0** | 导出文件离开本地后，复用主密码 = 主密码泄露 |
| 3 | 对象级导出不自动包含关联对象 | **P0** | 避免超出预期的数据泄露 |
| 4 | **P0 导入默认策略为 SkipExisting（跳过已有）** | **P0** | 防御性默认：在缺乏撤销机制时，避免意外覆盖导致数据丢失 |
| 5 | **IPC 命令参数使用 Struct 打包** | **P0** | 向后兼容、参数顺序安全、与前端 JSON 风格一致 |
| 6 | **导入使用 UPSERT（save_object）保留原始 ID** | **P0** | `object_create` 强制生成新 UUID 会破坏 parent_id / RelationProperty 关联 |
| 7 | manifest.json 采用开放结构（最小必需 + 兼容扩展） | **P0** | 允许向后兼容的字段扩展，如 `has_preferences`、`object_count` |
| 8 | 密码提示词明文存储于 manifest.json | **P1** | 帮助用户回忆密码，不包含密码本身 |
| 9 | 不支持增量导出 | **当前** | 复杂度收益比不高 |
| 10 | 偏好/行为数据导出降级为 P2+/未来 | **P2+** | 数据边界还在定义中，不应绑定导入导出 |
| 11 | 导入前自动静默备份从导入流程中剥离 | **未来** | 备份功能独立，不应耦合在导入流程 |
| 12 | **附件导出基于当前 properties 元数据实现（P1）** | **P1** | 等待"附件模块完全就绪"会无限期延迟功能交付；临时方案提供即时价值 |
| 13 | **附件统一加密（方案 B），HKDF 派生子密钥** | **P1** | 与 preferences.enc 模式一致，安全性足够，实现复杂度可控 |
| 14 | **附件大小限制（100MB/50个/1GB/10MB）** | **P1** | 内存安全、properties 膨胀防护、磁盘空间保护、流式加密触发 |

## 10. 附件导入导出子系统

> **前置阅读**：本章是导入导出功能在附件维度的详细扩展。附件元数据存储于对象 `properties["__attachments"]` 中，由 `commands/attachment.rs` 管理。

### 10.1 设计目标

附件（护照扫描件、银行对账单、合同 PDF 等）是 SoloSoul 用户数据中最敏感的部分之一。本规范明确附件在导入导出流程中的：

1. **加密方案**（必须加密，不可明文存储于导出包）
2. **密钥派生**（与 payload 密钥独立）
3. **UI 结构**（页面 → 对象 → 附件列表，三级树形，每行单独勾选）
4. **导入策略**（附件依附对象存在，对象级策略决定附件命运）
5. **删除/恢复机制**（与现有对象级附件回收站对齐）
6. **大小限制**（单附件 100MB / 单对象 50 个 / 单次导出 1GB / 流式加密阈值 10MB）

---

### 10.2 附件加密方案比较与决策

#### 10.2.1 方案对比

| 维度 | 方案 A：每个附件独立加密 | 方案 B：附件统一加密（推荐） | 方案 C：附件不加密 |
|------|----------------------|------------------------|----------------|
| **加密粒度** | 每个附件独立的 AES-256-GCM 密钥 | 所有附件共享一个 AES-256-GCM 密钥 | 不加密 |
| **密钥派生** | 每个附件通过 HKDF 独立派生 | 一次性派生附件总密钥 | 无 |
| **nonce 管理** | 每个附件需独立存储 12-byte nonce | 每个附件独立随机 nonce，附加在文件开头 | 无 |
| **安全性** | ⭐⭐⭐ 最高 | ⭐⭐☆ 足够 | ⭐☆☆ 最差 |
| **性能** | 文件数量多时派生开销大 | 派生一次即可，线性加密 | 最优 |
| **实现复杂度** | 高 | 中 | 低 |

#### 10.2.2 决策：采用方案 B（附件统一加密）

**理由**：
1. **与现有架构一致**：preferences.enc 已使用 HKDF 派生子密钥模式，附件沿用同一模式可降低心智负担。
2. **安全收益足够**：附件密钥通过 HKDF 与 payload 密钥在密码学上独立。
3. **实现成本可控**：独立加密的 nonce 管理和多密钥存储会显著增加 manifest 复杂度，而收益边际递减。
4. **用户体验**：统一加密意味着导入时只需派生一次附件密钥即可批量解密。

#### 10.2.3 密钥派生规范

```
attachments_key = HKDF-SHA256(
    master_key = derive_export_key(password, salt),
    salt       = salt,
    info       = b"solosoul:attachments:v1"
)
```

#### 10.2.4 单个附件的加密格式

```
attachments/{objectId}/{attachmentId}.enc
┌─────────────────────────────────────────┐
│  12 bytes   │  N bytes        │ 16 bytes │
│  nonce      │  ciphertext     │ auth tag │
└─────────────────────────────────────────┘
```

- **总大小**：原始文件大小 + 28 字节（12 nonce + 16 tag）

#### 10.5.2 附件导出流程

1. 收集选中对象 → `collect_scope_objects()`
2. 对每个对象，读取 `properties["__attachments"]` 元数据
3. 过滤附件：跳过 soft-deleted；如 `selected_attachment_ids` 非空，仅保留列表中的附件
4. 派生附件密钥：`derive_hkdf_key(&master_key, &salt, b"solosoul:attachments:v1")`
5. 对每个附件：读取原始文件 → 生成 nonce → AES-256-GCM 加密 → 写入 ZIP
6. 更新 manifest

#### 10.5.3 附件导入流程

1. 解析 manifest，检查 `has_attachments`
2. 派生附件密钥
3. 对每个导入对象：从 `properties["__attachments"]` 获取附件列表 → 逐个解密 → 写入 vault 存储目录 → 更新 `vault_path`
4. 对象被 SkipExisting 跳过 → 其附件整体跳过

### 10.6 附件删除/恢复机制

#### 10.6.1 设计原则

与对象级回收站对齐：
1. **Soft Delete**：保留元数据，`deleted_at` 标记，物理文件不删除
2. **Hard Delete**：从 `__attachments` 移除条目，物理文件删除
3. **Restore**：清除 `deleted_at`
4. **孤儿清理**：`attachment_cleanup_orphans` 扫描删除无引用物理文件

#### 10.6.2 导出时的删除状态处理

| 场景 | 行为 |
|------|------|
| 附件已 soft-delete | **不导出** |
| 对象已 soft-delete | 对象不出现在导出列表，其附件自然不导出 |
| 导入包中的附件 | 导入后均为活跃状态（`deleted_at = null`） |

#### 10.6.3 导入时的冲突处理

遵循对象级策略：SkipExisting → 附件跳过；Overwrite → 附件覆盖；Merge → 附件列表合并。

### 10.7 附件大小限制

#### 10.7.1 限制规则（已生效）

| 限制类型 | 阈值 | 超限行为 |
|---------|------|---------|
| **单附件大小上限** | 100 MB | 拒绝导出，返回错误 |
| **单对象附件总数** | 50 个 | `attachment_save` 拒绝新增；导出跳过超出部分 |
| **单次导出总大小** | 1 GB | `export_execute` 拒绝执行 |
| **流式加密阈值** | 10 MB | ≤10MB 全量加密；>10MB 流式分块加密（64KB 块） |

#### 10.7.2 设计理由

1. **单附件 100MB**：防止内存溢出（加密需读入内存）
2. **单对象 50 个附件**：防止 `properties` JSON 膨胀
3. **单次导出 1GB**：防止 ZIP 创建耗尽磁盘空间
4. **流式加密 10MB**：保持应用响应性

#### 10.7.3 流式 AES-256-GCM 加密规范

当附件大小 > 10 MB 时，采用分块流式加密：

```
attachments/{objectId}/{attachmentId}.enc
┌──────────────────────────────────────────────────────────┐
│ 12 bytes │ 8 bytes     │ N × (64KB + 16 bytes) │ 0~64KB+16 │
│ nonce    │ chunk_count │ chunk ciphertexts     │ final chunk│
└──────────────────────────────────────────────────────────┘
```

- **chunk_size**：64 KB
- **chunk_count**：大端序 u64，附加在 nonce 之后
- **每块格式**：`[ciphertext] + [16-byte auth tag]`
- **nonce 处理**：base_nonce XOR chunk_index，确保每块独立认证

#### 10.7.4 大小校验位置

| 校验点 | 代码位置 |
|--------|---------|
| 单对象附件总数 | `attachment_save` |
| 单附件大小 | `export_execute` 附件收集阶段 |
| 单次导出总大小 | `export_execute` 附件收集完成后 |
| 流式加密分支 | `export_execute` 单个附件加密时 |
