# SoloSoul 代码审查流程

> 适用于 Tauri v2 架构（Rust 后端 + TypeScript/React 前端）。
> 目标：系统性地分析、优化并修复代码库，过程需完全自动化（或半自动）并持久化记录。

---

## 核心流程

1. **全库扫描与分析**：探测死代码、可优化结构、性能瓶颈、潜在漏洞/安全风险。
2. **生成初始报告**：将发现写入 `CODE_ANALYSIS_REPORT.md`，并按优先级排序问题。
3. **迭代修复**：一次只解决一个高优先级问题 → 更新报告状态 → 提交到 Git → 继续下一问题。
4. **最终复审**：所有问题标记完成后，重新进行全面分析，生成终版报告。
5. **循环改进**：若终版报告仍有新问题，则重复步骤 3-4（形成渐进式修复循环）。

---

## 阶段 0：环境准备与初始检查

1. **确认当前目录为代码库根路径**（应包含 `tauri/`、`Cargo.toml` 等）。

2. **检查是否已存在 `CODE_ANALYSIS_REPORT.md`**：
   - 若不存在 → 进入阶段 1。
   - 若存在 → 读取报告中未解决的问题（状态 `[ ]`），按优先级继续修复（跳至阶段 3）。

3. **确保 Git 仓库干净**：
   ```bash
   git status
   ```
   如果有未提交代码，则先执行 `git commit & git push`，根据修改编写 commit message，确保本地仓库与远程仓库同步。

4. **运行项目自带检查（快速基线）**：
   ```bash
   cd tauri
   npm run check-all
   ```
   该命令会依次执行：TypeScript 类型检查 → Rust 格式化检查 → Clippy 静态分析 → ESLint → 单元测试。若此处已报错，优先修复后再进入全库分析。

## 阶段 1：全库分析（产生初始报告）

### 分析维度

#### A. 静态分析工具（优先运行）

| 工具 | 命令 | 覆盖范围 |
|------|------|----------|
| Rust Clippy | `cd tauri && cargo clippy -- -D warnings` | Rust 代码规范、性能建议、常见错误 |
| Rust Format | `cd tauri && cargo fmt --check` | 代码格式化一致性 |
| TypeScript | `cd tauri && npx tsc --noEmit` | 前端类型安全 |
| ESLint | `cd tauri && npm run lint` | 前端代码规范 |
| Rust Tests | `cd tauri && cargo test` | Rust 单元测试 |
| Frontend Tests | `cd tauri && npm run test` | 前端单元测试（Vitest）|

#### B. 启发式规则（人工/脚本辅助）

**死代码**：
- 未被调用的 Rust 函数（`pub` 但无外部使用需确认是否为 API）
- 未被导入的 TypeScript 模块/变量
- 不可达分支、废弃的 TODO 注释

**可优化代码**：
- 重复代码片段（相似度 > 70%）
- 过长函数（Rust > 50 行、TypeScript > 50 行非注释代码）
- 深层嵌套（> 4 层）
- 可简化的条件表达式、 match / if-let 冗余

**性能问题**：
- Rust：`Vec` 不必要的 `clone()`、频繁的 `String` 拼接、无缓存的重复计算
- TypeScript：循环中的频繁 DOM 操作、大列表无虚拟滚动、无 memo 的复杂渲染
- 数据库：循环内的 SQLite 查询（应使用事务或批量操作）
- 加密/解密：大文件未分块处理

**潜在漏洞**：
- 未过滤的用户输入（XSS 风险，前端渲染时）
- 不安全的反序列化（`serde` 的 `untagged` enum 需警惕）
- 弱加密或硬编码密钥
- 命令注入（Tauri 的 `Command` API 若拼接用户输入）
- 文件路径遍历（`tauri-plugin-fs` 读写时未校验路径）
- Rust `unsafe` 块的使用审查

**架构问题**：
- Rust crate 间循环依赖
- 前端状态管理（Zustand）与后端状态不一致
- FFI/Bridge 层错误处理缺失

### 输出报告格式（`CODE_ANALYSIS_REPORT.md`）

```markdown
# 代码分析修复报告

> 最后更新：YYYY-MM-DD HH:MM:SS
> 当前分支：`master`
> 修复轮次：1（初始分析）

## 问题清单（按优先级 P0 > P1 > P2）

| ID   | 优先级 | 类别       | 文件位置                         | 描述                                           | 状态      |
|------|--------|------------|----------------------------------|------------------------------------------------|-----------|
| P001 | P0     | 漏洞       | `tauri/src-tauri/src/auth.rs:23` | 硬编码密钥用于加密初始化                        | `[ ]` 待修复 |
| P002 | P0     | 性能       | `tauri/src/lib/api.ts:112-130`   | 循环内多次调用 Rust Command，应批量处理         | `[ ]` 待修复 |
| P003 | P1     | 死代码     | `tauri/src/components/OldModal.tsx` | 组件已无任何引用                            | `[ ]` 待修复 |
| P004 | P1     | 规范       | `tauri/src-tauri/src/vault.rs:45` | Clippy 警告：不必要的 `clone()`               | `[ ]` 待修复 |
| ...  | ...    | ...        | ...                              | ...                                            | `[ ]`      |

## 修复进度

- 已完成：0 / N
- 当前处理：无

## 详细问题描述与修复指引

（对每个问题展开，包含代码片段、影响分析、建议修复方案）
```

## 阶段 2：确定修复顺序

1. 按 **P0（严重）→ P1（中等）→ P2（轻微）** 排序。
2. 同优先级内，按依赖顺序（改动可能影响其他问题的先做）。
3. **Rust / TypeScript 分离原则**：同一轮次优先处理同一语言的问题，减少上下文切换成本。

---

## 阶段 3：迭代修复（一次一问题）

对当前优先级的第一个未解决问题（状态 `[ ]`）：

### 1. 标记进行中
在报告的「当前处理」字段填入问题 ID，并更新「最后更新」时间。

### 2. 实施修复
- 修改代码以解决问题。
- **遵循代码库现有风格**，最小化改动。
- Rust 代码需通过 `cargo fmt` 格式化。
- TypeScript 代码需通过 `prettier --write` 格式化。
- 若修复涉及 API 变化或重大重构，在报告中添加「修复备注」。

### 3. 本地验证（必须）
根据修改的栈执行对应检查：

```bash
# 若修改了 Rust 代码
cd tauri
cargo fmt
cargo clippy -- -D warnings
cargo test

# 若修改了 TypeScript 代码
cd tauri
npx tsc --noEmit
npm run lint
npm run test

# 或一键执行全部检查
npm run check-all
```

### 4. 更新报告
- 将该问题状态改为 `[x]`。
- 在问题下方添加「修复说明」（如：改了哪几行、采用的方案）。
- 更新「已完成」计数。
- 清除「当前处理」字段。

### 5. 提交到 Git（一项一提交）
**每修复一个 ID 必须单独 commit**，确保 commit 历史与问题清单一一对应，方便后续追溯与回滚。

```bash
# 仅添加与当前问题相关的文件，避免混入其他改动
git add <相关文件>
git commit -m "fix: resolve [ID] - [简要描述]"
git push origin master
```

> 禁止在单个 commit 中混用多个问题修复（除非它们属于同一根因或同一重构）。如果一次运行修复了多个问题，请拆分为多个独立 commit。

### 6. 继续下一个问题
重复阶段 3，直到所有问题的状态均为 `[x]`。

---

## 阶段 4：最终复审与循环

当所有问题都被标记 `[x]` 后：

1. **重新执行阶段 1 的分析**（全库扫描）。
2. **生成新报告**，保存为 `CODE_ANALYSIS_REPORT_FINAL.md`（若希望保留历史）或覆盖原报告（需保留历史则重命名）。
3. **若新报告中发现任何严重等级（P0/P1）问题** → 这不是终版。将新问题追加到原报告（标记为新一轮），重置状态为 `[ ]`，回到阶段 3 继续修复。
4. **若新报告仅剩 P2 或零问题** → 终版报告有效。

### 推送终版报告并打标签
```bash
git tag -a "code-audit-passed-$(date +%Y%m%d)" -m "Final code quality audit"
git push --tags
```

输出总结：在控制台打印「✅ 所有可识别问题已修复，代码库质量评估达标。」

## 约束与注意

- **不要自动执行破坏性操作**（如删除文件、强制推送）。如果修复问题需要删除文件（如删除死代码），则先将相关问题标记为暂缓，先执行其他修复任务，最后报告给用户修复总结时，再提醒用户相关任务的暂缓原因。

- **大文件/目录跳过**：分析时忽略以下生成目录和依赖目录：
  ```
  node_modules/
  .git/
  target/
  dist/
  .vite/
  *.min.js
  *.wasm
  ```

- **误报处理**：若某问题经分析是误报，可将其标记为 `[x]` 并在备注写明「误报/设计如此」。

- **测试依赖**：
  - Rust 侧：必须通过 `cargo test`，保证所有测试通过。
  - 前端侧：必须通过 `npm run test`（Vitest），保证所有测试通过。
  - 若某区域无测试覆盖，修复后应至少保证语法正确和主要路径不崩溃。

- **报告更新频率**：每次修复后必须更新报告并提交 Git，保证历史可溯。

- **一项一提交原则**：每个问题 ID 的修复必须对应独立的 commit。若多个问题由同一处根因引起，可在 commit message 中列出相关 ID，但仍应保持改动范围最小化。

## 用户显式授权可选开关

你可以在任务开始时询问以下参数（或由用户写入环境变量）：

| 变量 | 说明 | 默认值 |
|------|------|--------|
| `MAX_FIXES_PER_RUN` | 单次运行最多修复多少个问题（避免循环过久） | 100 |
| `SKIP_GIT_AUTO_COMMIT` | 若为 `true`，仅修改报告和代码但不自动提交 | `false` |
| `SAFE_MODE` | 若为 `true`，修复前自动备份原文件到 `.backup/` | `true` |
| `SKIP_RUST_CHECKS` | 若为 `true`，跳过 Rust 侧静态分析（仅审查前端） | `false` |
| `SKIP_FRONTEND_CHECKS` | 若为 `true`，跳过前端静态分析（仅审查 Rust） | `false` |
