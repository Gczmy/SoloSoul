# 04 — 云打包与云同步功能调研报告

> 调研目标：在插件体系中支持「一键打包数据上传到用户自己的云盘」与「自动同步 SoloSoul 数据到用户自己的云盘」。
> 结论先行：**需求可行，但不建议以纯 WASM 插件形态实现全部能力**——推荐「宿主内置加密包 + 云盘连接器抽象层 + 插件/前端薄 UI」的分层方案。
> 状态：调研稿（2026-08-22），供立项评审。

---

## 1. 需求拆解

| 编号 | 需求 | 关键词 | 本质 |
|------|------|--------|------|
| R1 | **云打包**：登录百度网盘 / OneDrive 等云盘后，一键把数据打包上传到对应网盘指定位置 | 打包 + 上传 + 手动触发 | 「加密导出包 → 云端对象存储」的一次性任务 |
| R2 | **云同步**：自动把用户的云盘中 Solosoul 数据保持最新 | 打包 + 上传 + 自动触发 + 多设备拉取 | 增量快照的定时发布/订阅，等价于「用云盘当离线消息总线」 |

两者的共同内核是：**生成加密包 + 放到云端某个位置 +（R2）另一台设备取回合并**。

## 2. 现状盘点（可直接复用的基础设施）

### 2.1 加密打包 ✅ 已完备

- **加密导出包 `.solosoul`**（`crates/solosoul-core/src/export_import.rs`）：Argon2id 口令派生 + AES-256-GCM，ZIP 内含 `manifest.json` + `payload.enc` + `attachments/{obj}/{att}.enc`（附件分块流式加密）。CLI/GUI 双端已对齐。
- **备份 `backup_create`**（`src-tauri/src/commands/backup.rs`）：Profile 级快照，已有 list/create/restore/delete 全套命令。
- 结论：**打包环节零新开发**，R1/R2 直接复用 `export_execute` 或 backup 快照产物。

### 2.2 与云盘相关的既有能力

| 能力 | 位置 | 说明 |
|------|------|------|
| Android SAF Vault | `state/app_state.rs` + `fs/saf_sync_driver.rs` + Kotlin 插件 | Vault 可置于用户选择的 SAF tree；第三方云盘 App（OneDrive 等）会向系统暴露 SAF DocumentsProvider，Kotlin 端已有 `syncDirToRemote/syncDirFromRemote` 双向目录同步驱动 |
| 桌面 OneDrive 白名单 | `commands/fs.rs:89-107` | `~/OneDrive`、`OneDrive - <组织名>` 前缀目录已在附件白名单内（N010） |
| 设备同步引擎 | `crates/solosoul-sync/` | HLC 增量水印 + Noise XX + mDNS 局域网 P2P；**不经云盘中转**，但增量协议/冲突检测可借鉴 |

### 2.3 插件沙盒能力边界（本次调研的核心约束）

实测代码级确认（`crates/solosoul-plugin/src/host.rs`）：

| 能力 | 现状 | 对 R1/R2 的影响 |
|------|------|----------------|
| HTTP 出网 | `solosoul_http_request/poll/read/close` 异步轮询式，受 manifest `network_policy.allowed_domains` 白名单约束；**body 为 UTF-8 String**，单次读取上限 **64 KiB**，响应截断 64 KiB | ❌ 无法承载几十 MB 二进制包直传云盘 API；❌ OAuth 授权码流程需浏览器回调，客户端无 deep-link 支持 |
| 文件写出 | `write_output_file` / `copy_output_file` → 仅限运行参数 `outputDir`（用户授权目录）；无大小硬限制（水印插件已处理大 PDF） | ✅ 可将加密包写入云盘**本地同步文件夹** |
| 定时/后台运行 | ❌ 无调度器；插件为看板手动触发的一次性运行（燃料上限 100 亿、TTL、sleep ≤ 1s/次） | ❌ R2 的"自动"必须由宿主侧调度，插件自身做不到 |
| 凭证保管 | 插件无持久状态（TTL 后内存清零）；宿主无通用 token vault | ⚠️ OAuth refresh token 属长期敏感凭证，不应交给 WASM 插件持有 |

## 3. 候选方案矩阵

### 方案 A：云盘官方 API 直传（插件内）

插件经白名单域名调 `pan.baidu.com` / `graph.microsoft.com` REST API 上传。

- ❌ 大包体上传被 64KiB/String body 卡死，需新增二进制流式上传 Host Function；
- ❌ OAuth 需要浏览器回调或设备码流程，无 deep-link 基础设施；
- ❌ refresh token 管理职责错位（插件不该持有长期凭证）；
- ✅ 优点仅在于"真·指定任意远端路径"。

**判定：不作为插件形态落地。若做，只能做成宿主内置连接器（见方案 C）。**

### 方案 B：写入云盘本地同步文件夹（插件可实现 ✅）

利用云盘桌面客户端的同步目录（OneDrive `~/OneDrive/SoloSoul/`、百度网盘"同步空间"、坚果云等），插件把加密包写到该目录，由云盘客户端负责上云。

- 实现路径（**零新 Host Function**）：
  1. 新增官方插件 `com.solosoul.official.cloud-packager`；
  2. manifest `params` 增加 `outputDir`（现有机制，用户选择云盘同步目录）+ `scope`（打包范围）+ `passwordHint` 等；
  3. 运行参数透传给宿主 → 宿主执行既有 `export_execute` 生成 `.solosoul` 包 → `copy_output_file` 复制到 outputDir；
     *（备选：插件只产出结果面板引导，由前端调用 export 命令——更简单，见 §5 推荐）*
  4. 包命名带时间戳/HLC 水印，便于云端多版本管理。
- ✅ 零知识模型天然满足（包本身口令加密）；✅ 无 token 管理；✅ Windows/macOS 用户大多已装 OneDrive 客户端。
- ⚠️ 依赖用户安装云盘客户端；Linux 部分网盘无客户端；移动端无此路径（移动端走 §2.2 的 SAF 通道）。

### 方案 C：宿主内置「云盘连接器」抽象层（核心功能，R2 必经之路）

Rust 侧新增 trait + 官方实现，UI 在 Settings，不走 WASM：

```rust
#[async_trait]
pub trait CloudConnector {
    async fn authorize(&mut self) -> Result<(), CloudError>;      // OAuth 设备码/本地回调
    async fn ensure_dir(&self, path: &str) -> Result<(), CloudError>;
    async fn upload(&self, path: &str, reader: Pin<&mut dyn AsyncRead>, size: u64) -> Result<(), CloudError>; // 分片直传
    async fn download(&self, path: &str, writer: Pin<&mut dyn AsyncWrite>) -> Result<(), CloudError>;
    async fn list(&self, path: &str) -> Result<Vec<CloudObjectMeta>, CloudError>;
}
// 官方实现：OneDriveConnector(Graph API, 分片上传 session)、BaiduPanConnector(OpenAPI 分片)、WebDavConnector(通吃坚果云/Nutstore/Nextcloud/自建)
```

- token 存入 Vault（解锁态才可用，与主密码生命周期绑定，符合零知识）；
- R1 = `export_execute` + `connector.upload`；R2 = 宿主调度器（复刻 `device_auto_sync.rs` 三触发模式：前台切换/变更防抖/周期轮询）+ 云端水位线（上传 HLC 水印清单，其他设备下载后走既有导入/冲突合并链路）;
- WebDAV 连接器建议优先做：一套代码覆盖坚果云/群晖/Nextcloud/Alist（Alist 又能聚合百度网盘/OneDrive 等 40+ 网盘），投入产出比最高。

### 方案 D：整库直接放云盘同步目录（❌ 否决）

Vault 为 SQLite 目录树，直接置于同步文件夹会被双向同步在写入中途抓走半事务状态，造成库损坏（SQLite-over-Dropbox 经典事故模式）。**必须走"快照包"而非"活库镜像"**。Android SAF 模式之所以可行，是因为其驱动按文件粒度显式同步（非透明挂载），且写入走原子替换——即便如此也仅用于单设备备份场景，不建议多设备并发指向同一 SAF tree。

## 4. 关键风险与对策

| # | 风险 | 对策 |
|---|------|------|
| 1 | 明文上云违反零知识承诺 | 强制仅允许 `.solosoul` 加密包/备份快照上云；上传前校验 ZIP 内含 `payload.enc`，拒绝裸文件 |
| 2 | 主密码未解锁时无法派生包口令/读取 token | R2 调度器仅在解锁态工作（与现有 auto-lock 语义一致）；锁定即暂停并记录断点 |
| 3 | 云端多版本包无限膨胀 | 保留策略：最近 N 份 + 每 日/周/月 各留一份（ grandfather-father-son ） |
| 4 | 两台设备先后上传产生分叉 | 包内嵌 HLC 水印 + device_id；导入时复用 `sync_conflicts` 冲突 UI；同设备重复上传做幂等跳过 |
| 5 | 百度网盘 API 配额/审核不稳定 | 连接器抽象隔离差异；WebDAV/Alist 作为兜底出口 |
| 6 | 恶意"云盘目录"诱导路径逃逸 | 复用 P004 教训：outputDir 仅接受用户经系统对话框选择的目录，拒绝插件可控字符串 |

## 5. 推荐落地路线

### Phase 1（R1 · 短期，1~2 周）：「云打包」= 导出向导增加云盘目标

- **形态**：核心功能而非插件——前端「设置 → 数据」页在现有导出流程加一步「保存到云盘」：
  - 桌面：系统目录选择器选云盘同步文件夹（复用 `saveWithPause` 封装）→ 生成 `.solosoul` 到目标；
  - Android：SAF tree 选择器（复用现有 SAF 基础设施）。
- 同时发布官方插件 `com.solosoul.official.cloud-packager` 作为市场样板（演示 params/outputDir 用法），验证插件生态叙事。
- 交付物：一键「打包并放入云盘」、包命名 `{account}_{HLC时间戳}.solosoul`、结果面板显示云盘客户端同步提示。

### Phase 2（R2 · 中期，3~5 周）：「云同步」= 宿主内置 WebDAV/OneDrive 连接器 + 调度器

- Rust `CloudConnector` trait + WebDAV 实现（优先）+ OneDrive Graph 实现；
- token 入 Vault（AES-256-GCM，随主密钥）；
- 调度器复刻 `device_auto_sync` 触发模型；云端布局：
  ```
  /SoloSoul/{account_id}/snapshots/{device_id}/{hlc_watermark}.solosoul
  /SoloSoul/{account_id}/latest.json   ← 各 device 最新水印索引
  ```
- 下行：其他设备发现新水印 → 提示或静默拉取 → 走既有 import + conflicts 合并链路；
- 设置项：开关、频率、保留份数、Wi-Fi only（移动端）。

### Phase 3（远期，可选）：插件化连接器生态

- 若社区需要小众网盘，再考虑开放「连接器插件」Host Functions（`request_oauth_device_code` / `upload_stream` 等）——届时连同 token vault、deep-link 一起立项评审，本报告风险表 #6 类安全审查前置。

## 6. 结论

1. **R1 云打包**：立即可做。推荐 Phase 1 形态（核心导出流程扩展 + 样板插件），零新增安全面。
2. **R2 云同步**：可行但必须宿主实现。WASM 插件缺三样东西——后台调度、大文件网络、长期凭证保管，这三样恰是沙盒刻意不给的能力；强行塞进插件等于给所有第三方插件开危险先例。
3. 统一原则：**上云的永远只有口令加密的快照包**，活库不出本机——这是与项目「独奏生命数据，重塑数字原点」哲学的唯一兼容姿势。
