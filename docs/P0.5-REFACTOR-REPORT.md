### Phase 2 — 合并重复实现（中等风险）

> 目标：把两套做同一件事的代码合成一套，降低同步维护成本。

#### 2.1 合并两套 AES-256-GCM 实现 —— ❌ `wontfix`

经过详细评估，`cipher.rs` 与 `aes.rs` **不是重复实现**，而是服务于两个不同协议层的封装，合并收益远低于风险，决定跳过。

**功能对比**

| 维度 | `cipher.rs`（389 行） | `aes.rs`（352 行） |
|------|----------------------|---------------------|
| 数据格式 | 原始 `nonce(12) \|\| ciphertext+tag` | SOLO 格式 `Magic(4) \|\| Ver(1) \|\| nonce(12) \|\| ct+tag` |
| AAD 支持 | ✅ 全部函数支持 | ❌ 不支持 |
| 错误类型 | `CipherError` enum | `String` |
| 单块加密 | `encrypt` / `decrypt` | `encrypt_blob` / `decrypt_blob` |
| 分块加密 nonce | 1 个 base nonce + XOR 派生 per-chunk | 每个 chunk 独立随机 nonce |
| 流式加密签名 | `encrypt_chunked_stream(key, total_size, reader, writer)` | `encrypt_chunked_stream(key, reader, writer, chunk_size)`（需 `Read + Seek`） |
| 返回值 | `EncryptedData` 或 `Vec<u8>` | 始终 `Vec<u8>`（含 SOLO 头部） |

**核心结论**

- `cipher.rs`：通用 AES-256-GCM with AAD，用于 `.solosoul` 导出/导入包。
- `aes.rs`：SOLO 专用 blob 格式，用于 Vault 字段、生物识别文件、前端加密命令等。
- 两种 chunked 格式完全不兼容：
  - `cipher.rs`：`nonce(12) \|\| chunk_count(8) \|\| ct1+tag \|\| ct2+tag \|\| ...`
  - `aes.rs` v3：`SOLO(4) \|\| 0x03(1) \|\| orig_size(8) \|\| chunk_size(4) \|\| chunk_count(4) \|\| nonce1(12) \|\| ct1+tag \|\| ...`

**调用者分析**

- `cipher.rs` 调用者（5+ 文件，均与 export/import 相关）：
  - `solosoul_cli/src/commands/export_import.rs`
  - `tauri/src-tauri/src/commands/export_import/export.rs`
  - `tauri/src-tauri/src/commands/export_import/import.rs`
  - `tauri/crates/solosoul-core/src/pin.rs`
  - export/import 测试文件
- `aes.rs` 调用者（Vault/文件存储）：
  - `tauri/crates/solosoul-vault/src/encryption.rs`
  - `tauri/crates/solosoul-core/src/biometric/legacy.rs`
  - `tauri/src-tauri/src/commands/crypto.rs`
  - `tauri/src-tauri/src/commands/fs.rs`

**评估结论**

| 项 | 评估 |
|----|------|
| 风险 | 🔴 高 — 两种分块格式完全不同，`.solosoul` 文件必须保持向后兼容 |
| 影响范围 | ~15 个文件，±300 行变更 |
| 预期收益 | 仅约 -37 行净减少（核心加解密逻辑都是必要的，重叠很少） |
| 合并难度 | 需要统一格式（破坏兼容性）或保留两种格式（收益几乎为零） |
| 建议 | ❌ 不建议合并 |

**替代方案（如仍想优化）**

1. 轻量整理（低风险）：统一 `cipher.rs` 的 `CipherError` 和 `aes.rs` 的 `String` 错误风格，更新 re-export。变更约 50 行，收益有限。
2. 按兵不动（推荐）：保留两个模块，各自服务不同协议层。

### Phase 3 — 架构层瘦身（影响较大，需单独评审）

> 目标：把本应由核心层承担的职责从 CLI 和前端抽出去。

#### 3.1 CLI export/import 下沉到核心

- **现状**：`solosoul_cli/src/commands/export_import.rs` 共 1,772 行，包含了完整的 `.solosoul` 包解析、密码验证、附件流式加解密、审计日志、冲突处理。
- **目标**：在 `solosoul-core` 中新增 `export_import` 模块，暴露高层 API：
  ```rust
  pub fn export_vault(...) -> Result<Vec<u8>, CoreError>
  pub fn import_vault(...) -> Result<ImportSummary, CoreError>
  ```
- **CLI 保留**：参数解析、进度回调、终端输出。
- **验证**：必须跑通 `solosoul_cli/src/commands/export_import.rs` 里的所有单元测试，并补充与 GUI 导出包的互操作测试。

#### 3.2 CLI vault_write / attachment 下沉

- **现状**：`vault_write.rs`（1,202 行）和 `attachment.rs`（889 行）在 CLI 层手工组装 `ObjectRecord`、复制附件物理文件、维护 `__attachments` metadata。
- **目标**：在 `solosoul-vault` 或 `solosoul-core` 提供：
  ```rust
  pub fn create_object_with_attachments(...)
  pub fn add_attachment_to_object(...)
  pub fn soft_delete_attachment(...)
  ```
- **CLI 保留**：命令解析、字段编辑器交互、结果展示。

#### 3.3 替换窗口状态管理

- **现状**：`tauri/src/hooks/useWindowSize.ts` 通过 localStorage + UI preferences + account preferences + 防抖实现窗口大小持久化，共 173 行。
- **目标**：使用 `@tauri-apps/plugin-window-state`。
- **操作**：
  1. 安装 `@tauri-apps/plugin-window-state`。
  2. 删除 `useWindowSize.ts`。
  3. 在 `tauri/src-tauri/src/lib.rs` 的 builder 上调用 `.plugin(tauri_plugin_window_state::init())`。
  4. 删除 `ST_WINDOW_SIZE` 相关 storage key 和 UI/account preference 写入点。
- **风险点**：该插件默认不恢复登录前窗口大小，需确认首次启动体验是否可接受。

#### 3.4 插件 SDK helper 统一

- **现状**：约 15 个插件各自实现了 `escape_json`、`truncate`、字符串读取循环。
- **目标**：
  1. 在 `SoloSoul_plugin_market/SDK/rust/src/lib.rs` 中暴露 `pub fn escape_json(s: &str) -> String` 和 `pub fn truncate(s: &str, max: usize) -> String`。
  2. 各插件删除本地副本，改用 `sdk::escape_json` / `sdk::truncate`。
  3. 删除未使用的异步 HTTP SDK 表面：`HttpRequest`、`HttpPollState`、`post_json_async`。
- **注意**：修改插件后必须重新运行 `python3 scripts/generate_registry.py` 并提交 `registry.json`。

## 五、注意事项

1. **不要一次性做完所有改动**。Phase 3 每一项都建议单独 PR，避免 review 爆炸。
2. **Phase 2.1 已评估为 `wontfix`**。`cipher.rs` 与 `aes.rs` 分别服务不同协议层，合并会破坏 `.solosoul` 导出/导入格式或收益几乎为零，故保留现状。
3. **窗口状态替换要人工验证**：首次启动、多账户切换、退出重开三种场景。
4. **插件市场修改后必须本地重新生成 `registry.json`**，否则 `validate-registry.yml` 会失败。
5. **所有删除操作前先 `git grep` 确认没有隐藏调用方**，尤其是动态字符串拼接的命令名。
