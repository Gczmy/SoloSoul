## 二、最终状态（按子系统）

### ✅ Refactor A：`SyncService` 跨 crate 上提（完成 + 5-方法 idiom 统一）

`solosoul-sync::SyncService` 现在被 GUI 与 CLI 共用（CLI 接入留待 Stage 1）。

**类型推断错误的真正根因（事后追溯）**:
之前以为 12 个 E0282 是 `match &*guard { Some(m) => m.method() }` 在 `tokio::sync::MutexGuard<Option<SyncManager>>` 上的 match ergonomic 失败，但**实际两个独立 bug 共同触发**：
1. **错误的 in-crate import**：`use solosoul_sync::manager::SyncManager` 在 `service.rs` 里，但 service 已经属于 `solosoul-sync` crate，应该写 `use crate::manager::SyncManager` — 否则 `SyncManager` 未解析，所有 `m.method()` 调用退化成 `m.fingerprint()` on `m: &Unknown`，编译器以 E0282 形式报；
2. **缺失 `uuid` 依赖**：`crates/solosoul-sync/Cargo.toml [dependencies]` 漏掉 `uuid = { workspace = true }`，导致 `uuid::Uuid::new_v4()` 在 `get_or_create_sync_identity` 处 E0433 — `keys` 类型无法推断，整个 match 退化成 E0282 风暴。

**修法**:把上面两个 bug 修了之后，**`match guard.as_ref() { Some(m) => m.method() }` 一行就能推断**，根本不需要任何类型注解、helper、宏、显式 `let opt`。所有 5 个公共方法统一为同一 idiom：

```rust
let guard = self.manager.lock().await;
match guard.as_ref() {
    Some(m) => m.method(),                       // enable / is_enabled / sync_with_device
    None => Err("Sync is not enabled".into()),   // known_peers / trust_peer / forget_peer / local_fingerprint
}
```

具体覆盖到的 **8 个公共方法**（含构造函数 `new`）：

| # | 方法 | 失败臂（`None =>`） |
|---|------|---------------------|
| 1 | `new() -> SyncService` | ——（构造函数） |
| 2 | `enable(bool) -> Result<(), String>` | `Some(m) => m.enable(b)` |
| 3 | `is_enabled() -> bool` | `Some(m) => m.is_enabled()` |
| 4 | `sync_with_device(&str) -> Result<SyncSessionResult, String>` | `Some(m) => m.sync_with_device(...)` |
| 5 | `known_peers() -> Result<Vec<SyncPeerInfo>, String>` | `None => Err("Sync is not enabled")` |
| 6 | `trust_peer(&str, bool) -> Result<(), String>` | `None => Err("Sync is not enabled")` |
| 7 | `forget_peer(&str) -> Result<(), String>` | `None => Err("Sync is not enabled")` |
| 8 | `local_fingerprint() -> Result<String, String>` | `None => Err("Sync is not enabled")` |

后 5 个（5–8）共享同一 `None => Err("Sync is not enabled")` fallback arm；前 4 个（1–4）按业务返回不同结果（`Ok(())`/`bool`/`Result<SyncSessionResult, String>`）。所有这些方法都收敛为同一 `match guard.as_ref() {...}` shape，没有任何 `if let Some` 退化形式。

**impl-block 结构崩塌的 brace 修复**:在迭代过程中，impl SyncService 区块结构破损（`local_fingerprint` 文档注释行起首的 `}` 误把 impl 提前关闭，导致方法被解析为带 `&self` 的 free function）。单字符修复：把 `}    /// 返回本地节点...` 改成 `    /// 返回本地节点...`（删除多余的 `}`），让 impl 区块正确闭合。

#### 🟢 qualified-path strategy（`commands::llm::X` 兼容性策略）

**实测 upstream grep 结果**：
```bash
grep -rnE 'commands::llm::(LlmUsageStats|ModelUsage|DailyUsage|Conversation|ConversationSummary|LlmConfig|ChatMessage|ProviderConfig|AiFeatures|ApiType|ProviderWithKey)' tauri/ solosoul_cli/
# → 0 行匹配（worktree 内无任何 caller 使用 qualified path）
```

**策略选择**：因为 `commands::llm::X` 的真实 caller 数为 0（在 `tauri/` 和 `solosoul_cli/` 全树 0 命中），加 `pub use` re-export 是对将来不存在的 caller 做防御性工作。但入口只添加一个 canonical import 就够用：

```rust
// commands/llm.rs 顶部
use solosoul_core::llm::service::LlmService;
use solosoul_core::llm::config::{
    AiFeatures, ApiType, ChatMessage, Conversation, ConversationSummary,
    DailyUsage, LlmConfig, LlmUsageStats, ModelUsage,
    ProviderConfig, ProviderWithKey,
};
```

这条 `use` 把 11 个名字都带入**当前文件的本地命名空间**（`commands::llm`），同时 binding 的源就是 `solosoul_core::llm::config::X` 的 canonical 定义。文件内部所有引用（`HashMap<String, LlmUsageStats>` 在 `STATS_MAP`、`ProviderWithKey { ... }` 在 `default_providers()`、`&[Conversation]` 在 `save_conversations`）都走得通。

**未来如何打开 `commands::llm::X` qualified-path 访问**：当某一天真有 external caller 想走 `commands::llm::LlmUsageStats` 这条路径，加 **一行**：
```rust
pub use solosoul_core::llm::config::{
    AiFeatures, ApiType, ChatMessage, Conversation, ConversationSummary,
    DailyUsage, LlmConfig, LlmUsageStats, ModelUsage,
    ProviderConfig, ProviderWithKey,
};
```
紧挨着现有 `use` 即可。若 rustc 报 unused-import warning（提示文件内部没用这些 re-export），加 `#[allow(unused_imports)]` 前缀即可。这一行补充不在 P0.5 范围（0 caller 状态下不需要）；已在 `cmd/run_p0_5_finalize` 时机保留为 followup。

### 6.5 · 元任务：归档本次重构的经验教训

主教训（从 P0.5 实际发生的事故里提炼）：
1. **Rust in-crate 路径必须用 `crate::`，不能写成外部 crate 名**。`service.rs` 写到 `use solosoul_sync::manager::X` 时，错误地假设自己还在其他 crate 里——其实是 in-crate 模块。E0282 不是 match ergonomics 失败，是 unresolved import 的 cascading 症状。
2. **`tokio::sync::MutexGuard<Option<T>>` 的 match 工效** 一旦根因是 unresolved import，rustc 不会被指引去看 import，而是把没解析的 `m: &SyncManager` 当成 `m: &Unknown` 然后报 E0282。修 import 后 match 自然推断通过。
3. **defer 一个跨 crate refactor 时，先用 `comm -12 <(grep -E '^pub (struct|enum|type) ' commands/X.rs) <(grep -E '^pub (struct|enum|type) ' core/X.rs) | grep '<` upfront diff** 一次性发现所有重复类型，然后一次性删完。比"删一个、cargo check、发现下一个、删除..." 节省 5+轮。
4. **Python 脚本按 exact-bytes 替代的话，源文件里若已有空行 / 注释，关键 token 可能跨行**——比如 `}    /// 起首的 `}` 与下面的 `///` 不在同一行但被 Python 错误地合并成单行。使用 `cat -An` (或 `cat -A`) 核对是不可省略的步骤。
5. **`SyncService` 5 个方法 + 1 个 helper 的 idiom 应该一开始就统一**——用 `match guard.as_ref() { Some(m) => m.method(), None => { Err } }`，而不是 `if let Some(m) = ... { return Ok }; return early` 等退化形式。
