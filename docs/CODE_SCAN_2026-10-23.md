## P052 — 非原子的对象读改写可丢失并发附件更新

**优先级：P1；状态：待修复。**

位置：`tauri/src-tauri/src/commands/object/mod.rs:694–732`；附件元数据写入
`tauri/src-tauri/src/commands/attachment/crud.rs:185–200,256–291`；
`tauri/crates/solosoul-vault/src/storage/objects.rs:458–475,525–535`；
`tauri/crates/solosoul-vault/src/storage.rs` 的 `OBJECT_SAVE_SQL`。

对象更新先 `load_object`，在连接锁外修改整个 record，最后再 `save_object`。
附件也使用同样模式。每次保存本身有事务及最新锁保护，但整个读取、修改和保存不在同一事务内，
UPSERT 也不检查旧版本。`preserve_object_edit_metadata` 保留的是读取当时的附件列表，并非提交当时的最新值。

确定的交错为：编辑请求读取附件列表空 → 附件请求写入一项并成功 → 编辑请求提交旧 record，
把附件列表重新覆盖为空。两个操作均返回成功，同一版本号也可能被重复使用。
文件实体可能仍在，但引用从活动对象消失；这不是锁保护绕过，当前锁定对象仍会拒绝普通写入。

**修复任务：**在共享 Vault 层提供受事务保护的对象修改入口，或为普通写入引入显式版本冲突检查。
在提交时重读最新保护标记及附件，针对要修改的字段合并；附件增改删也接入同一机制。
保持账户归属、导入专用事务、同步 HLC 和现有加密/锁保护，不能简单移除检查或仅在前端串行化。

**验收：**在临时 Vault 中设置阶段屏障，复现上述交错；允许两项修改均保留，或第二次保存明确冲突并保留草稿，
不能两次成功后丢失附件。另覆盖两项附件元数据并发修改、并发锁定、版本/HLC 更新及失败回滚。
执行 Vault/Core/Host 定向回归，再执行工作区 fmt、严格 Clippy 和 tests，并复验 CLI 的固定依赖检查。

**复现记录：**独立合成程序直接依赖当前共享 Vault 源码，两个 `save_object` 均返回成功；
附件写入后引用数为 1，旧编辑副本保存后变为 0，最终版本仍为 2。
根目录活动保护允许同一根下的正常任务并行，不会把整个 GUI 读改写串行化；
该交错不是绕过实际存在的命令级互斥后构造的假象。探针未创建真实附件文件，也未读取用户数据。

## P053 — 普通文件预览的生产分支忽略读取上限

**优先级：P1；状态：待修复。**

位置：`tauri/src-tauri/src/commands/fs.rs:210–248,377–383,465–471`；
关联 `tauri/crates/solosoul-core/src/attachment_crypto.rs:99–117`。

`fs_read_file_as_text` 与 `fs_read_file_as_data_url` 都传入 10 MiB 上限。
生产 `read_file_with_attachment_decrypt` 对普通文件直接调用 `std::fs::read(path)`，没有使用 `max_size`。
`#[cfg(test)]` 替代实现却会先按 metadata 拒绝超限文件，造成测试与生产逻辑不同。
文件越大，Rust 内存、Base64 及 IPC/WebView 副本越大，可能导致界面停顿或内存耗尽。
前端 `useAttachmentPreview.ts` 的普通文本与图片读取会调用这两个入口；旧版明文附件仍是支持的读取路径。
新密文附件走另一分支，不能把本探针描述为所有密文上限都已验证失效。

**证据：**从当前生产 helper 提取完全相同的普通文件分支，在独立 Rust 程序中传入 10,485,760 字节上限，
11,534,336 字节的合成文本仍成功完整读取。该探针证明生产分支的缺口，不是完整 Tauri 命令运行。

**修复任务：**生产与测试共用有界文件读取核心；在打开的句柄上检查长度，实际读取也限制为 `max_size + 1`，
超过后明确失败，避免文件在读取期间增长而绕过 metadata 检查。解密输出也应按明文字节数限定，
保持旧明文兼容、路径白名单与现有密文校验，不能通过测试替身掩盖差异。

**验收：**普通文本、data URL 与加密附件分别覆盖上限前、恰好上限、超限和读取期间增长；
失败时不返回部分内容或巨型 Base64，不破坏原文件。测试应执行生产所用核心实现。
执行 Host 文件预览与 Core 附件加解密回归、fmt、严格 Clippy 和 tests。

## P054 — 详情的迟到读取覆盖已确认的对象锁状态

**优先级：P2；状态：待修复。**

位置：`tauri/src/components/object/useObjectDetailModal.tsx:153–190`；
消费方 `tauri/src/hooks/useObjectEditLocked.ts`、`tauri/src/components/object/ObjectDetailModal.tsx`。

摘要打开详情时直接发起 `object_get`，回填 `currentObjectCache`。
现有 guard 只检查该弹窗请求是否活跃、是否换过对象，没有与同一对象后续成功写入比较新旧。
如果在读取返回前执行锁定并收到成功，旧的未锁定 GET 仍会覆盖缓存，徽章和操作许可回退到可编辑。
后端保护仍生效，但页面会显示相反状态，下一次操作报错；反向交错也可能覆盖解锁结果。

**证据：**真实详情 Hook + Store 的合成延迟测试：先开始未锁定 GET → `setObjectLocked(true)` 成功且
锁状态为 true → 旧 GET 返回 → 缓存与 `useObjectEditLocked` 都变为 false。
工作区通过 `useObjectWorkspaceData.ts:53` 的局部选择状态把摘要传入详情，
并非每次 Store 更新都会替换详情 prop，因此不能依赖父组件重传对象来使旧请求失效。

**修复任务：**详情读取接入统一的对象读取/写入代次或可靠修订信息；成功写入后拒绝旧读回填，
同时保持打开详情不触发全局列表 loading 的现有行为。不能只修徽章而继续覆盖共享缓存。

**验收：**覆盖锁定及解锁两个方向、延迟详情、切对象/账户、关闭弹窗，以及失败后的重新读取。
验证列表、详情、悬停预览和编辑页的状态一致，旧响应不能覆盖已确认写入。

## P055 — 读取请求可取消成功写入回执并留下加载状态

**优先级：P2；状态：待修复。**

位置：`tauri/src/stores/objectStore.ts:91–112,155–196,201–221`；
`tauri/src/lib/sessionRequests.ts:37–57`。

`getObject`、`updateObject`、`setObjectLocked`、`deleteObject` 使用相同的 `object:${objectId}` 请求序号。
“最新读取胜出”适合读取乱序，不能直接当作同会话写入是否成功的标准：
写入已发往后端后，新 GET 增加序号，真实成功的写回执被 `assertCurrent` 当成会话过期拒绝。
另一方向：GET 先设置 `isLoading=true`，锁定请求使 GET 失效，锁定自身不结束该 loading；旧 GET 也直接退出，
没有剩余请求会恢复它。工作区订阅此全局 loading，可能一直停留在加载展示。

**证据：**两项真实 Store 延迟探针均通过复现：同账户读取使成功锁定 Promise 抛出
`Request belongs to an expired session`；反向交错的所有 Promise 完成后 `isLoading` 仍为 true。

**修复任务：**区分会话失效、读取版本和已发送写入；同会话读取不能撤销已完成写入的业务回执。
同时为加载状态设置明确的操作所有权或计数，不能让一个失效请求负责结束另一个操作。
修复与 P054 配合，防止拆分 key 后反而放开旧读覆盖新写；继续阻止锁库、换账户后的回填。

**验收：**保存/锁定/删除与详情读取的双向交错，后端写入成功不误报失败，失败不误报成功；
全部结束后加载状态正确，A→锁定→B 的会话隔离仍通过。

该项当前证据为 Store 级确定交错；没有把所有对应界面手势都描述为已完成原生实机复现。

## P056 — 递归扫描跟随链接返回白名单外的元数据

**优先级：P2；状态：待修复。**

位置：`tauri/src-tauri/src/commands/fs.rs:302–350`。

`fs_scan_directory` 只校验顶层目录。递归使用 `path.is_dir()` / `is_file()` / `metadata`，
都会跟随子目录或文件链接，没有对子项执行同样的规范路径边界检查。
白名单内若包含指向外部目录的 junction/symlink，扫描会进入目标并返回文件名、路径和大小。
后续单文件读取仍有边界检查，因此当前证据不支持“可读取任意文件正文”的结论。

**证据：**使用原样提取的 `scan_dir_recursive` 和 `display_fs_path`，创建独立的 allowed 与 outside 目录，
仅在 allowed 下创建指向 outside 的 junction。扫描返回 outside 的合成哨兵，目标内容哈希保持不变。
自建 junction 在探针结束时移除；没有扫描用户目录。

**修复任务：**递归时跳过链接/reparse point，或对子项的真实目标持续验证获准根边界；
若允许根内链接，还需处理循环和重复路径。保持原有文件数量及深度上限，不扩大白名单。

**验收：**Windows junction、文件/目录 symlink、越界目标、根内目标、循环、损坏链接、普通目录及原有限额。
负向场景不得暴露外部哨兵元数据，不能导致递归循环或以静默漏检冒充完整扫描。

- 插件当前已有 fuel、会话及宿主访问检查，不能称作“没有沙箱”。内存/table 限额与进程级编译缓存上限
  仍适合单独做受控容量验证；本轮未运行大内存插件，不把潜在风险冒充已实测崩溃。
- 文件读取另有需核实的权限边界：普通文件分支依赖路径白名单，前端 `ipcClient` 的锁定守卫不能等同于后端鉴权。
  应结合旧明文附件兼容约定，用隔离的已锁定服务验证这些路径是否还应获准读取；本轮没有将该待核实风险计入确定漏洞，
  也没有尝试读取任何真实账户文件。
- 发布签名假密钥测试的 Windows 编码/POSIX 运行条件问题单列检查边界，不声称发现新的密钥泄露。
