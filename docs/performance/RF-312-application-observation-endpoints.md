# RF-312：系统启动到登录操作的观察端点

本项把已有 AM 队列的真实启动请求与登录控件、输入法及首次公开文字输入放在同一个设备时钟下。产品、采集器、原读取器与预算不改；没有新 SDK、原生运行或输入。规范离线入口重新通过原状态／IME／UI 和 24 项阶段绑定，415／401 份原生回包逐字核验。

## 本轮数据

沿用[显式 AM 配置](RF-312-startup-am-profile.md)的一台 API31 x86_64 隔离设备，100／5,000 对象各 n=1，周期内存采样开启。以下秒数均以匹配的 `MetricsLogger:launchObserverNotifyIntentStarted` 为零点；原进程／UID／出生时间和 BOOTTIME 零偏移绑定保持。

| 观察端点 | 100 对象 | 5,000 对象 |
| --- | ---: | ---: |
| 系统冷启动窗口结束 | 0.414 | 0.549 |
| 首份匹配登录控件与夹具标记的元数据快照结束 | 7.789 | 4.305 |
| 原登录截图采集结束 | 8.426 | 4.898 |
| 密码框与 Unlock 的稳定命中检查完成 | 11.237 | 7.517 |
| 首次聚焦点击方法完成 | 13.039 | 8.932 |
| 稳定的密码框焦点／单输入法检查完成 | 16.468 | 10.970 |
| 首段公开密码的原生按键方法完成 | 19.199 | 13.876 |
| 快照首次观察到完整公开密码长度 | 19.313 | 14.103 |
| 已验证首页对象计数的截图采集结束 | 26.182 | 20.737 |

这是观察方法的端点，不能把最后一次未匹配的可访问性快照当作应用此前不可用的证明，也不能把第一次匹配当作精确 TTI。原登录图片已实际查看，密码框和 Unlock 可见；这些图片晚于最早两帧，不追认那两帧的内容。密码输入包含 54 个同步原生按键事件，相关方法区间包括事件处理和等待。

密码框及 Unlock 各有三次末尾成功命中，原 350 ms 宿主稳定性要求继续由冻结行程执行。本轮这些组三次末尾回包的设备跨度为 0.756／0.869 秒和 0.826／0.690 秒；这只是实际跨度，不把宿主期限换算成新设备期限。输入检查沿用原谓词：EditText 为空、目标聚焦且可聚焦，并且恰有一个可见输入法；实际按键方法的成功另列。输入前仍未就绪的检查为 3／1 次，焦点和输入法状态原样保留；它们是等待状态，不改判为成功检查或失败的应用运行。

首次 Unlock 点击方法开始至可证首页计数截图结束的区间为 5.320／5.007 秒，包含命中、输入、应用等待和截图成本。登录稳定检查之前的原生方法区间总和为 5.637／2.608 秒，也包含应用／系统等待；不能从整体跨度中扣除它们得到应用独占耗时。其余十二阶段的截图观察窗口和原宿主行程上界在结构化记录中保留，跨阶段相减不冒充某项业务延迟。

## 同口径复跑与派生

1. 按[公开队列](RF-312-public-native-queue.md)和[AM 配置说明](RF-312-startup-am-profile.md)准备默认 APK、小／大合成 Vault 及全新设备。完成原预检、原十二阶段、恢复和正常宿主退出；先运行原四组独立重放。失败和错过的采样不删除，不补发输入。
2. 对完成且恢复的原件运行以下入口。它执行自己的原状态、IME、UI 核验，要求 `phase-progress` 与已审查状态中的阶段记录精确一致，再冻结原始请求／回包和阶段文件。每次输出目录必须全新。

```powershell
python -B docs/performance/rf312-observer-timing/read-native-timing.py `
  --native $CompletedNative --adapter-inputs $AdapterInputs `
  --unit-evidence $UnitEvidence --output $NewTimingOutput
```

3. 对同一未修改 trace 用固定 v58.2、完整排序和原 45 秒期限运行[启动 SQL](rf312-startup-events.sql)与[主窗口帧 SQL](rf312-first-main-frames.sql)。选取绑定到实际主进程的唯一 SoloSoul `cold` 窗口，不用整个 trace 的起点；要求 PID／UID／出生量化区间和 BOOTTIME 偏移继续匹配。保留其它系统启动及失败通知。
4. 按请求序号扫描原快照。使用原 `native_journey_contract.visible`、`Journey.action_candidates('Unlock')` 和 `Client.target`／`target_ready`，寻找唯一空密码框、唯一 Unlock 和本档夹具标记。记录首份匹配快照的整个方法区间，不只取一个假定的“渲染时刻”。原 `startup.nativeScreenshot` 的摘要、对应快照和规范阶段记录必须一致。
5. 登录截图后，按原行程顺序绑定密码框命中组和 Unlock 命中组，核对各自末尾连续成功的三个目标及保存的 `login-readiness`。将最后一次 Unlock 命中回复的 `nativeFinishedAtNs - intent.ts` 记为稳定点击检查端点。进入解锁阶段后的密码框点击组单独记录，不能混成启动组。
6. 键盘出现后输入框会移动。本次派生初稿错误要求前后坐标相等而拒绝，原反例保留。正确绑定要求同一非空控件 ID 与字段语义，并在每个阶段使用其当时的精确原生命中目标；不能沿用旧坐标，也不能省略原命中检查。记录 `type-public` 前空密码框、焦点和单输入法条件的检查，保留未就绪回复，使用最后稳定检查和实际公开按键方法的完成时间。
7. 保留首个后续快照中完整公开密码长度的证明；首次实际 Unlock 点击必须唯一，并与首页物理计数截图的原生时间和内容证明绑定。通用计算为 `观察方法结束 ns - 同设备启动请求 ns`；解锁观察区间使用 `首页截图方法结束 ns - Unlock 方法开始 ns`。不混用宿主与设备的绝对时钟。

上述步骤只派生已由原规范读取器审查的端点。原请求／回包、阶段状态、来源摘要或图片变化时重新审查，不沿用先前的通过标记。相同来源文件没有改变，本次不重复计算既有单元测试数量；新做的是这批数据的规范重放、控件关联和数值核对。

## 决策与后续

当前保留加载和分页策略。该队列每档只有一个带观察器、追踪和内存采样的样本，冷启动系统窗口、完整登录观察和人为输入步骤不同；这些数据不足以把差异归到路由加载或列表规模。既有[默认配置重复样本](RF-312-observer-cohort-timing.md)、失败和尾部口径仍分别保留，不混入本配置，不为获取易通过结果制造优化提交。

带明确定义的功能观察上界可以作为本地基线的一部分；它不要求先得到完美的独占耗时。RF-312 的多端测量与原方法边界继续保持。Windows 本次只读复查仍为断开连接、输入桌面不可用（错误 5），没有激活窗口或改设置。RF-112／121 及依赖任务的原平台条件不变，台账仍为 369/378、九项未完成。

见[去标识数值与摘要](rf312-application-observation-endpoints-2026-10-18.json)。原始 XML、截图、程序、trace、路径及运行标识留在本机；本项不接受精确首次可交互、前两帧内容、应用独占耗时或新的性能分布。
