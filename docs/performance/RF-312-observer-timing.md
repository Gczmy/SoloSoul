# RF-312 已有原生控制回包的耗时分析

本入口读取已完成、正常恢复的默认公开夹具队列，复用原状态、IME 和 UI 读取器核验，再计算 Observer 已有回包中的设备时钟区间。它不启动 SDK、不发送输入，不改变产品、观察器、原读取器或既有采集预算。

## 复跑

需要 Python 3.12，以及按[原生队列](RF-312-public-native-queue.md)保留的完整原件、对应 adapter 声明和原 206＋17 项当前源码回归证据。以下输出目录必须全新，并位于原生证据目录之外：

```powershell
python -B docs/performance/rf312-observer-timing/read-native-timing.py `
  --native $CompleteNativeQueue --adapter-inputs $AdapterInputs `
  --unit-evidence $OriginalUnitEvidence --output $NewTimingOutput
```

程序先按原入口建立独立 context，依次执行原 `replay_state.py`、`replay_ime.py`、`replay_ui.py`。前置失败即停止，不生成被接受的耗时结果；原 stdout、stderr 和拒绝原因保留。分析前冻结两档 request／response 和阶段文件字节，分析后再次核对源文件、原父结果与回包摘要；不使用可跳过原断言的 Python 优化模式。

每个文件上限 8 MiB，最多 512 对连续、完整的原协议回包。拒绝失败 action、错误截图身份、布尔／浮点时间、反向／重叠时间及验证后字节漂移。统计使用整数纳秒；偶数样本中位数保留精确分子／分母，p95 使用最近秩。十二阶段只绑定其原截图对应的观察区间。

## 口径

`Observer.java` 在原生方法开始和完成时调用 `SystemClock.elapsedRealtimeNanos()`；[Android 文档](https://developer.android.com/reference/android/os/SystemClock#elapsedRealtimeNanos())定义其为包含休眠的开机后纳秒数。两次调用围住获取层级、输入派发／等待、截图和 PNG 编码等工作。因此：

- 方法耗时是控制请求的实际经过时间，可能包含应用等待；不是观察器独占 CPU 开销，不能从业务总时间相减得到应用耗时。
- 首个开始到最后结束的跨度是观察通道窗口，不是启动、解锁、搜索或预览的业务延迟。
- 截图回包绑定的阶段窗口表明何时观察状态，不证明精确可交互时刻或绘制完成。
- 按 action 统计的中位／p95 是本轮请求总体描述，不是多轮业务性能分布。
- 相邻且 XML／根包一致的“仅元数据→截图”配对保留正负差值；没有随机顺序控制，不把差值认作因果观察开销。

## 验证与结果

本轮复用[公开完整行程入口的原生记录](rf312-public-trace-entry-2026-10-18.json)，两档各一轮。418／401 个成功回包全部核验；它们的开始／结束区间互不重叠。观察通道跨度分别为 141.724／137.782 秒，方法区间总和分别为 38.438／33.255 秒。两者均含控制与等待成本，不当作应用耗时，也不与前一追踪队列合并为重复样本。

15 项唯一回归及带空格异地目录中的相同 15 项通过；后者不另算新增测试。实际 CLI 核验完整状态、IME 和 UI 后派生统计。不合格单测证据、关闭断言模式均被拒绝，原生父结果没有改变。首次入口曾遗漏状态重放前置，原 UI 读取器以缺少状态收据拒绝；修正仅调整新入口的调用顺序，保留第一次失败及原件，没有放宽原读取器。

本项仅补齐已有原生控制区间的可复算分析；没有新增原生样本。帧完整性、服务统计覆盖、应用独占耗时、连续内存峰值及完整 RF-312 均未据此接受。下一步可在同一口径下分析原默认六对的已有回包，保留拒绝模式和缺失区间，继续完成原性能基线；现有数据不支持改变全路由加载或分页策略。台账保持 368/377、九项未完成。
