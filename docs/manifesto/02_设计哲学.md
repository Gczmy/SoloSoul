# 02 设计哲学

> *设计 SoloSoul 的每一个功能时，我们在回答一个问题：
> "这会让用户对自己的数据更有掌控感，还是更依赖我们？"*

---

## 五大核心原则

### 原则 1：本地优先（Local-First）

**定义**：数据首先存在于用户的本地设备上。互联网是可选的增强，不是必要条件。

**实践**：
- 所有核心功能（创建、编辑、查看、搜索）在无网络环境下 100% 可用
- 同步是"锦上添花"，不是"雪中送炭"
- 用户打开应用时，看到的是本地数据——不是加载动画

**对比**：

| 场景 | 云端优先应用 | SoloSoul |
|---|---|---|
| 打开应用 | "正在同步..." 3 秒 | 立即显示本地数据 |
| 无网络时 | 只读模式 / 无法使用 | 完整功能 |
| 服务关闭 | 数据可能丢失 | 数据仍在设备上 |
| 搜索 | 发送查询到服务器 | 本地索引，毫秒响应 |

**设计检验**：如果一个功能需要网络才能使用，它不应该存在于 SoloSoul 的核心体验中。

---

### 原则 2：隐私优先（Privacy-First）

**定义**：默认情况下，不向任何第三方暴露用户的任何数据。隐私不是可选项，是基线。

**实践**：
- 端到端加密：数据在离开设备前加密，到达眼睛前解密
- 零知识架构：开发者无法解密用户数据
- 最小化数据收集：我们不收集用户行为数据、不使用分析追踪
- 敏感度分级：每个字段都有 `SensitivityLevel`，系统自动应用相应的保护措施

**敏感度分级系统**：

```
public      → 无遮盖，任何人可见（如应用主题设置）
internal    → 模糊显示，点击展开（如常用联系人列表）
private     → 模糊显示，需要解锁查看（如家庭住址）
sensitive   → 完全遮盖，需要密码/生物识别（如银行卡号）
restricted  → 完全遮盖，需要重新验证（如护照号码）
critical    → 完全遮盖，需要重新验证 + 操作确认（如私钥备份）
```

**设计检验**：如果某个设计决策要求我们把用户数据发送到我们的服务器，这个决策就是错误的。

---

### 原则 3：用户主权（User Sovereignty）

**定义**：用户对自己的数据拥有最终、不可剥夺的控制权。

**实践**：
- 数据导出：用户可以随时完整导出所有数据，格式开放
- 数据删除：删除就是删除，没有隐藏的云端备份
- 无 vendor lock-in：不使用私有格式，数据不依赖 SoloSoul 存在
- 无强制同步：用户可以选择不同步，只做本地单机使用

**关键认知**：SoloSoul 不是 SaaS。我们不"托管"用户数据，我们**提供工具**让用户管理自己的数据。

**设计检验**：如果用户决定明天停止使用 SoloSoul，他们能否在不联系我们、不支付费用、不损失数据的情况下离开？如果不能，设计就是错误的。

---

### 原则 4：安全默认（Secure by Default）

**定义**：安全不是高级功能，不是可开关的选项。安全是默认状态，不可降级。

**实践**：
- Argon2id + AES-256-GCM 是唯一的加密方式，没有"不加密"选项
- 生物识别（Touch ID/Face ID）是推荐但非强制的便利层，底层始终有主密码保护
- 自动锁定：应用进入后台后，超时自动锁定 Vault
- 内存安全：所有密钥使用 `zeroize` 自动擦除

**反模式警示**：

```
❌ "是否启用加密？" — 用户不应该被问到这个问题
❌ "简单密码 / 复杂密码" — 密码强度应该由系统保证
❌ "导出时可选加密" — 导出必须加密，不可关闭
```

**设计检验**：如果一个安全设置可以被用户"关闭"以换取便利，这个设置本身就是设计缺陷。

---

### 原则 5：最少惊喜（Least Surprise）

**定义**：用户应该能预测系统的行为。不隐藏副作用，不做"为用户好"但用户不理解的事情。

**实践**：
- 操作日志：每次 CRUD 操作都生成 `OperationEntry`，记录 before/after 差异
- 明确告知：同步前告诉用户将要传输多少数据
- 撤销支持：删除不是永久删除，30 天内可从回收站恢复
- 透明处理：自动保存时显示"已保存"状态，不是静默后台操作

**设计检验**：当用户执行一个操作后，系统做的事情是否完全在用户预期之内？如果不是，需要重新设计。

## 产品体验的取舍

SoloSoul 在设计上有意做出以下取舍。这些不是妥协，是**价值观的表达**。

### 取舍 1：安全 > 便利

| 我们选择的 | 我们放弃的 |
|---|---|
| 主密码 + 生物识别 | "打开即用"的无密码体验 |
| 导出强制加密 | 一键明文导出 |
|  Argon2id（可能耗时 1-2 秒） | 毫秒级弱哈希 |
| 敏感字段遮盖 | 全部明文显示 |

**理由**：SoloSoul 管理的是身份数据，不是笔记。一次数据泄露的后果远大于一次解锁的延迟。

### 取舍 2：掌控 > 智能

| 我们选择的 | 我们放弃的 |
|---|---|
| 用户手动分类和标签 | AI 自动分类（需要上传数据） |
| 本地搜索（不联网） | 云端智能搜索 |
| 用户决定同步到哪里 | 自动同步到我们的服务器 |

**理由**："智能"的代价往往是数据离开设备。SoloSoul 的 AI 功能（如有）必须运行在本地，或使用联邦学习——绝不上传原始数据。

### 取舍 3：持久 > 流行

| 我们选择的 | 我们放弃的 |
|---|---|
| 开源协议 + 开放 Schema | 闭源护城河 |
| 本地 SQLite + 文件存储 | 时髦的云端数据库 |
| 极简依赖（Flutter + Rust） | 追逐最新框架 |

**理由**：个人数据管理软件需要存在 10 年、20 年。今天的"流行技术"可能是明天的技术债。

## 设计决策框架

当面临一个设计决策时，按以下顺序提问：

```
1. 这会损害用户的隐私吗？
   └─ 是 → 拒绝，重新设计
   └─ 否 → 继续

2. 这会让用户更依赖 SoloSoul，还是更有掌控感？
   └─ 更依赖 → 拒绝，重新设计
   └─ 更有掌控感 → 继续

3. 这能在无网络环境下工作吗？
   └─ 不能 → 降级为可选功能，核心路径不依赖
   └─ 能 → 继续

4. 用户停止使用 SoloSoul 时，这个功能会造成数据损失吗？
   └─ 会 → 拒绝，重新设计
   └─ 不会 → 继续

5. 这个功能的实现是否引入了不可信的外部依赖？
   └─ 是 → 评估替代方案或自建
   └─ 否 → 通过
```

**前两个问题的答案必须是"否/更有掌控感"，否则功能不应该存在。**

## 反模式清单

以下是在 SoloSoul 中**绝对禁止**的设计模式：

| # | 反模式 | 为什么禁止 | 正确做法 |
|---|---|---|---|
| 1 | 云端强制同步 | 违背本地优先 | 本地优先，同步可选 |
| 2 | 收集使用数据 | 违背隐私优先 | 零遥测，零分析 |
| 3 | 社交功能（分享、点赞） | 违背隐私优先，引入网络效应 | 纯个人工具，无社交 |
| 4 | 订阅制锁定功能 | 违背用户主权 | 核心功能免费，增值透明 |
| 5 | 强制账号注册 | 违背匿名性 | 本地账户，无需邮箱 |
| 6 | 隐藏的数据备份 | 违背透明度 | 用户明确知道数据在哪里 |
| 7 | 弱密码允许 | 违背安全默认 | 强制密码强度检查 |
| 8 | 明文导出选项 | 违背安全默认 | 导出必须加密 |

## 设计哲学与 Slogan

> **"独奏生命数据，重塑数字原点。"**

- **独奏**：你是唯一的演奏者，数据的主权在你。
- **生命数据**：不是文件，是你的人生——身份、旅行、财务、职业。
- **重塑**：从零开始，建立新的范式。
- **数字原点**：回到数据属于个人的原点状态。
