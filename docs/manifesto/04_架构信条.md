# 04 架构信条

> *"不是因为我们能做什么技术，而是因为我们相信什么价值，所以选择什么技术。"*

---

## 技术决策的第一性原理

在 SoloSoul，所有技术选型都遵循以下优先级：

```
1. 用户数据安全与隐私（不可妥协）
2. 本地优先与离线可用（核心约束）
3. 长期可维护性（10 年视角）
4. 性能与资源效率
5. 开发效率与生态丰富度
```

**前两个优先级是硬约束。任何技术如果违反 1 或 2，无论多么流行、多么方便，都不被采用。**

---

## 信条 1：数据存储 — 文件系统优先于数据库服务

**信条**：用户的个人数据应该以文件形式存在于用户可见的文件系统中，而不是被埋藏在应用沙盒的某个数据库里。

**实践**：
- Vault 数据存储在 `~/.solosoul/{account_id}/`（或平台等效路径）
- 附件是独立的加密文件（`.solo` 格式），可以直接看到
- 配置是 JSON 文件，可以用文本编辑器打开

**为什么**：
- 用户知道数据在哪里
- 可以用标准工具备份（Time Machine、rsync）
- 即使 SoloSoul 消失，文件还在
- 调试和排障更简单

**反模式**：
- ❌ 使用 Core Data / Realm 等不透明数据库
- ❌ 数据埋在应用沙盒深处，用户找不到
- ❌ 自定义二进制格式，只有应用能读取

## 信条 2：密码学 — 标准算法，标准实现

**信条**：使用经过公开审计、广泛部署的标准密码学算法和库。绝不自创算法，绝不使用未审计的实现。

**批准的算法**：

| 用途 | 算法 | 库 |
|---|---|---|
| 密钥派生 | Argon2id | `argon2` (RustCrypto) |
| 对称加密 | AES-256-GCM | `aes-gcm` (RustCrypto) |
| 备选对称加密 | ChaCha20-Poly1305 | `chacha20poly1305` (RustCrypto) |
| 密钥交换 | X25519 | `x25519-dalek` |
| 数字签名 | Ed25519 | `ed25519-dalek` |
| 哈希 | SHA-256 / BLAKE3 | `sha2` / `blake3` |
| 随机数 | CSPRNG (OsRng) | `rand` |
| 安全擦除 | `Zeroizing<T>` | `zeroize` |

**禁止**：
- ❌ 自定义加密算法
- ❌ 使用未经验证的第三方加密库
- ❌ 硬编码密钥或 IV
- ❌ 重复使用 nonce
- ❌ 降低密钥长度或迭代次数来"优化性能"

**算法可插拔性**：
- Vault 元数据中记录使用的算法版本
- 未来可以迁移到新算法（如后量子密码学），旧数据仍可读

## 信条 3：依赖最小化 — 少即是多

**信条**：每增加一个依赖，就增加了一个信任对象、一个攻击面、一个维护负担。

**Go 后端的极端实践**：仅 2 个直接外部依赖（`golang.org/x/term` 和 `protobuf`），其余全部标准库。

**Rust 核心的原则**：
- 优先使用标准库
- 外部依赖必须经过安全审计或有广泛使用基础
- 定期 `cargo audit` 检查依赖漏洞
- 不因为"方便"引入重量级框架

**Dart/Flutter 侧的原则**：
- 状态管理只用 `flutter_riverpod`，不混用 `Bloc`/`MobX`
- UI 组件优先使用 `liquid_glass_widgets`，不引入 Material 3 回退
- 不因为"生态丰富"引入不必要的包

**依赖决策检查清单**：

```
□ 这个依赖解决的是我们必须解决的问题吗？
□ 这个依赖的维护状态活跃吗？（最近 6 个月有提交？）
□ 这个依赖有已知的安全漏洞吗？（cargo audit / npm audit）
□ 如果不使用这个依赖，自建实现的成本是多少？
□ 这个依赖的许可证与我们的项目兼容吗？
□ 引入这个依赖后，编译时间/包体积增加多少？
```

## 信条 4：错误处理 — 显式优于隐式

**信条**：错误应该被显式处理，而不是静默吞掉。用户应该得到清晰的错误信息，而不是崩溃或奇怪的行为。

**Rust 侧**：
- 使用 `thiserror` 定义清晰的错误类型
- 不使用 `.unwrap()` 或 `.expect()` 在生产代码中
- 错误信息包含上下文（"解密失败：密文可能已损坏或被篡改"）

**Dart 侧**：
- 使用 `Result<T, E>` 模式（via `dartz` 或 freezed）
- 不返回 `null` 表示错误
- 错误处理统一在 Provider/Notifier 层，UI 只展示

**Go 侧**：
- 包级别预定义错误变量（`var ErrVaultLocked = errors.New(...)`）
- 跨包传递原始错误，不包装为字符串
- 表驱动测试，精确错误比对

## 信条 5：测试 — 不是可选项

**信条**：没有测试的代码是未完成代码。测试不是"以后补"，是"现在写"。

**测试策略**：

| 测试类型 | 覆盖范围 | 工具 |
|---|---|---|
| 单元测试 | Rust crypto、Dart Provider 逻辑 | `cargo test` / `flutter test test/unit/` |
| Widget 测试 | 页面渲染、交互流程 | `flutter test test/widget/` |
| 集成测试 | FFI 端到端、同步协议 | `flutter test integration_test/` |
| 安全测试 | 加密往返、篡改检测 | `cargo test`（crypto 模块） |

**测试原则**：
- 新功能必须有测试
- Bug 修复必须有回归测试
- 测试使用 `t.TempDir()`，不污染文件系统
- 测试不依赖外部网络

---

## 信条 6：跨平台 — 原生优先于模拟

**信条**：每个平台都应该获得原生的、最优的体验，而不是最低公共分母的模拟。

**实践**：
- macOS：Liquid Glass 设计语言、Touch ID、Keychain、原生菜单
- iOS：Face ID、iOS 控件、Haptic Feedback
- Android：Material You 适配、指纹、本地加密回退
- Windows：Windows Hello、原生文件对话框
- Linux：系统钥匙串、标准路径

**不追求"完全一致"**：允许各平台有差异化的体验，只要核心功能一致。

---

## 信条 7：向后兼容 — 尊重用户已有数据

**信条**：用户的数据比我们的代码更重要。新版本必须能读取旧版本的数据，不能要求用户"重新导入"。

**实践**：
- Vault 格式版本化（当前 SOLO blob v2/v3）
- 自动迁移：检测到旧格式时静默升级
- 降级保护：新版本写入的数据，旧版本至少能识别为"不支持的格式"而不是崩溃

**迁移策略**：
```
检测到旧格式
    ↓
读取旧数据（使用旧格式解密逻辑）
    ↓
转换为内部模型
    ↓
使用新格式重新加密
    ↓
原子替换文件
    ↓
记录迁移日志
```

## 信条 8：可观察性 — 不发送数据，但记录数据

**信条**：SoloSoul 不向开发者发送任何用户数据，但应用本身应该有完善的本地日志和诊断能力。

**实践**：
- 操作日志：每次 CRUD 生成 `OperationEntry`，本地存储
- 调试日志：可选开启，写入本地文件，不包含个人数据
- 性能指标：本地测量，不上传
- 崩溃报告：如果用户选择发送，先由用户审查内容，再手动发送

**日志分级**：
```
ERROR → 影响功能的错误，用户应该被告知
WARN  → 非致命问题，可能影响体验
INFO  → 重要操作记录（如同步完成、导出成功）
DEBUG → 开发调试信息，默认不显示
TRACE → 详细流程跟踪，仅在调试模式启用
```

## 信条 9：性能 — 足够快，而不是最快

**信条**：性能优化的目标不是 Benchmark 第一，而是用户体验流畅。

**具体标准**：
- 打开应用：≤ 1 秒（本地数据，无网络等待）
- 搜索响应：≤ 100 毫秒（本地索引）
- 保存数据：≤ 200 毫秒（含加密写入）
- 解锁 Vault：≤ 2 秒（含 Argon2id KDF）
- 同步 1MB 数据：≤ 10 秒（局域网）

**不过度优化**：
- 不为 10% 的场景牺牲 90% 场景的可维护性
- 不因为"可能慢"而提前引入缓存层
- 性能问题出现后再 profile，再优化

---

## 信条 10：透明 — 代码即文档

**信条**：代码应该自解释。注释解释"为什么"，代码解释"做什么"。

**注释规范**：
- 中文注释为主，技术术语保留英文
- 每个 public API 必须有 doc comment
- 复杂的算法必须有注释说明原理
- 不注释显而易见的代码（`i += 1 // 增加 i` ❌）

**文档即代码**：
- ADR（架构决策记录）与代码变更同步更新
- 用户契约的变化必须反映在产品行为中
- 架构信条的变化必须经过团队讨论

## 技术债务的处理

技术债务不可避免。我们的处理原则：

1. **记录**：发现技术债务时，在 TODO.md 或 issue 中记录
2. **评估**：评估债务的影响范围和风险
3. **计划**：在重构路线图（如 Tauri 重构）中安排偿还
4. **不累积**：不因为"以后重构"而在当前写劣质代码

**当前已知的技术债务**：
- Flutter 端的同步功能有已知 Bug（不修复，在 Tauri 重构中重写）
- Go 后端已废弃，但文档中仍有引用（正在清理）
- iOS Keychain Handler 缺失（P0 问题，临时回退到文件存储）

## 信条检验

当你做技术决策时，问自己：

```
□ 这个决策会损害用户隐私吗？
□ 这个决策会让数据离开用户设备吗？
□ 这个决策增加了不可信的依赖吗？
□ 这个决策在 5 年后仍然合理吗？
□ 这个决策让用户更难离开 SoloSoul 吗？
□ 这个决策有测试覆盖吗？
```

**任何一条的答案如果是"是"，请重新考虑你的决策。**
