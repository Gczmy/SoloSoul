## 已验证的失败

两次修复前测试使用生产主包 `f82370125a99ce46260a2cecea7fed7396fc60d55a30be498ccc052b75341c13`、冷启动测试包 `d630f4502b1c38521865cf85c9198e148d86f78001ae6f43afc3835ba13d8858`。18 阶段的生产 UI 双账户准备成功不是冷启动通过。

- `attempt-1-supported`：第一阶段通过，驱动误将 instrumentation 完成后的 `pidof` 退出 1 当作故障，未执行第二阶段，整体退出 1。改为允许已退出的原进程；若出现不同或多个 PID 则仍拒绝操作。源码见 `initial-source.json`。
- `attempt-2-supported`：第一阶段 PID 8609，确认已结束后启动第二阶段 PID 9027。私有目录中两份清单 / 账户身份核验通过，但实际 WebView 进入 `/bootstrap`，显示 Create Account 和首次引导，锁定页等待失败；冷启动接受阶段为 0，整体退出 1。没有因 instrumentation 最后返回 -1 就判定成功；方法状态 -2 和失败原文保留。
- 第二次 PID 纠错后的驱动没有在执行时单独冻结；原生测试源码仍为 initial-source 版本，原始日志和报告保留。不能将之后的 fixed-source 当成第二次运行的精确驱动快照。
- 两次均完整恢复 242 项私有文件内容 / 链接 / 权限、私有根权限、blur、通知授权 / 标记与系统夜间模式。未证明数据丢失：两份合成账户在启动前仍存在。

## 限定的生产修复

移动端启动没有保存 SAF URI 时，原来总是创建 `.uninitialized_vault` 占位服务。此前通过 UI 选择应用私有目录并建立账户也没有 SAF URI，因此进程重启会读取错误的空根。

现在复用原 `try_init_local_vault` 工厂：应用私有根已存在 `accounts.json` 时加载该根，否则仍创建占位服务。只判断清单存在，不扫描或搬迁账户，不改变 SAF 优先级、失效 SAF 恢复、认证、密码学或目录锁。目录错误继续返回错误，不切入另一个空根。

真实服务重建的 3 项 Rust 回归通过：已有账户恢复但保持锁定；只有 UI 偏好 / 锁文件的首次安装仍进入占位根；已有根繁忙时失败而不生成空占位根。默认功能 Clippy（含测试）`-D warnings`、最终 Rust fmt 与驱动 18 项单测通过。初次 fmt 检查指出两处排版，格式化后复验通过。

## 目录修复后的第二个外观失败

`attempt-3-root-fixed-supported` 使用主包 `819b14d1a444cebe2fdd2e6eb2cd2717c0e0d1ec2289bcf0fc99b642662ee1a3`、测试包 `2af4ed5744928f26da075447e95b9bc128dc0baeec4ed81369584347a6be717b`，源码为 `fixed-source.json`。第一阶段 PID 9422，第二阶段 PID 9848；实际 `/login`、两个账户和密码区已恢复，但显示 light / local / ocean，没有恢复 A 的 dark / enhanced / custom。整体退出 1，0 冷启动接受阶段；全部 242 项数据与系统设置恢复。

后续发现并分别复现两个外观持久化缺陷：

- `lazy_cleanup_old_ui_prefs` 只比较路径文本，目录别名指向同一文件时会误删现有配置。临时目录回归修复前 1/1 失败；文件身份判断同时用于清理和迁移，修复后后端偏好模块 24/24 通过。Android 专用应用的 `/data/user/0` 与 `/data/data` 路径实际设备号 / inode 相同；只读身份检查保留，未读取账户内容。配置读取也与写入共用原有文件锁，避免读到覆盖中的部分 JSON。
- `loadSettings` 切换账户后未刷新启动缓存。新的 A / B 配置回归修复前失败、实际保留 B 的 light / local / custom 黄色；现在从当前账户确认值更新缓存，不复制正在保存的乐观值。61 项设置 / 会话 / 认证 / 主题定向测试与定向 ESLint 通过。

原生准备阶段增加真实 `ui_get_preferences` 回执：等待 A 的五个外观键已落入登录前镜像，再结束原进程。只等待真实读取结果，不调用写入、解锁或主题注入；原生冷启动外观断言保留。`prefs-fixed-source.json` 是缓存修复前的中间源码，`final-native-source.json` 是随后新包的 8 份生产 / 测试 / 驱动源码来源。最终主包与测试包已重新构建，两组设备结果如下；单测与原生证据分别登记。

## 新包接受门槛

原生测试仍通过生产 UI 创建两个账户和一个公开对象，第一阶段结束后强制停止应用，再执行不同 PID 的第二个 instrumentation 方法。第二阶段必须满足：

1. 真实 `/login`、两个账户、密码区存在，未进入首页；恢复上一次 A 账户的深色 / 森林底色 / 增强玻璃 / 自定义强调色。
2. 通过密码 UI 解锁 A；在系统浅色与深色下均维持 A 的显式深色主题、1 对象和实际文字 / 画布分区。
3. 锁定并选择 B，再通过密码 UI 解锁；B 保持显式浅色、局部玻璃、不同强调色与 0 对象，五个加密账户偏好不串用。
4. 两个方法分别精确 1 项通过、0 跳过；图片包含实际正文及操作文字像素、足够对比度和命中检查，完整数据与系统设置恢复成功。

`fixed-source.json` 对应第三次目录修复后的失败；最终通过使用 `final-native-source.json` 的 8 份源码。两组执行后再次核对快照与当前源码 SHA256 一致，与旧 APK 的来源分开。

此场景不替代原生非空附件预览、旧 WebView、多窗口、其他键盘、iOS、实体设备性能或完整 macOS 验收。FE2 总数保持 8 完成 / 6 待验证。
