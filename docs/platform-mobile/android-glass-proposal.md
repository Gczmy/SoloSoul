# Android 玻璃材质增强方案

日期：2026-09-15。状态：**已按审核方案接入客户端**，当前默认局部玻璃；实现细节与客户端验证见 [实施记录](android-glass-implementation.md)。下文保留审核时的设计参数和原型说明。本方案接续已完成的 Material 3 Expressive 改造，保留四入口导航、现有业务与敏感字段机制。

## 审核入口

- [交互 HTML](android-glass-review.html)：三屏对照、组合方案、深浅外观、材质开关、系统模糊失效模拟，以及可调节的液态折射样片。单文件可离线打开。
- [浅色总览](android-glass-overview.png)、[深色总览](android-glass-overview-dark.png)。截图为 HTML 渲染结果，使用虚构数据。
- [组合方案手机截图](android-glass-combined-mobile.png)、[折射样片](android-glass-optical.png)。
- 推荐先比较三屏，再切到“组合方案”，操作底部导航和新建菜单；向上滚动对象列表观察内容从导航栏后方经过。
- 下方光学样片可用指针、触摸、强度滑块或“播放 4 秒”查看折射。减少动效时保留静态材质。

**预览真实性：**局部玻璃是实际 CSS 背景模糊；液态样片是实际 WebGL 着色器，折射其自行生成的网格与色带；系统窗口模糊使用 HTML 模拟视觉层次，浏览器没有调用 Android Window API。三者均不代表已通过 Android 真机性能验证。

## 建议采用的组合

采用“清晰内容、局部通透、少量折射”。主窗口仍用现有稳定色底，玻璃集中于导航和短时操作层，液态效果集中于首页装饰。

| 区域 | 材质 | 设计目标 | 默认策略 |
| --- | --- | --- | --- |
| 系统栏与 AppBar | 连续的色调底 + 局部模糊 | 滚动内容延伸到顶部，状态栏图标与标题保持清晰 | AppBar 为 64 CSS px，系统 inset 另加；不新增重复顶部留白 |
| 手机底部导航 | 浅着色毛玻璃 | 可感知下方内容，选中项始终清晰 | 距左右边缘 12px；导航本体 77–80px；底部 inset + 6px；图标与标签位置固定 |
| 平板导航轨道 | 色调表面，局部玻璃可选 | 大屏仍有明确分区 | 沿用 88px 轨道；先验证是否有值得透出的内容 |
| 搜索输入框、对象行、字段容器 | 实色色调表面 | 保证输入、阅读、掩码对比度 | 继续复用现有组件 |
| 新建快捷菜单 | 原生圆角窗口背景模糊 + 轻度 blur behind | 让当前操作靠前，保留页面上下文 | Android 支持且开启时升级；首轮仅三项快捷操作 |
| 复杂表单、对象详情、密码验证 | 现有 React 弹层；局部 CSS 玻璃外壳可选 | 保留焦点、返回栈、揭示与验证行为 | 字段本身保持实色；不为材质重复业务实现 |
| 首页概览装饰 | 自绘液态徽记 | 一处可感知的折射与边缘高光 | 默认强度 35/100；文字在独立前景层；其他页面不常驻 |
| FAB | 色调填充为主，轻边缘高光 | 主动作稳定易找 | 不缩放图标、不改变标签锚点；首轮不做全内容折射 |

手机底栏由贴边色块改成悬浮玻璃，是本轮明确提出的布局调整；触摸区域与手势安全区不会跟着视觉边框缩小。首尾滚动留白需要与新几何一致。

## 三种渲染路径

### A. 应用内局部玻璃：优先实施

`backdrop-filter: blur(...) saturate(...)` 模糊的是元素后方的网页绘制内容，前景文字单独呈现。它适合当前 React + WebView 架构，不能采样壁纸，也不单独产生光学折射。[Chrome 团队的背景模糊说明](https://web.dev/articles/backdrop-filter)

实施位置：`tauri/src/styles/android.css`、`components/android/AndroidAppBar.tsx`、`AndroidNavigation.tsx`、`AndroidSheet.tsx` 和 `components/layout/AppShell.tsx`。

- 提取 `AndroidGlassSurface` 或等价材质类，统一颜色、浓度、模糊、边缘与层级；避免每个页面随意叠加滤镜。
- 固定栏覆盖滚动层，内容通过内边距避开首屏遮挡，但滚动后允许经过栏后。不要在 fixed 父级引入改变定位基准的 transform。
- Portal 浮层继续放在应用根内容之外。玻璃伪元素只画材质，不接收点击；清晰内容放在其前景，轮廓与模糊采用同一圆角。
- `CSS.supports` 与实际 WebView provider 版本共同用于诊断；CSS 支持检测不能证明 GPU 表现良好。AndroidX WebKit 依赖版本不是设备实际 WebView 版本。[Android WebView 版本 API](https://developer.android.com/develop/ui/views/layout/webapps/managing-webview#version-api)
- 不在滚动过程中插值 blur 半径。页面切换保持现有稳定呈现，只更新选中背景；不重播整个首页入场。

### B. 系统窗口模糊：独立原生菜单的渐进增强

Android 12 / API 31 起公开了跨窗口模糊。`setBackgroundBlurRadius` 作用于当前窗口边界内的后方窗口；`FLAG_BLUR_BEHIND` 配合 `setBlurBehindRadius` 则柔化窗口后方区域。窗口需要透明/半透明背景与明确轮廓，设备及系统状态会决定是否提供效果。[AOSP 窗口模糊文档](https://source.android.com/docs/core/display/window-blurs)

**当前差距：**`MainActivity.kt` 继承 TauriActivity；主要 UI 都在一个 WebView 中。现有 `AndroidSheet` 是 DOM Portal，并不是 Android Window；仅给主 Activity 设置模糊不会模糊同一 WebView 的某个浮层背景。当前主题也没有透明浮动窗口配置。

建议新增一个由 MainActivity 持有的原生 `Dialog`，通过窗口级 API 绘制三项快捷操作。它覆盖当前应用窗口，底层主窗口继续保持不透明。目标是模糊本应用页面，而不是依赖桌面壁纸或其他应用作为背景。

接入流程：

1. 新增 Android 材质桥接插件，暴露能力快照、能力变化事件、打开/关闭快捷菜单及返回的 action ID。通过项目现有 Tauri 插件/IPC 路径接入，避免另建 JS 任意执行通道。
2. 复用当前 React 端上下文与权限判断。原生菜单只接收本地化标题、固定 action ID、主题 token 和一次性请求标识；不接收主密码、解密字段或全部对象数据。
3. Dialog 使用单独 theme 与圆角 ShapeDrawable。设置背景浓度、背景模糊、必要的 blur-behind/dim；不把根 WebView reparent 到 Dialog，不改变整个主 Activity 的透明主题。
4. 监听 `isCrossWindowBlurEnabled` / `addCrossWindowBlurEnabledListener`，系统关闭模糊时同步增大底色 alpha 与遮罩。销毁时移除监听；旧 Window 回调不得修改新实例。
5. 用户点击后仅返回允许的 action ID。前端重新检查账户与上下文，然后调用既有 `androidNewObjectUrl`、页面表单或 OCR 路由。请求完成/取消只处理一次，避免双重导航。
6. 原生菜单打开/取消与 `useOverlayBackGuard` 协调，确保一次返回只关闭一层。只有页面表单打开后才使用现有 React 返回栈，不给同一菜单同时注册两套守卫。
7. 区分“应用仍在前台但 Dialog 获取焦点”与真正进入后台。材质窗口不应触发误锁，也不能暂停真正的后台自动锁定；账户锁定/退出时必须关闭菜单并使待处理 action 失效。

若设备不支持系统模糊，或原生桥接失败，则采用同一 React 操作菜单和局部玻璃；用户选择关闭全部玻璃时再使用实色表面。系统失效是能力变化，不应变成反复出现的提示。

### C. 自绘液态：先采用 WebGL 装饰，再评估 AGSL

需要区分“透镜渲染”与“背景来源”。光学外观可通过圆角距离场、局部法线、偏移取样、少量色散和边缘高光构成；着色器不会自动拿到其后方的 DOM。

本次 HTML 已采用 WebGL 进行实际偏移取样，来源为同一个着色器生成的网格/色带。正式首版可以移植这条路径，仅在非敏感概览装饰中使用；数量、标题、按钮依然是普通 React 元素，不进入纹理。

Android 13 / API 33 起可使用 `RuntimeShader` / AGSL；它工作在 Android Canvas / RenderNode 绘制管线，所需输入仍须由调用者提供。已有 `RenderEffect.createBlurEffect` 模糊的是被绑定的 RenderNode 内容，并不是给任意 WebView 子节点加一个“背景材质”。[RuntimeShader](https://developer.android.com/reference/android/graphics/RuntimeShader)、[AGSL 取样机制](https://developer.android.com/develop/ui/views/graphics/agsl/agsl-quick-reference)、[RenderEffect](https://developer.android.com/reference/android/graphics/RenderEffect)

因此当前优先 WebGL：无需给同一装饰区增加原生视图的位置同步与触摸分发。AGSL 可以在后续原生组件中复用光学思路，但需独立验证效果与性能，不能把 HTML 效果直接宣称为 AGSL 实机结果。

首轮不承诺“任意页面文字/卡片在玻璃下面连续实时折射”。若后续要求该效果，需要先证明 WebView 背景采样和纹理更新可行；不能默认通过逐帧截图或每帧 IPC 达成。

## 初始材质参数

以下为 SoloSoul 的待审核起始值，不是 Google 或 Apple 官方规范。CSS px 与 Android API 接收的物理 px 分开处理，原生目标 dp 需按设备 density 转换。

| 参数 | 局部玻璃 | 原生快捷菜单 | 自绘液态 |
| --- | --- | --- | --- |
| 着色底 | 现有 surface 配色 | 当前深浅主题色 | 现有 primary-container 派生装饰色 |
| 浅/深底色 alpha | 0.76 / 0.80 | 初始 0.71 / 0.76 | 前景文字区至少 0.93 的阅读底 |
| 模糊 | 18 CSS px；弹层 24 CSS px | 背景半径初始 24dp 转 px；behind 4dp 转 px，实机调参 | 不做整页 blur；透镜取样与高光 |
| 圆角 | 底栏 27px；外壳 24–30px | 30dp；左右至少 10–16dp 留白 | 保持徽记包围盒稳定 |
| 动效 | 选中背景 180–240ms | 最多约 300ms 平移；不同时动画模糊半径 | 默认强度 35；短时输入驱动，静止不持续绘制 |
| 减少动效 | 直接更新最终状态 | 直接显示最终位置 | 保留一帧静态折射，禁用连续播放/随动 |

HTML 中的状态栏和手势区都是示意高度；落地继续由 Android WindowInsets 与现有安全区逻辑提供实际值。分屏时保留现有 caption bar 处理。

## 能力与设置

沿用现有三套配色和减少动效，不增加多个难以理解的实验开关。用户侧建议增加“玻璃材质”三档：关闭 / 局部玻璃 / 增强玻璃。增强档加入首页折射及支持设备上的系统菜单；初始默认局部玻璃，增强档待真机验证后再决定是否默认。

开发侧能力状态独立于用户偏好：`backdropFilter`、WebGL 可用与上下文状态、Android API、跨窗口模糊当前状态。`reduceMotion` 与“减少透明度/实色”是不同诉求，不能混为一个开关。

| 情况 | 有效表现 |
| --- | --- |
| Android 9–11，WebView 支持 CSS | 局部玻璃可用；系统窗口模糊不启用；WebGL 通过能力和性能验证后可用 |
| Android 12+，系统允许窗口模糊 | 可以启用原生菜单材质；仍需设备验证 |
| Android 13+ | 额外具有 AGSL API；不是必须切换渲染后端的理由 |
| 系统关闭跨窗口模糊 | 原生菜单提高色底和遮罩；CSS 玻璃是否继续由其自身策略决定 |
| 无 CSS 支持 | 使用不透明色调表面，布局与交互尺寸保持一致 |
| WebGL 创建失败或上下文丢失 | 显示现有概览静态装饰，文字与操作继续可用；恢复时重建材质资源 |
| 用户关闭玻璃或高对比/性能保护策略生效 | 实色材质；不隐藏入口、不缩小触摸区 |
| 应用隐藏、装饰离屏、账户锁定 | 停止连续绘制；锁定卸载字段与敏感状态；返回后按需绘制一帧 |

## 实施顺序与验收

1. **局部玻璃与几何。** 调整主题 token、AppBar、底栏与滚动留白，验证透明/实色切换不移动布局，Portal 不被覆盖，底部对象能完整滚出 FAB/导航覆盖区。
2. **原生快捷菜单验证。** 在独立 Dialog 中验证系统模糊、圆角、能力变化、前后台往返；通过后再接入三项真实操作及取消/锁定路径。原生失效仍有同一操作入口。
3. **单个液态组件。** 将光学样片限制在首页，支持离屏停绘、上下文丢失恢复、减少动效与低成本静态回退；不把全页放入着色器。
4. **设备验证后确定默认。** 保留用户可比较的局部/增强档，依据性能与可读性结果决定增强是否默认。

性能目标是待验证的验收线：60Hz 设备按约 16.7ms 帧预算观察滚动，玻璃版本相较实色版本不产生持续性卡顿；shader 静止时不持续产生帧；离屏或后台不渲染。不以桌面浏览器结果替代真机耗电和 GPU 测量，也不预先保证所有设备都能消除平台合成闪烁。

重点矩阵：

- Android 9–11 / 12 / 13+，至少一台中低端设备与一台高刷新设备；当前 WebView 与一版较旧 provider。
- 浅/深主题、三套配色、强明暗背景、敏感字段掩码与揭示；正文目标对比度至少 4.5:1，边界与交互提示至少 3:1，并按真实合成结果测量。
- 320–430px 手机、大屏轨道、横屏/分屏、字体放大、三键/手势导航、软键盘弹出与关闭。
- 冷启动、连续前后台切换、返回首页、原生菜单显示期间切后台/锁定、系统临时关闭 blur、WebGL context loss。
- 导航图标位置/尺寸恒定、一次返回关闭一层、遮罩不可点穿、关闭后焦点恢复、真实后台仍按现有规则自动锁定。

## 原型验证结果

- Chrome 通过 320、360、390、430、768、820、1024、1440px 八档宽度检查：页面与手机容器无横向溢出；导航交互区域至少 48×48px。
- 已验证导航图标切换前后几何不变、搜索/分类/空结果、字段示例揭示与关闭清理、锁定移除内容、菜单取消及焦点恢复、局部玻璃/实色切换、原生模糊不可用时的样式切换。
- 用户减少动效与系统 `prefers-reduced-motion` 均生效。实际比较 Canvas 像素，确认指针移动改变了光学输出；主动触发 WebGL context loss 后成功恢复渲染。
- WebKit 手机宽度下的组合方案、菜单、深色外观与基础交互通过。浏览器无脚本异常，页面未发出外部 HTTP 请求。
- 已目测浅色、深色、手机组合与光学样片截图。上述结果只对应独立 HTML，未测试原生 Dialog、Android WebView GPU 性能或实机前后台切换。
