# SoloSoul 移动端色彩与材质统一方案

> 2026-10-07。设计讨论稿，未修改客户端或重构执行清单。移动端先以现有 Android 实现为基线；iOS 可复用色彩与表面职责，原生材质另行评估。

建议移动端与桌面端共用主题色板、文字层级、强调色和状态色，保留移动端的底部导航、底部弹层、大触控区与局部玻璃。两端共同遵循“导航有材质、正文有稳定底色、操作有明确主次”的规则。移动端的高级感来自清晰层次、细腻边缘和合适的按压反馈，不依赖每张卡片使用不同颜色。

## 1 当前割裂的来源

| 来源 | 当前行为 | 影响 |
| --- | --- | --- |
| [主题应用](../../tauri/src/lib/theme.ts) | `applyScheme` 后再执行 `applyAndroidMaterial` | 桌面主题的底色和文字色在 Android 被后续覆盖 |
| [Android 独立色板](../../tauri/src/lib/androidMaterial.ts) | 固定浅绿灰 / 深绿灰底色；相同 ocean、forest、amber 在两端有不同色值 | 选相同主题与强调色，也不像同一套产品；custom 会回退 ocean |
| [Android 页面样式](../../tauri/src/styles/android.css) | 页面卡片用 `nth-child` 分配 secondary / tertiary 底色；neutral 与 quiet 按钮也使用 primary container | 排列顺序被误读为业务类别或选中状态，次要按钮过于突出 |
| 同一文件的玻璃 token | 浅色 `rgb(249 250 246 / 76%)`、深色 `rgb(29 38 33 / 80%)`，固定偏绿 | 玻璃与暖石、冷灰、粉色等主题不能自然协调 |
| [首页玻璃装饰](../../tauri/src/components/android/AndroidLiquidArtwork.tsx) | 独立调用 `androidMaterialTokens`；WebGL 用 primary、secondary、tertiary 混色 | 只改 CSS 会留下另一套装饰颜色，需一起改主题输入 |
| [移动端外观设置](../../tauri/src/components/android/AndroidAppearance.tsx) | 主要提供模式和三个强调色色板 | 不能完整表达桌面已有的底色方案与强调色独立选择 |

现有玻璃已经将前景文字与装饰分层，并提供原生菜单、CSS 与 WebGL 回退。应复用这些能力；重构重点是色彩来源和表面职责，不重新开发一套材质引擎。参见[现有实施记录](android-glass-implementation.md)。

## 2 统一的部分

### 2.1 共用底色方案与强调色

主题分为三项：深浅模式、底色方案、强调色。使用桌面现有 [themeSchemes](../../tauri/src/lib/themeSchemes.ts) 和主题配置，移动端不再将这三项合并为独立 Material 色板。

默认沿用暖石色板与海蓝强调色；青绿、冷灰等只是用户可选主题，不把之前登录预览的绿色固定为品牌唯一颜色。一个账户在两端选择相同配置时，正文底色、文字色、危险色、主操作色一致，导航只因平台材质和环境合成略有差异。

暖石主题的示例映射如下，来自当前桌面色板，并非新的强制全局颜色：

| 语义 | 浅色 | 深色 |
| --- | --- | --- |
| 基础底色 | `#fafaf6` | `#1f1c18` |
| 内容卡片 | `#fdfcf9` | `#2a2620` |
| 主文字 | `#1f1c18` | `#ddd8c8` |
| 次文字 | `#7a7265` | `#a69d8a` |

玻璃着色、弱强调底色和输入区由已解析的主题生成，不能再独立读取一次系统深浅模式。主按钮前景色根据最终强调色计算；自定义色同样参与对比检查。对比不足时提高文字或控件的对比，不让低对比预览直接成为正式样式。

### 2.2 共用表面职责

| 职责 | 桌面表现 | 移动表现 |
| --- | --- | --- |
| 导航外壳 | 半透明侧栏和窗口顶栏 | 轻着色 AppBar、悬浮底部导航；平板导航轨道 |
| 工作内容 | 纯色圆角内容面 | 连贯的纯色正文，顶角可轻收圆角；手机不增加厚重外围框 |
| 内容分组 | 中性卡片、行式列表 | 同色系分组卡片、整行触控，减少每项单独套框 |
| 临时操作 | 菜单与少量操作浮层 | 半透明底部菜单、选择器；长表单和对象字段使用实色 |
| 主操作 | 一个高强调入口 | 新建 FAB 或主按钮使用统一强调色 |
| 局部品牌材质 | 登录玻璃面板 | 登录面板、首页一处小型玻璃装饰 |

共享的是功能与表面的关系，几何按平台适配。手机不复制桌面的交通灯、侧栏布局，也不把 desktop 32px 按钮作为触控尺寸。

### 2.3 共用操作层级

主操作用实色强调底色；次操作用中性浅底色；低强调操作用文字或图标加按压反馈。取消、指南、更多等不统一染为强调色。危险操作继续使用红色文字，必要时加轻量红色底色，避免把所有删除入口做成高亮红块。

对象字段敏感度、同步状态和警告保留语义色与图标；不能为了“全中性”抹掉状态区别。类别卡片取消按索引着色；用户明确选择的页面图标或颜色可作为小范围身份标记，不能和选中反馈混用。

## 3 保留移动端的材质特色

### 3.1 玻璃集中在导航和短时操作面

默认使用局部玻璃。AppBar 与底部导航共享主题色相和材质公式；导航比正文略深或略暖，正文不透明。底栏可保留悬浮留白与柔和阴影，利用掠过其后的内容体现深度，不增加全屏背景模糊。

建议起点：导航填色约 88%～92%，短操作弹层约 90%～94%，背景模糊 12～18 CSS px，弹层沿用现有约 24px 后实机调整。深色模式减弱边缘高光，避免出现白边框。百分比只作用于背景颜色，不作用于容器、图标或文字；这些是预览参数，最终取决于叠加背景与可读性。

阴影主要给悬浮导航、FAB、弹层提供深度；普通对象卡片靠底色差和间距分组。静止时不持续播放光带、呼吸或流动动画。

### 3.2 增强档位增加光学细节

保留 `off / local / enhanced` 三档和用户已有偏好：

| 档位 | 设计表现 |
| --- | --- |
| 关闭 | 同一套颜色与几何，导航、菜单变成实色；不丢失表面层次 |
| 局部玻璃，默认 | 导航和短时菜单轻模糊，薄边高光；正文、字段、表单实色 |
| 增强玻璃 | 增加首页小范围折射装饰，以及已有支持设备上的原生新建菜单；内容与文字位置保持相同 |

增强档位的首页概览卡片仍以中性底色承托名称和数量，玻璃装饰限制在右侧预留区域，不覆盖文字。自绘场景从同一主题快照取得颜色，减少独立的黄绿 / 桃色混色；背景纹理仍仅用自绘内容，不取真实对象字段或屏幕截图。

系统窗口模糊只保留在现有独立原生菜单能力范围，不扩为主 Activity 的全屏透明。Android 12+ 的跨窗口模糊依赖设备和系统状态，可能在省电等状态下关闭；关闭时提高底色不透明度、保留遮罩和层次。[Android 官方窗口模糊说明](https://source.android.com/docs/core/display/window-blurs)

### 3.3 移动端几何与动效

保留现有 48px WebView 命中区，并在真实设备核对其有效物理尺寸；Android 官方建议交互区域至少 48dp，图标可小于命中区。[官方触控尺寸说明](https://support.google.com/accessibility/android/answer/7101858?hl=en)

建议普通内容分组圆角 16～20px、底部导航与弹层 24～28px，减少所有组件统一 24px 的膨胀感。图标约 20～24px，正文约 15～16px，关键字段不少于 16px；名称、数量和图标不因按压缩放而错位。按钮视觉可以轻，命中区仍完整。

导航选中以稳定的短底色块或图标胶囊表达，不改变图标尺寸。弹层保留自下向上进入与返回键关闭；建议 240～320ms 为调试起点，尊重减少动态效果。这里只收敛新增动效，不改动已经稳定的返回栈。

## 4 各页面的改造方向

| 页面 | 建议 |
| --- | --- |
| 首页 | 概览使用中性内容卡片，统计数据不染不同颜色；页面卡片统一底色；增强装饰固定在一处 |
| 对象列表 | 与桌面一致的中性卡片、标题与字段层级；模板 / 页面标识稳定，敏感度保留图标徽章 |
| 对象详情与编辑 | 实色承托字段、输入框和附件；短操作菜单局部玻璃，长内容不在玻璃上阅读 |
| 工具 | 工具图标用统一强调色或正文色，方块 / 分组使用中性底色，不按功能位置分色 |
| 设置 | 与桌面一致的组名、状态色和行层级；移动保留整行点击、开关和独立详情页 |
| 外观设置 | 区分深浅模式、底色方案、强调色、材质档位；显示相同主题名称和缩略图 |
| 登录 | 深色底板与较浅局部玻璃面板沿用共同方向；布局适应软键盘，80% 卡片填色需单独验证文字对比 |
| 更新与文件预览 | 更新区由布局占位，状态与进度用共同语义色；照片工具栏对比独立校准，不能简单沿用玻璃正文色 |

系统状态栏、手势导航区和键盘安全区与应用主题协调；避免内容与底栏重叠。平板导航轨道可先保留稳定实色，等性能证据充分后再决定是否局部玻璃。

## 5 建议的执行顺序

1. **统一主题来源。** Android 不再覆盖共享的底色、文字和强调色；旧 `--md-*` 暂作为派生别名。保留单一 ThemeController，完成缓存首帧、锁定、解锁和账户切换的兼容。
2. **统一材质输入。** CSS、WebGL 与 Kotlin 菜单消费同一解析结果；原生菜单仍使用现有受校验的 payload。新增派生色须转换成渲染器支持的最终数值颜色，不能把 `var()` 或 `color-mix()` 原样传给目前只解析 hex 的 `rgb()`。
3. **迁移核心页面。** 先首页、底部导航和新建菜单，再对象详情、工具、设置。取消索引着色，分清 primary、neutral、quiet；不顺带改变业务功能。
4. **迁移外观偏好。** 旧 ocean / forest / amber 映射为同名共享强调色；不改用户已保存的玻璃档位和主题模式。底色方案首次采用已有账户值，否则采用公共默认；保持现有偏好链路，不建立第二份 Android 主题配置。custom 应得到支持。
5. **验收并回填。** 浏览器检查布局，实际 Android WebView 检查主题、原生菜单和性能；公共 token 改动补 macOS / Windows 回归。iOS 先做共享样式验证，再单独验原生能力，不以 Android 结果替代。

旧 `--md-*` 名称只作为迁移桥梁，逐组件核对中立表面语义后移除，遵守第一轮待执行的表面迁移前置，不借调色一次性删除兼容选择器。

## 6 验收重点

- 同一个主题 / 强调色在两端得到同一组正文色、主文字色和操作色；关闭玻璃不会切回另一套配色。
- 最终叠加表面的常规文字以 4.5:1、大字和必要控件轮廓以 3:1 为设计检查目标；玻璃需对多种底页验证，不能只计算填色本身。[文字对比要求](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[非文字控件对比要求](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)。
- 320 / 390px 手机、平板、文字放大和软键盘下无裁剪或覆盖；保持对象详情、工具子页和附件菜单的返回逻辑。
- 系统深浅主题与媒体查询不一致、账户切换和首帧缓存时不出现文字与画布分别用不同主题的旧问题。
- 系统 blur 关闭、WebGL 丢失、旧 WebView 和减少透明度时回退为同主题实色；减少动效保留静态材质。
- 滚动时避免正文卡片逐个模糊；后台、离屏和静止时停止装饰重绘。性能测试报告实际设备、系统、WebView 和场景，不以桌面浏览器证明手机功耗或流畅度。

建议采用“共用色彩与层级，平台负责几何与材质实现”作为本轮原则。先确认首页、工具和底部菜单的视觉，再登记具体重构任务；此讨论稿不改变已有客户端与执行台账。


## 2026-10-07 实施状态

本方案随后已获授权实施，macOS 前端改造及回归在先，Android 统一色彩、材质输入、核心表面与外观设置在后。上述源码事实是讨论时基线，不代表改造后的实现。[实施记录](android-glass-implementation.md#2026-10-07共用桌面主题的前端重构)、[执行台账](../REFACTOR_FRONTEND_EXECUTION_REPORT_2026-10-07.md)区分已完成实现、浏览器检查与原生待验范围；iOS 原生效果没有沿用 Android 通过结论。
