# 附件「转发」功能设计与实现方案

> 状态：已实现（2026-08-10 落地，实现偏差见 §9）
> 日期：2026-08-10

## 1. 需求背景

为附件增加「转发」能力，使用户能把 Vault 中的附件文件直接发送给其他应用（典型场景：转发到微信）。

### 平台范围决策

| 平台 | 方案 | 理由 |
|------|------|------|
| **Android** | 系统分享面板（`Intent.ACTION_SEND` + FileProvider） | 微信等目标应用主要在手机端；系统分享面板是标准交互，可直发微信 |
| **桌面端（macOS/Windows）** | 复制附件到临时目录后 `opener::reveal()` 在文件管理器中显示，用户自行拖入目标应用 | 桌面操作系统无通用分享面板 API；macOS 原生 `NSSharingServicePicker` 需编写 objc2 代码，投入产出比低，本期不做 |
| **iOS** | 不做 | 项目当前 `attachment_open` 在 iOS 也未真正支持，无现成原生插件先例，工作量最大 |

## 2. 安全考量

1. **明文离开加密 Vault**：分享/转发会把 Vault 内的私密文件以明文交给第三方应用（微信会自行留存副本）。因此**转发前必须弹确认对话框**，明确提示用户：
   - 「转发 "文件名"？文件将以明文离开加密 Vault，接收方应用（如微信）可能留存副本。」
2. **路径校验复用**：`attachment_share` 与 `attachment_open` 共用同一段 vault 路径校验（canonicalize + `..` 拒绝 + `path_within_base`），抽取为共享 helper，避免安全关键代码出现两份副本日后发散。
3. **桌面端 reveal 临时副本而非 vault 原文件**：复制到 `temp_dir/solosoul_share/` 后再 reveal，避免把用户带进隐藏的 vault 目录、也避免用户误改 vault 内文件。
4. **脱敏日志**：与 `attachment_open` 的既有规范一致——错误日志不记录完整路径、文件名、对象 ID。

## 3. 后端设计（Rust）

### 3.1 `attachment_share` 命令（`tauri/src-tauri/src/commands/attachment.rs`）

- 将 `attachment_open`（现 :986-1052）中的「加载对象 → 查找附件 → 取路径 → canonicalize + `..` 拒绝 + `path_within_base` 校验」抽为私有 helper：

  ```rust
  fn resolve_verified_attachment_path(
      svc: &VaultService,
      object_id: &str,
      attachment_id: &str,
  ) -> Result<(std::path::PathBuf, AttachmentMeta), String>
  ```

  `attachment_open` 改为调用该 helper（行为不变，仅去重）。

- 新增命令：

  ```rust
  #[tauri::command]
  pub async fn attachment_share<R: Runtime>(
      app: AppHandle<R>,
      state: State<'_, AppState>,
      object_id: String,
      attachment_id: String,
  ) -> Result<(), String>
  ```

  - 调 helper 获得校验后的 `(path, att)`。
  - `#[cfg(target_os = "android")]`：`app.state::<AttachmentImportPluginHandle<R>>().share_file(OpenFilePayload { path, mime_type })`（复用现有 `OpenFilePayload`，字段 `path/mimeType` 相同）。
  - `#[cfg(not(target_os = "android")])`：复制到 `std::env::temp_dir().join("solosoul_share")`（`create_dir_all`，同名覆盖），然后 `opener::reveal(&dest)`（opener 0.7.2 已含 `reveal()`，已核实）。

### 3.2 插件句柄（`tauri/src-tauri/src/attachment_import_plugin.rs`）

- `AttachmentImportPluginHandle` 新增 `share_file(&self, payload: OpenFilePayload) -> Result<(), String>`，仿照现有 `open_file()`（:153-166）：Android 走 `run_mobile_plugin::<serde_json::Value>("shareFile", payload)`；非 Android 返回 "only supported on Android"。

### 3.3 命令注册（`tauri/src-tauri/src/lib.rs`）

- invoke_handler 在 `attachment_open`（:471）后注册 `commands::attachment::attachment_share`。
- ACL 权限列表在 `"attachment_open"`（:936）后加 `"attachment_share"`。

## 4. Android 实现（Kotlin）

`tauri/src-tauri/gen/android/app/src/main/java/com/solosoul/app/AttachmentImportPlugin.kt` 在 `openFile()`（:700-752）后新增：

```kotlin
@Command
fun shareFile(invoke: Invoke)
```

实现要点（复用 `openFile` 的现成基础设施）：

1. 解析 `OpenFileArgs`，校验源文件存在。
2. 复制到 `filesDir/open_temp/`（现有暂存目录，FileProvider 已配置覆盖）。
3. `FileProvider.getUriForFile` 生成 content URI。
4. 构造 `Intent(Intent.ACTION_SEND)`：`setType(mimeType)` + `putExtra(Intent.EXTRA_STREAM, uri)` + `FLAG_GRANT_READ_URI_PERMISSION`，`Intent.createChooser(intent, null)` 启动系统分享面板。
5. PDF 不做特殊分支（分享场景不需要 `PdfPreviewActivity`）。
6. `ActivityNotFoundException` → reject「没有应用可接收此文件」；其他异常 reject + `Log.e`。

## 7. 明确不做的范围

- 不做 iOS 分享。
- 不做 macOS `NSSharingServicePicker` 原生分享面板。
- 不动 CLI（`solosoul_cli` 的 `/attach` 无转发需求）。
- 不清理 `open_temp` / 临时目录旧文件（沿用现状）。

## 9. 实现记录与偏差

> 2026-08-10 实现落地。除以下偏差外均按本设计执行，验证：`cargo check --tests` 通过（本机 `cargo test` 因预先存在的 0xc0000139 DLL 加载问题无法启动，CI 在 ubuntu 运行）、`tsc`/`eslint`/`vitest` 全量通过（69 文件 604 用例）、ACL 一致性 192 命令。macOS 原生分享面板代码额外通过 `cargo check --target x86_64-apple-darwin` 交叉类型验证（临时 crate 仅依赖 objc2 系，纯 Rust 无 C 依赖）。

1. **opener `reveal` 需显式启用 feature**：设计 §3.1 称「opener 0.7.2 已含 reveal()」，实际 `reveal` 在 opener 0.7.2 中被 `#[cfg(feature = "reveal")]` 门控，`src-tauri/Cargo.toml` 已改为 `opener = { version = "0.7", features = ["reveal"] }`。
2. **桌面复制走 `spawn_blocking` 并提前释放读锁**：`attachment_share` 将 vault_service 读锁放在块作用域内（guard 在 await 点前销毁，同时满足 async 状态机 Send 约束），复制/`reveal` 在 `spawn_blocking` 中执行，避免大文件复制阻塞 tokio worker。
3. **临时文件名防御加固**：`file_name()` 对 `.`/`..` 原样返回，`share_dir.join("..")` 会写出临时目录，故在 `solosoul_share` 复制前显式拒绝 `.`/`..` 文件名。
4. **iOS 显式拒绝**：`#[cfg(target_os = "ios")]` 分支返回「not supported on iOS」，与设计「iOS 不做」一致（attachment_open 仍沿用旧行为，iOS 落入 opener::open，二者保持文档既定差异）。
5. **Kotlin 补充 `clipData`**：`shareFile` 在 `ACTION_SEND` 上同时声明 `ClipData.newRawUri(null, uri)`，保证 Android 10+ 接收方读取 `EXTRA_STREAM` 时 URI 授权可靠投递。
6. **透传链含中间组件**：设计只列了 `AttachmentRow`/`AttachmentListItem`，实际链路 `AttachmentPageCard → AttachmentObjectGroup → AttachmentRow`（全局附件页）与 `AttachmentViewer → AttachmentListItem`（对象卡）均新增 `onShare` 透传。
7. **单测落在 helper 而非命令**：`resolve_verified_attachment_path` 的 5 个用例（库内解析/库外拒绝/`..` 拒绝/实体缺失/文件缺失）直接测纯逻辑，不触发 `opener`/Android 插件；测试通过 `create_account_with_id + unlock` 构造已解锁 `VaultService`。
8. **macOS 改用原生分享面板 `NSSharingServicePicker`**（§8 新增）：设计 §1 原定桌面统一走 `opener::reveal` 降级方案。用户反馈后改用方案 ②——macOS 分支改为 `NSSharingServicePicker::showRelativeToRect:ofView:preferredEdge:` 系统分享面板（复制到 `solosoul_share` 临时目录 → 主线程 AppKit 调用），Windows/Linux 保留 `opener::reveal`。
   - `src-tauri/Cargo.toml` 新增 `objc2-foundation` 直接依赖（`NSString`/`NSURL`/`NSArray`/`NSGeometry`/`objc2-core-foundation` features）；`objc2-app-kit` 增加 `NSSharingService`/`NSView`/`NSResponder` features
   - `NSSharingServicePicker` 不是 `Send`，通过 `tauri::AppHandle::run_on_main_thread` 调度到主线程 + `tokio::sync::oneshot` 错误回传
   - 面板由 `Box::leak` 保持存活（每次分享泄漏一个轻量对象，量级可忽略）
9. **Windows 改用系统分享面板 `IDataTransferManagerInterop`**（§8 新增）：设计 §1 原定桌面统一走 `opener::reveal` 降级方案；macOS 落地原生分享面板后，Windows 同步落地方案 ②——Windows 10 1809+ 分支改为 WinRT Share Contract 系统分享面板（复制到 `solosoul_share` 临时目录 → 主线程 `ShowShareUIForWindow`），低于 1809 或 `IsSupported()==false` 时降级 `opener::reveal`。
   - `src-tauri/Cargo.toml` 的 windows 依赖增加 `Storage_Streams` feature（`StorageFile` 门控项）并新增 `windows-collections = "0.2"` 直接依赖（`IIterable` 构造）；已有 `ApplicationModel_DataTransfer`/`Storage`/`Win32_UI_Shell`/`Win32_System_WinRT`/`Foundation` features 复用
   - 事件流：`RoGetActivationFactory::<IDataTransferManagerInterop>` → `GetForWindow::<DataTransferManager>(hwnd)` → `DataRequested(handler)` → `ShowShareUIForWindow(hwnd)`；handler 内 `StorageFile::GetFileFromPathAsync().get()` → `IIterable<IStorageItem>` → `SetStorageItems` → `DataRequest::SetData`
   - `DataTransferManager`/事件 token 非 `Send`，通过 `run_on_main_thread` 调度 + `oneshot` 错误回传；`(dtm, token)` 由 `Box::leak` 保持存活（同 macOS picker 策略）
   - windows-collections 的 `IIterable` 元素类型为 `T::Default = Option<T>`，接口元素用 `Vec<Option<IStorageItem>>` 经 `From` 构造；`DataRequest::SetData` 的 `Param<DataPackage>` 由 `&package` 满足（`impl<T,U> Param<T, InterfaceType> for &U`）
   - 验证：Windows 本机 `cargo check --tests` 通过（Windows 可本地直接编译，无需交叉验证）；clippy 仅剩预先存在的 window.rs dead-code
   - 评审后加固：① 抽取共享 `copy_to_share_dir` helper（macOS/Windows/Linux 三处「建目录 + 文件名清理 + `.`/`..` 拒绝 + 复制」重复块收敛为一处，防漂移）；② `ShowShareUIForWindow` 失败时降级 `opener::reveal`（与 `IsSupported` 降级路径统一）；③ 只泄漏 `DataTransferManager`（token 是 `i64` Copy，无需保留）
