# LLM 流式聊天归属与保存约定

本规范记录 RF-002 与 RF-104 的实现约定。适用于聊天页和快捷聊天的共享前端 Store，不定义跨进程写入锁；GUI/CLI 的数据目录互斥由 RF-905 单独处理。

## 请求与投影

每次发送固定 `accountId`、`conversationId`、`requestId` 和目标 `assistantMessageId`。事件必须同时匹配前三者和请求绑定的后端 `sessionGeneration`。后端代次取首个合法事件并固定，不与前端本地代次数值比较。前端会话票据在锁定、账户切换、同账户重新解锁时失效；旧事件、旧监听器注册结果和旧异步回调不能恢复已清理状态。

共享 Store 按账户、对话保存请求和消息快照。聊天页与快捷入口只投影对应快照，不把全局 chunk 写入当前列表最后一条消息。切换视图不取消后台请求；一个入口读取已保存对话时不清除另一个入口仍需要的共享回复。敏感内容在会话失效时统一清除。

同一账户、对话的发送与改名、删除、恢复操作同步占位，两个启动顺序均互斥；不同对话可独立处理。元数据操作结束时还须检查当前会话/视图归属，不能修改等待期间新选中的对话。

## 保存与结算顺序

每轮发送先读取已有对话的规范历史和元数据，再追加一次本轮用户消息。模型请求与发送前保存均使用这份历史；不得以某一入口的旧消息覆盖另一入口已保存的回复。首次创建不靠 UI 消息数量推断是否已保存，既有对话的持久化状态跨重试保留，读取失败或软删除检查失败不能变成新建同 ID 的操作。

发送前 `llm_save_conversation` 保存本轮用户历史，失败时不调用模型；当前视图回退未发送消息并恢复空输入，已读取的规范历史供其他入口继续使用。最终 assistant 回复唯一由 Rust `persist_conversation_reply` 保存，前端流结束后不得再整段覆盖保存。

`isDone` 事件可能包含尾部正文，并且先于后端保存结果。因此前端仍累积尾部正文，持续接纳该请求的后续保存失败事件，直到 `llm_send_message_stream` 的 invoke 结算。该命令返回 `void`，事件发送是 best-effort；成功结算后前端只读规范对话，确认历史前缀与新增 assistant，补齐遗漏正文。确认读取失败或结果不匹配时保留已接收回复并提示记录可能丢失（保存结果未确认），不尝试补写最终回复。

后端持久化失败标记 `__LLM_PERSIST_FAILED__` 保留已收到的正文。失败提示通过共享领取状态只显示一次，包含两个入口同时挂载及入口已关闭的后台场景。成功完成通知只针对登记过的请求，在权限等待后再次校验请求/会话，旧请求不能发送系统通知或兜底 toast。

## 验证边界

RF-104 回归使用真实 Zustand Store、共享 hook 与会话票据，模拟 Tauri 事件、invoke 和系统权限等待。它验证前端归属、保存调用次数和并发顺序，不代表真实模型网络、原生通知设备验收或 RF-312 性能结果。执行记录见 [重构修复报告](REFACTOR_EXECUTION_REPORT_2026-09-25.md#rf-104)。
